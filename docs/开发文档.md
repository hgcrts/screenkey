# 幕键

简体中文 | [English](../README.en.md)

把直播间弹幕变成真实的键鼠操作。观众发「左」，主播的电脑就按一下左方向键。

支持 **B站** 与 **抖音** 两个平台，抖音走的是真实的 WebSocket 弹幕协议（不是模拟、不是轮询页面）。

## 项目简介

程序的主干是一条流水线：

```
抓取弹幕  →  按规则筛选  →  匹配映射表  →  注入按键/鼠标
(抖音/B站)   (ALLOW/DROP)   (精确/包含/   (SendInput 或
                            前缀/正则/感应)  扫描码)
```

- **抓取层**：B站基于 `blivedm`，抖音基于自己手写的 `protobuf_lite` + `websockets`。
- **界面层**：PyQt5 单窗口，四个标签页（连接 / 映射 / 选项 / 日志）。
- **执行层**：Win32 `SendInput` / `keybd_event`，游戏模式下改用扫描码，绕过 DirectInput 游戏的屏蔽。

弹幕抓取跑在后台线程，按键也**刻意**在后台线程执行——`SendInput` 是线程无关的 Win32 调用，
这样界面卡住时按键依然不会延迟。

## 功能特性

| 能力 | 说明 |
| --- | --- |
| **真抖音实时弹幕** | WebSocket + 手写 protobuf 解析 + 本机 Node 常驻进程计算 `signature`。**不是模拟**，实测已抓到真实弹幕。需要本机安装 Node.js。 |
| **B站弹幕** | 基于 `blivedm` + **自实现 WBI 签名**（`danmaku/bilibili_wbi.py`），支持扫码登录（`login/bilibili_qr.py`）。**实测已抓到真实弹幕**（房间 `34348`，30 秒 41 条）。历史上困扰项目的 `-352` 不是出口 IP 风控，而是 `getDanmuInfo` 缺 WBI 签名，签名补齐后即通。**进场/关注**自己解 `INTERACT_WORD_V2`（blivedm 0.1.1 只认旧版 `INTERACT_WORD`），**在线人数**取 `ONLINE_RANK_COUNT` 与 `WATCHED_CHANGE`。 |
| **规则化弹幕筛选** | 有序规则列表，**第一条命中即生效**；支持 ALLOW / DROP / DISPLAY_ONLY / REWRITE 四种动作。 |
| **按键映射** | 键盘与鼠标两套映射；精确 / 包含 / 前缀 / 正则 / 感应（重复字符长按）五种匹配模式；长按动作可设按住时长；按键列是可搜索下拉。 |
| **游戏模式** | 用扫描码（DirectInput）绕过游戏对 `SendInput` 的屏蔽。 |
| **全局热键** | 默认 `Ctrl+Shift+P` 暂停/恢复按键输出，游戏全屏时也能按。 |
| **焦点窗口过滤** | 只在指定窗口是前台时注入键鼠：按 窗口标题 / 进程名 / 窗口类名 匹配（包含 / 精确 / 正则）。非指定窗口在前台时**一个键都不发**，且不消耗冷却。默认关闭。 |
| **注入环境诊断** | 启动自检 + 切换窗口时检查 + `--check-env`：能区分「本进程被限制」与「目标窗口权限更高」，并用**注入回环实测**（注入 1px 鼠标移动再读光标）给出确证结论，不再让用户白猜。 |
| **模拟模式** | 不需要任何真实直播间即可测试全部链路。 |
| **防按键风暴** | 四道闸：每条映射的冷却、全局冷却、同一用户冷却、内容去重；另有「单条弹幕最多触发几个映射」的数量上限。 |
| **单一配置文件** | 全部状态写在一个 `settings.json` 里，原子写（临时文件 + `os.replace`），损坏自动备份为 `.bad` 并回落默认值。 |

默认开箱可用：内置 **25 条键盘映射** + **9 条鼠标映射**（`w/s/a/d`、方向、空格、回车、Esc、数字技能键、`qerf`、左/右键、滚轮等）。

## 安装

### 1. 创建虚拟环境并安装依赖

```bat
cd /d <项目根目录>
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt
```

依赖清单见 [`requirements.txt`](../requirements.txt)：PyQt5、pynput、requests、segno、websockets、aiohttp、blivedm、pytest。
PyQt5 在 Windows 上有官方预编译 wheel，绝大多数依赖都能直接装。

> **⚠️ 有编译工具链时才会顺滑：`blivedm` 锁定了 `brotli==1.0.9`，而 PyPI 上 1.0.9
> 没有任何 Python 3.12 的 wheel**（82 个发行文件里最高的 CPython 只到 cp311，
> 只剩 `Brotli-1.0.9.zip` 源码包）。所以 `pip install -r requirements.txt` 在
> **Python 3.12 上会尝试本地编译 brotli**——装过 Visual Studio Build Tools（含
> 「使用 C++ 的桌面开发」）就能编过；没有编译器的机器会失败。
> 如果卡在这一步，可任选其一：
>
> - 装 [Microsoft C++ Build Tools](https://visualstudio.microsoft.com/visual-cpp-build-tools/) 后重装；
> - 或先用 **Python 3.11** 建环境（3.11 有 1.0.9 的官方 wheel，无需编译）；
> - 或先 `pip install "brotli==1.0.9"` 让它单独编译，再装其余依赖逐个定位问题。
>
> 另外注意：**不要试图把 brotli 升到 1.2.0 来绕过编译**——那会破坏 `blivedm` 的
> 依赖约束（它精确锁定 `==1.0.9`）。本项目已经在 `Accept-Encoding` 层面绕开了
> aiohttp 对 `br` 的自动协商，所以 brotli 只被 `blivedm` 用它自己的
> 一次性 `brotli.decompress()` 调用，不需要升级。

> 如果这个 `.venv` 是用 `python -m venv --without-pip` 建的，`python -m pip` 会报「No module named pip」。
> 先执行 `.venv\Scripts\python.exe -m ensurepip --upgrade`，或者直接用普通方式重建虚拟环境。

### 2. 抖音：安装 Node.js（可选，但要用抖音就必须装）

从 <https://nodejs.org/> 安装 LTS 版本，然后在命令行确认：

```bat
node --version
```

只要 `node` 在 `PATH` 里，程序就能自动找到它；装在非常规位置时用环境变量 `SCREENKEY_NODE` 指定完整路径。

**本项目任何脚本都不会替你自动安装东西**——`启动.bat` 只检查依赖是否齐全，缺了就打印指引然后退出。

## 启动

### 方式一：`启动.bat`（推荐）

```bat
启动.bat              :: 用 pythonw.exe 启动图形界面，不留控制台窗口
启动.bat --console    :: 带控制台启动，能直接看到报错
启动.bat --selftest   :: 只跑离线自检，不开界面、不联网
```

脚本会依次检查：入口文件是否存在 → `.venv` 是否存在 → 依赖是否齐全，任何一步不过就给出明确提示并退出。
没有 `pythonw.exe` 时自动退回 `python.exe`（会多一个控制台窗口）。

### 方式二：直接跑 Python

```bat
.venv\Scripts\python.exe src\screenkey\main.py
```

`main.py` 自己会把 `src` 加进 `sys.path`，**不需要**先 `set PYTHONPATH`；
工作目录也无所谓（项目根、`src\`、甚至 `C:\` 都能跑）。`python -m screenkey.main` 同样可用。

> **这条曾经是坏的。** 早先 `main.py` 把**包目录** `src\screenkey` 插进 `sys.path`，
> 而 `from screenkey import ...` 需要的是它的**父目录** `src`，于是直接跑入口必然
> `ModuleNotFoundError: No module named 'screenkey'`——`启动.bat` 的默认与 `--console`
> 分支因此完全无法启动（`--selftest` 分支因为自己设了 `PYTHONPATH` 而幸免）。
> 它长期没被发现，是因为**所有测试都替它设好了 `PYTHONPATH`**，把被测代码的缺陷兜住了。
> 现在 `tests/test_cli.py::TestBootstrapWithoutPythonPath` 刻意清空 `PYTHONPATH` 来守这条路径；
> `tests/test_cli.py::TestLauncherBat` 另外直接跑 `启动.bat --selftest`，
> 并断言批处理里**不再出现** `PYTHONPATH`——入口既然能自举，就不该再用环境变量打补丁
> （否则默认分支仍会漏，而 `--selftest` 分支又恰好绕过它）。

### 方式三：打包成 exe

```bat
build.bat             :: 按 main.spec 打包
build.bat --clean     :: 先删 build\ 与 dist\ 再打包
build.bat --check     :: 只检查环境与路径，不打包
```

`build.bat` 用 `.venv` 里的 PyInstaller 执行 `main.spec`。**PyInstaller 不在依赖清单里**，
需要单独装（脚本发现缺失会直接报错退出，不会自动安装）：

```bat
.venv\Scripts\python.exe -m pip install pyinstaller
```

产物是 onedir 形态：`dist\幕键\ScreenKey.exe` 加一个 `_internal\` 目录，
**必须整个目录一起拷贝**，不能只拿走 exe。`sign.js` 会被打进 `_internal\screenkey\data\`。

`main.spec` 必须带上这个 JS，原因很直接：抖音的 `signature` 只能由它算出来，
而 `danmaku/signature.py` 是用 `Path(__file__).resolve().parent.parent / "data"` 去找它的；
打包后模块的 `__file__` 落在 `<_MEIPASS>\screenkey\danmaku\...`，
所以 spec 里的 `datas` 目标目录必须写成 `screenkey/data`，两边才对得上。漏了它，
打包版就会报「找不到 sign.js」，抖音连不上（但不会假装连上）。

#### 项目路径含中文时：`build.bat` 会自动处理

**这是本项目打包最容易踩的坑，而且报错信息会把人引向错误的方向。**

如果项目路径里有非 ASCII 字符（例如本机的 `E:\DSHwork\幕键`），
PyInstaller 会这样失败：

```
Exception: Qt plugin directory 'E:/DSHwork/????V2/.venv/Lib/site-packages/PyQt5/Qt5/plugins' does not exist!
```

注意路径里的 `????V2` ——「幕键」四个汉字变成了四个问号。而那个目录**其实存在**。

根因**不是 PyInstaller**，是 **PyQt5 5.15.x 的 `QLibraryInfo` 处理不了非 ASCII 安装路径**：
它把路径按 ASCII 转换，`os.path.isdir()` 于是全部为 False。PyInstaller 的 Qt hook
去读 `PluginsPath` 收集插件，拿到坏路径后直接抛异常。换 PyInstaller 版本没有用。

判别因子只有一条：**路径里有没有非 ASCII 字符**。已经排除的假设包括 codecs 插件缺失、
`locale.setlocale`、`QTextCodec.setCodecForLocale`、`QT_PLUGIN_PATH` / `PYTHONUTF8` /
`PYTHONLEGACYWINDOWSFSENCODING` 等环境变量（六种组合实测全部无效）。也不是 Qt 整体不会处理中文——
`QFileInfo(r"...\幕键\src").exists()` 是 True，**只有 `QLibraryInfo` 这一条计算路径是坏的**。

`build.bat` 会自动调用 `tools\build_helper.py`：检测到非 ASCII 路径时，
在 `%TEMP%` 下建一个**纯 ASCII 的目录联接（junction）**指向项目目录，再从那里构建。

```
[检查] 项目路径含非 ASCII 字符：
       E:\DSHwork\幕键
       非 ASCII 字符：幕弹盘键
[处理] 在 C:\Users\...\Temp\...\dmkb2_build_link 建立指向项目目录的 junction …
       完成：C:\Users\...\Temp\...\dmkb2_build_link
[说明] 产物仍会出现在真实项目目录里（junction 是透明的重定向）：
       E:\DSHwork\幕键\dist\幕键\
```

junction 用 `mklink /J` 创建，**普通用户权限即可，不需要管理员**。产物仍然落在真实的
`dist\` 目录里（junction 是透明重定向）。

> **一个反直觉的细节**：光把工作目录 `cd` 到 junction 是**不够**的。
> `QLibraryInfo` 是按 **`sys.prefix`**（由 python.exe 自身的路径推出）算 Qt 安装前缀的，
> 跟 CWD 无关。所以必须**通过 junction 里的 python.exe 启动**，
> 这样 `sys.prefix` 才是纯 ASCII 的。实测：真实路径的 python.exe 得到
> `sys.prefix = E:\DSHwork\幕键\.venv`（非 ASCII，Qt 路径全部 MISSING）；
> junction 里的 python.exe 得到纯 ASCII 的 `sys.prefix`，Qt 三个路径全部 EXISTS。
> `build.bat` 已经替你做了这件事。

如果不想用 junction，也可以**把项目直接放到纯 ASCII 路径**（例如 `D:\screenkey\`），
那样 `build.bat` 会检测到路径没问题并直接构建，这是最省事的方式。
想手工建 junction 也行：

```bat
mklink /J "C:\dmkb2" "E:\DSHwork\幕键"
cd /d C:\dmkb2
build.bat
```

## 使用说明

### 连接弹幕

界面「连接」标签页：

1. 选平台（B站 / 抖音）。
2. 填房间号——支持直接粘整条直播间链接，程序会自己抠出 ID：
   - B站：`https://live.bilibili.com/12345` 或直接写 `12345`
   - 抖音：`https://live.douyin.com/123456789` 或直接写 `123456789`
3. 按需填写登录凭证（见下）。
4. 点 **「开始接收弹幕」**（界面主控条上最左边的蓝色按钮；勾了模拟模式后它的文案会变成「开始模拟弹幕」）。

> 「连接」只是**标签页**的名字，不是按钮。真正的启动按钮是「开始接收弹幕」。
> 参考项目把两者都叫「连接」，文档与界面因此对不上号。

#### B站登录

- **收弹幕**：只需要 `SESSDATA`。不填也能以游客身份连上收弹幕，只是无法发言——本程序本来也不发言。
- **扫码登录**：点凭证输入框旁边的 **「获取凭证…」** 按钮，用 B站 App 扫码（`login/bilibili_qr.py`）。
- B站接口对**未签名**请求会回 `-352`（历史上因此误判成"IP 被风控"）。本项目已内置
  **WBI 签名**（`danmaku/bilibili_wbi.py`：先取 `nav` 的 `wbi_img`，按混淆表混出
  `w_rid`/`wts`，再把值写进参数、把 `wbi_sign` 折进 `key`），并改用
  `room_init?id=<房间号>` 取真实 `room_id`（旧代码拿短号去查 `room_init?room_id=`，会得到
  `60004` 或 `-352`）。
- **签名后仍报 `-352` 才是真的风控**：这时换房间号没用，换网络出口（家宽 / 手机热点）重试，
  程序不会假报成功。
- **昵称被掩码（`伊***`）曾经是程序的锅，已修**（2026-10-24）：B站对**未登录**的弹幕客户端
  确实会在服务端下发掩码昵称（WS 里还会推一条 `LOG_IN_NOTICE`：*为保护用户隐私，未登录无法查看
  他人昵称*；`DANMU_MSG` 里的 `uid` 也是 `0`）。但"明明扫码登录了还是掩码"另有原因：SESSDATA 以前
  只塞进 aiohttp 的 **cookie jar** 并绑定在 `live.bilibili.com` 上，那是 **host-only cookie**——
  `api.bilibili.com`（登录态自检）和弹幕 WebSocket 真正所在的 `tx-*.chat.bilibili.com` 都收不到，
  服务端因此仍按游客处理。现在改成**会话级 `Cookie` 请求头**（`_session_headers`，所有域名与 WS
  握手都带上）。实测（房间 650 / 真实 room 4350043，40 秒 26 条弹幕）：掩码 0 条、`uid=0` 0 条，
  昵称与网页端一致。连接前仍会先问一次 `nav`：Cookie 失效时在弹幕窗口里明确提示「请重新扫码登录」。

#### 抖音登录

- **抖音不支持扫码登录**。平台 passport 接口现在要求 `ttwid` + `msToken` 一类由 JS 现场生成的设备指纹，
  纯 HTTP 客户端拿不到，二维码根本画不出来（实测 `get_qrcode` 返回 `error_code: 4031` 并下发反爬挑战页）。
  **与其做一个点了必然失败的按钮，不如老实告诉你怎么做。**
- 请手工从浏览器复制 Cookie：

  1. 用 Chrome/Edge 打开 `https://live.douyin.com/<房间号>`；
  2. `F12` → Application（应用）→ Cookies → `https://www.douyin.com`；
  3. 至少复制 `ttwid`，建议连 `sessionid` / `msToken` / `__ac_nonce` 一起复制；
  4. 把内容整体粘进程序的登录框（支持 `name=value; name=value` 连写、`document.cookie` 格式、
     以及 DevTools 那种 `name<TAB>value` 的表格粘贴）。

- 程序在没有 Cookie 时也能连：它会先 GET 一次 `https://live.douyin.com/` 暖场，
  服务端在 `Set-Cookie` 里下发 `ttwid`，程序合并后再去请求直播间页。带上浏览器里
  手工复制的完整 Cookie 成功率更高（可少一次请求，也不容易被风控）。

### 筛选规则

「选项」→ 筛选规则。规则是**有序列表**，从上往下第一条命中的就生效，后面的不再看。
如果一个都没命中，**默认放行**（保持「不加规则就等于不过滤」的直觉）。

四种动作：

| 动作 | 行为 |
| --- | --- |
| `ALLOW` | 放行，参与按键映射 |
| `DROP` | 丢弃，界面也不显示 |
| `DISPLAY_ONLY` | 界面显示，但不触发按键 |
| `REWRITE` | 改写内容后放行（配合 `rewrite_to` / `strip_prefix`） |

每条规则由若干**条件**组成，可匹配的字段有 `content`（内容）、`nickname`（昵称）、`user_id`、
`platform`（平台）、`msg_type`（消息类型）；比较方式有 `equals`、`contains`、`not_contains`、
`startswith`、`endswith`、`regex`、`not_regex`、`in`、`not_in`、`length_gt`、`length_lt`、`length_eq`。

一条规则里的多个条件怎么组合，由规则属性 `match_any` 决定，界面上是「条件之间」下拉框：

| 选项 | `match_any` | 含义 |
| --- | --- | --- |
| 全部满足（与） | `false`（默认） | 每个条件都成立才命中本规则 |
| 任一满足（或） | `true` | 只要有一个条件成立就命中本规则 |

**这个开关不是可选项。** 用 `DROP` 表达「长度必须落在 [min, max] 内」时，条件必须写成
「太短 **或** 太长 → 丢弃」；在「与」语义下这两个条件永远不可能同时成立，规则会**彻底失效**。

> **界面上的默认值是「与」，不是「或」。** `ui/filter_editor.py` 先加
> `("全部满足（与）", False)` 再加 `("任一满足（或）", True)`，所以下拉框停在第一项；
> `FilterRule.match_any` 字段本身也默认 `False`（`filters/rules.py`）。
> 也就是说，**你新建一条规则时拿到的是「与」**，写「长度必须落在 [min, max] 内」这类
> 规则必须自己手动切成「或」。只有 Python 侧的工厂函数 `length_rule()` 才预先帮你设了
> `match_any=True`（`filters/rules.py`）——但那个函数在界面上没有入口。
> 早先的文档写成「长度模板现已默认选中「或」」，是**错的**：那说的是工厂函数，
> 不是界面。

**默认规则只有两条**，开箱即用的意图是「不丢任何弹幕，但别让观众进出就乱按键」：

1. `进入直播间不触发按键` —— 对 `ENTER` / `FOLLOW` / `LIKE` / `STATS` 类型的消息执行 `DISPLAY_ONLY`；
2. `默认放行` —— 兜底 `ALLOW`。

> **关于「规则模板」**：`filters/rules.py` 里确实有四个工厂函数
> `keyword_block_rule()` / `user_block_rule()` / `prefix_rewrite_rule()` / `length_rule()`
> （默认规则名分别是「屏蔽关键词」「屏蔽用户」「剥掉指令前缀」「长度限制」），
> 但它们是给**写 Python 的人**用的，**界面上没有任何模板按钮或模板下拉框**——
> 界面只有「新增 / 删除 / 上移 / 下移 / 加条件 / 删条件 / 保存 / 取消」。
> 早先的文档写成「界面里还提供常用规则模板」，是**错的**。
> 要在界面上做出这些规则，请手工加条件。**注意下拉框里的实际文案**（下面这张表
> 左列是工厂函数名，右列是你在界面上真正要选的东西）：
>
> | 想要的模板 | 界面上的做法 |
> | --- | --- |
> | 屏蔽关键词 | 命中后 `丢弃（不显示、不触发）`；加条件 字段 `弹幕内容` 判断 `正则匹配` 值 `关键词1\|关键词2` |
> | 屏蔽用户 | 命中后 `丢弃（不显示、不触发）`；加条件 字段 `用户ID` 判断 `属于（逗号分隔）` 值 `uid1,uid2` |
> | 剥掉指令前缀 | 命中后 `改写内容（再按改写后的匹配）`；加条件 字段 `弹幕内容` 判断 `开头是` 值 `!`；再把「剥离前缀」填 `!` |
> | 长度限制 | 命中后 `丢弃（不显示、不触发）`；**「条件之间」先切成 `任一满足（或）`**；加条件 字段 `弹幕内容` 判断 `长度小于` 值 `2`，再加一条 字段 `弹幕内容` 判断 `长度大于` 值 `50` |
>
> 界面上**没有**「长度」这个字段——长度类判断是挂在 `弹幕内容` 字段上的三个
> 独立判断（`长度大于` / `长度小于` / `长度等于`），它们的值直接当数字用。
> 界面里「判断」下拉框的全部 12 个选项见「筛选规则」正文。

#### 「长按(秒)」：长按到底按多久

「动作」选成**长按**时，按住的时长由这一列决定：

- **这一列是跟着动作出现的**：只有当表里至少有一行的「动作」选了**长按**，
  「长按(秒)」列才会显示出来，而且只有长按那几行有输入框。
  选「按下 / 松开 / 按下并松开」的行看不到这一格，也就不会误以为它对自己生效。
  把某一行的动作改成「长按」，这一列当场出现；全部改回去，整列收起。
- 范围 `0.05` – `5.00` 秒，步进 `0.05`，两位小数；默认 `0.50`。
- 值**独立保存**：动作改成别的、这一格藏起来时值仍然留着，改回长按不用重新填。
- 载入时会夹进范围（手改 `settings.json` 写成 `99` 会显示成 `5.00`，写成负数会显示成 `0.05`）。
- 下限 `0.05` 秒再短已经等同点按；要按住更久建议配两条映射（「按下（不松开）」+「松开」），
  而不是把一条长按设成好几秒——长按期间其它动作会被这条映射自己占着。
- 「映射」标签页的只读总表里，**「动作」列也是中文**（`按下并松开（点按）` / `长按` / `单击` / `向上滚动` 等），
  长按还会带上时长（`长按 1.25s`），一眼能看出这个值存没存下来。
  总表与编辑器下拉共用 `ui/mapping_editor.py` 的同一份文案，不会一边中文一边英文。

#### 多个触发词：一个映射可以配多个词

触发词写 `w,上,前`，就表示**弹幕等于 `w`、或 `上`、或 `前`** 都触发同一条映射。
中英文逗号都认（`,` 与 `，`），两侧空白会被自动去掉。

> 这是**已修复**的行为。早先的实现把 `triggers` 写成 `[self.trigger]`——整串当作**一个字面量**，
> 于是用户照界面提示写 `w,上,前` 之后，发 `w` / `上` / `前` 一个都不触发，
> 只有弹幕原文恰好是 `w,上,前`（连逗号一起）才触发。界面上承诺了三件事，实现只做了一件。
> 现在数据层（`input/mappings.py` 的 `triggers` / `normalized_triggers`）与匹配层
> （`input/matcher.py` 遍历 `normalized_triggers`）都已改对，`tests/test_matcher.py::TestMultiTrigger`
> 与 `tests/test_mappings.py` 守住它。

几个要点：

- **去重且保序**：`w,w,W` 在不区分大小写时只算一个 `w`（否则匹配循环会白跑一遍，
  且"最长优先"的挑选结果会不稳定）。
- **冷却属于整条映射，不属于单个词**：`w` 与 `上` 共享同一个 `cooldown`。
  这是刻意的——用户把 `w` 改成 `w,上` 不该凭空多出一份独立冷却。
- **触发词更长的优先**：命中时按「命中词的长度」排序，长度相同时精确匹配优先于包含匹配。
  所以 `abcd` 与 `ab` 两条都开 `contains` 时，弹幕 `abcd` 命中 `abcd`。
- **正则模式下逐个词试**：某一个词的正则写错了（`re.error`）只跳过它，不影响同一条映射里的其它词。
- **弹幕原文恰好带逗号时不再命中**：`w,上,前` 现在不等于任何单个触发词，这是上述语义变更的
  自然结果——界面承诺的是「三个触发词」，不是「一个含逗号的触发词」。

#### 五种匹配模式

| 模式 | 界面显示 | 行为 | 例子 |
| --- | --- | --- | --- |
| `exact` | 精确匹配 | 内容完全等于触发词 | 触发词 `左` 只匹配 `左` |
| `contains` | 包含 | 内容包含触发词 | 触发词 `6` 命中 `6666` |
| `startswith` | 开头是 | 内容以触发词开头 | 触发词 `打` 命中 `打他` |
| `regex` | 正则 | 用正则匹配（写错了当作不匹配，静默跳过） | `^6+$` |
| `sensing` | 感应（重复字符） | 把重复字符识别成连按/长按 | `666666` → 按 6 并判定为**长按** |

匹配有严格的**三级顺序**，`match_mode` 只决定第三级怎么走：

1. **精确**：`内容 == 触发词`（不区分大小写时先转小写）→ 直接命中。
2. **感应**：开了 `enable_sensing`（或 `match_mode` 就是 `sensing`）时，检测「整串重复字符」。
   重复次数 `>= short_press_count` 才算数，`>= long_press_count` 判为长按。
3. **声明式**：按 `match_mode` 走 `contains` / `startswith` / `regex`。
   **`exact` 与 `sensing` 到这里会直接返回「不匹配」**——刻意不放宽成「包含」，
   否则「精确」会退化成「包含」，短触发词就会乱触发（参考项目踩过这个坑）。

感应模式是给刷屏弹幕准备的：观众发一串 `wwwww`，程序识别成一个持续的方向输入，而不是按 5 次。
默认的 25 条键盘映射里**有 21 条开了感应**（`w/s/a/d`、`上/下/左/右`、`空格`/`space`、
`1`-`7`、`q/e/r/f`）；只有 4 条没开：`回车`、`enter`、`esc`、`退出`。

**限流设置**（「选项」里能调的 4 个，与每条映射自带的 `cooldown` 叠加生效）：

| 界面上的名字 | 字段 | 默认 | 作用 |
| --- | --- | --- | --- |
| 单条弹幕最多触发： | `max_actions_per_message` | `1` | 一条弹幕最多命中几条映射（**设为 0 就完全不匹配**） |
| 全局动作间隔（秒）： | `global_cooldown` | `0.0` | 任意两次动作之间的最小间隔 |
| 同一用户冷却（秒）： | `per_user_cooldown` | `0.0` | 同一个用户两次动作之间的最小间隔 |
| 相同内容去重窗口（秒）： | `dedupe_window` | `0.0` | 窗口内内容完全相同的弹幕只算一次 |

其中前四项里**只有 `max_actions_per_message` 是「数量上限」**，其余三个都是「时间间隔」；
真正意义上拦动作的**四道闸**是：`这条映射的 cooldown`、`同一用户冷却`、`全局冷却`、`内容去重`
（`max_actions_per_message` 是在更前面决定「一次弹幕最多匹配几条」）。
检查顺序（全程持锁，先到先拦）：`总开关` → `去重` → `这条映射的 cooldown` → `同一用户冷却` → `全局冷却`。
`delay` 是在**锁外** sleep 的（上限 5 秒），所以它不会把整条流水线堵住。

弹幕刷屏时它们能防止按键风暴。想更狠一点，直接按 `Ctrl+Shift+P` 暂停按键输出。

#### 鼠标映射

9 条默认鼠标映射，字段与键盘映射同构，只是把「按键」换成「鼠标键」、动作换成鼠标动作：

| 字段 | 含义 | 默认值 |
| --- | --- | --- |
| `button` | `left` / `right` / `middle` | `left` |
| `move_x` / `move_y` | `移动` 动作的位移量（像素）；**允许负值**（负=左/上） | `0` |
| `scroll_amount` | 滚轮动作的滚动格数（1 格 = 120 单位，即 Windows 的 `WHEEL_DELTA`） | `1` |

`移动` 默认是**相对位移**；写绝对值需要走 `MouseController.move(..., absolute=True)`（配置里没有暴露）。

### 游戏模式

游戏用 DirectInput 读键盘时，会**忽略** `SendInput` 合成的按键事件——这是刻意设计的反作弊/防宏机制。
开启「游戏模式」后，程序改用**扫描码**（scancode）直接下发，多数 DirectInput 游戏能收到。

- 全局开关：选项 → 「游戏模式（用扫描码发送，兼容 DirectInput 游戏）」。
- 单条映射粒度：映射的 `use_scancode` 字段。
- 四种发送后端都实现了，日志里能看到当前用的是哪个：

  | 后端 | 说明 |
  | --- | --- |
  | `sendinput` | `SendInput`（普通模式默认，通用） |
  | `directx` | 扫描码 + 虚拟键码（游戏模式默认） |
  | `scancode` | 纯扫描码（走 `keybd_event`） |
  | `keybd_event` | 兼容旧程序 |

> 游戏模式切换**真的会换后端**。早先的实现里 `set_game_mode()` 判断的是 `self.send_method`，
> 而它在构造时就已经被填成非空默认值，**那个条件永远为假**——勾选框是个纯粹的空操作。
> 现在用独立的 `_explicit_send_method` 标志记录「用户是否显式指定过后端」，
> 显式指定过就不覆盖它。

注意：游戏模式能解决的是「按键发出去了但游戏没反应」，**解决不了**带内核级反作弊的游戏。
在那类游戏里用任何宏工具都可能被封号，风险自负。

### 全局热键

默认 **`Ctrl+Shift+P`** 暂停/恢复按键输出。这是全局热键，游戏全屏时也有效，
直播事故时按它比切窗口快。可在「选项」→「暂停/恢复热键：」里改，或用 `--no-hotkey` 彻底关掉。

热键名称大小写不敏感、顺序不敏感、重复键自动合并：

| 你写的 | 归一化结果 |
| --- | --- |
| `Ctrl+Shift+P` | `ctrl+p+shift` |
| `shift+Ctrl+Q` | `ctrl+q+shift` |
| `cmd+q` | `q+win` |
| `page_up+ctrl` | `ctrl+pageup` |
| `ctrl+ctrl+q` | `ctrl+q`（重复键合并） |
| `  space + ctrl ` | `ctrl+space`（空白被忽略） |

别名表还认得 `control`→`ctrl`、`return`→`enter`、`esc`→`escape`、`cmd`/`cmd_l`/`cmd_r`→`win`、
`ctrl_l`/`ctrl_r`→`ctrl`、`shift_l`/`shift_r`→`shift`、`alt_l`/`alt_r`/`alt_gr`→`alt`。

> 归一化的结果是**按字母序**拼起来的。早先的实现注册时按书写序、查表时按字母序，
> 于是 `ctrl+shift+q` 这类热键**永远不可能触发且不报错**；现在两边都走 `normalize_hotkey`。
> 另一处老缺陷是归一化用了生成器推导、不去重，`ctrl+ctrl+q` 的规范串与运行时按下的键集合对不上，
> 同样永不触发——现在改成了集合推导。

`--no-hotkey` 启动后会直接停掉热键监听。没装 `pynput` 时程序照常运行，只在日志里记一条
「提示：未安装 pynput，全局热键不可用（pip install pynput）。」。

### 焦点窗口过滤（只在指定窗口生效）

**它解决什么问题**：默认情况下，弹幕按键会发到**当时的前台窗口**。你切出去回个消息、
看一眼浏览器，观众的 `666666` 就打进了聊天框/地址栏里——轻则乱打字，重则误操作。

打开「选项」→「焦点窗口（只在指定窗口为前台时才注入按键）」后，**只有你指定的那个窗口
是前台窗口时才会发按键**；别的窗口在前台时，一个按键都不发。

| 字段 | 说明 |
| --- | --- |
| 启用：非指定窗口在前台时不发送任何按键 | 总开关，默认**关**（关着＝旧行为） |
| 比对目标： | `窗口标题` / `进程名` / `窗口类名`，默认标题 |
| 匹配方式： | `包含` / `精确` / `正则`，默认包含 |
| 目标内容： | 你要匹配的文字，例如 `YuanShen.exe` |
| 区分大小写 | 默认不区分 |
| 从当前打开的窗口选择… | 列出当前可见窗口，选一个自动填进去 |
| 刷新状态 | 立刻重算下面那条实时状态 |

下面那行**实时状态**会每秒刷新一次，直接告诉你现在到底会不会注入，例如：

```
当前前台：原神　[YuanShen.exe] → 会注入按键
当前前台：Google Chrome　[chrome.exe] → 不注入（窗口不匹配）
```

**推荐用「进程名」而不是标题**：游戏标题常带等级、房间名、更新公告，会变；
进程名（`YuanShen.exe`、`GenshinImpact.exe`）不会。选「进程名」+「精确」是最稳的组合，
而且精确匹配进程名时**带不带 `.exe`、大小写不同都算同一个**（填 `genshinimpact` 也能匹配
`GenshinImpact.exe`）。

几个刻意的设计（都由测试锁住）：

- **拦在注入之前**，不是"发出去再让系统忽略"——这个功能的意义就是按键根本不该出现在别的窗口里。
- **正则写错＝不匹配**（fail closed），而不是"匹配一切"。正则写错却继续注入，等于把按键打进
  你当时正在看的任意窗口，正是这个功能要防的事。写错会在日志里留一条 warning。
- **读不到前台窗口也＝不匹配**。取不到就不发，绝不赌。
- **被拦下的那次不消耗冷却**。否则你切回游戏后还要再等一个冷却，体感就是"切回来了还是没反应"。
- **改完立即生效**，不用重连、不用重启。
- 开着过滤但**还没填目标**时按"没配好"处理：不断按键（而不是匹配一切）。

> 判定同时**不**依赖"跑自检时恰好哪个窗口在前台"：`--selftest` 与测试里引擎处于空跑模式，
> 焦点过滤不参与判定，所以自检结果可复现。

对应的配置字段（`settings.json` → `input.focus_filter`）：

```json
{
  "input": {
    "focus_filter": {
      "enabled": true,
      "pattern": "YuanShen.exe",
      "field": "process",
      "match_mode": "exact",
      "case_sensitive": false
    }
  }
}
```

`field` 只认 `title` / `process` / `class`，`match_mode` 只认 `contains` / `exact` / `regex`，
写别的会被收敛回默认值（`title` / `contains`）——拼错一个字母不该表现成"填了却不生效"。

### 模拟模式

勾选连接页里的 **「启用模拟弹幕（不连接任何平台，适合先验证映射是否正确）」**，或加 `--simulate`，
程序不连任何直播间，直接循环吐内置的测试弹幕。
用来验证映射表写对没有、按键有没有真的生效、游戏能不能收到——不需要真的有观众。

- 「发送间隔（秒）：」可调（`0.1` - `10.0`，默认 `0.8`）。
- 「手动发一条」按一次发一条；「发一组测试弹幕」按一次把内置序列全发一遍。
- 内置序列：`666666`、`w`、`s`、`上`、`下`、`左`、`右`、`左键`、`右键`、`上滚`、`1`、`2`——
  刻意覆盖了长按感应、方向键、中文触发词、鼠标左右键与滚轮。

## 快速上手（5 分钟）

不想读全文的话，照这个顺序走一遍，就能看到「弹幕变成按键」的完整链路：

```bat
:: 1. 装依赖（见「安装」；有编译工具链会顺滑很多）
cd /d <项目根目录>
python -m venv .venv
.venv\Scripts\python.exe -m pip install -r requirements.txt

:: 2. 先确认程序本身没坏（不联网、不开界面，11 项检查）
启动.bat --selftest

:: 3. 用模拟弹幕跑通整条链路（不连任何直播间）
.venv\Scripts\python.exe src\screenkey\main.py --simulate
```

第 3 步会弹出界面并自动进入模拟模式。此时：

1. 打开一个能看按键的窗口（记事本最方便，**别开输入法**）；
2. 在界面里点「开始模拟弹幕」；
3. 看记事本：模拟序列里的 `w` / `s` / `上` / `左` 等会真的敲进去。

然后想接真实直播间，按这个顺序：

| 步骤 | 做什么 | 怎么确认成功了 |
| --- | --- | --- |
| 1 | 「连接」标签页选平台、填房间号（可整条 URL 粘进去） | 输入框下方的提示会跟着平台变 |
| 2 | 按需填凭证（B站扫码 / 抖音手工 Cookie） | B站扫码成功后 `SESSDATA` 框会被自动填上 |
| 3 | 点 **「开始接收弹幕」** | 主控条右侧的状态变成「已连接」 |
| 4 | 看「日志」标签页与状态栏统计 | 统计数字在涨 |
| 5 | 看 `danmaku.log` | **文件在涨才是真的收到了** |

> **最重要的一条**：「已连接」只表示**传输层就绪**，不等于收到过弹幕。
> 绝大多数直播间极其安静，几分钟没人说话是常态。别把「没弹幕」当成「连不上」——
> 判据永远是 `danmaku.log` 在涨、统计数字在涨。详见「如何验证真的连上了」。

想换成自己的按键，去「映射」标签页 →「编辑映射…」：按键那一列是**可搜索下拉框**，
直接打字就能筛（支持中文名，如 `空格`、`方向键 ↑`），也可以照旧手填；
动作选「长按」后，右边才会出现「长按(秒)」列让你调按住多久。

聊天弹幕保持默认文字色——旧版按类型给整行上色，一屏三四种颜色同时闪，读起来很吵。

显示单行格式：`[时:分:秒] [平台中文名] 昵称: 内容`（时间与平台受「选项」里「显示时间」/「显示平台」控制）。
系统提示（连接/断开/错误）用灰色显示，和观众弹幕区分开。

导出的文本文件里格式**略有不同**：时间是完整日期时间，平台写的是原始 id：

```text
[2025-01-01 12:00:00] [douyin] 某观众: 666666
[2025-01-01 12:00:03] [bilibili] 另一个观众: w
```

即导出用 `[{YYYY-MM-DD HH:MM:SS}] [{platform}] {nickname}: {content}`，
其中 `platform` 是 `douyin` / `bilibili` / `simulator` 之一（**不是**界面上的中文名），
`nickname` 为空时该位置直接是空字符串。导出**只写 `_history` 里的内容**——
也就是所有收到过的弹幕，不受「只看触发按键的」筛选影响。

内部有两级缓冲：显示区最多 `max(50, 最多显示行数)` 行，历史区最多 5000 条
（超出时丢掉最旧的 1000 条）。刷新是**批量**的——每 100 毫秒一次、单次最多写 200 行，
所以弹幕刷屏时界面不会被逐条重绘拖死。

### 登录对话框

「获取凭证…」打开，标题「获取登录凭证 - 幕键」，两个标签页：

- **B站扫码登录** —— 点「生成二维码」，用手机 B站 App 扫码确认；成功后 `SESSDATA` 自动填入。
  另有「停止轮询」按钮。没装 `segno` 时会显示占位图并提示
  `⚠ 未安装 segno，二维码显示为占位图。安装命令：pip install segno`。
- **抖音 Cookie** —— 因为抖音不支持扫码（见「抖音登录」），这里给的是 5 步手工引导 +
  一个粘贴框 + 「校验」按钮（至少要有 `ttwid`）。

### 筛选规则编辑器

标题「编辑筛选规则 - 幕键」。左边是**有序规则表**（列 `启用 / 规则名 / 动作`，
**自上而下优先**）+ 操作按钮 `新增` / `删除` / `上移` / `下移`；右边是选中规则的详情：

- **规则名：**
- **命中后：** —— 四个动作的中文选项（`放行（可触发按键）` / `丢弃（不显示、不触发）` /
  `只显示（不触发按键）` / `改写内容（再按改写后的匹配）`）
- **条件之间：** —— `全部满足（与）` / `任一满足（或）`。**新建规则时默认是「与」，注意手动改**
- 条件表（列 `字段 / 判断 / 值 / 区分大小写 / 取反`）+ `加条件` / `删条件`

### 映射编辑器

标题「编辑映射 - 幕键」，默认 `860×600`，两个标签页
`键盘映射（N 条）` / `鼠标映射（N 条）`。列与按钮见「按键映射」。
底部提示：**触发词更长的优先；长度相同时精确匹配优先于包含匹配**。

**填按键不用背键名**：键盘映射的「目标」列是一个**可搜索下拉框**。

- 下拉里列出全部按键，并带中文说明：`字母 A`、`数字 1`、`方向键 ↑`、`空格`、
  `回车（Enter）`、`F1 功能键`、`小键盘 1`、`左 Ctrl` …
- 直接打字就会筛选：输 `a` 出字母 A、Alt 系列；输 `方向` 只剩四个方向键；
  输 `空格` 出空格；输 `f1` 出 F1；输 `ctrl` 出左/右 Ctrl。匹配**包含**关系，
  不区分大小写——所以 `page` 能筛出 `pagedown` 和 `page_down`。
  多词写法（`page down`）保存时也认，但**候选弹窗按字面匹配**，
  想看候选请敲 `page` / `pagedown` / `page_down`。
- 列表里的按键可以用方向键 / 鼠标直接选；**也可以照旧手填**，
  并且手填的内容会被同步进筛选框（边打边筛）。
- 手填接受键名、别名与列表里显示的中文说明（`回车`、`方向键 ↑` 都认），
  存盘时统一成规范键名（`enter`、`up`），所以 `settings.json` 里永远是键名。
- 键名不区分大小写；空格键仍然是那个**单个空格**（也可以写 `space`）。

**长按按多久**：把「动作」选成**长按**之后，右边的「长按(秒)」列才会出现，决定按住多久
（`0.05`–`5.00` 秒，默认 `0.50`，见「[长按(秒)](#长按秒长按到底按多久)」）。

### 鼠标映射（9 条）

同样是每条一个触发词：

| # | 触发词 | 鼠标键 | 动作 | 感应 |
| --- | --- | --- | --- | --- |
| 1 | `左键` | `left` | 单击 | 开 |
| 2 | `左` | `left` | 单击 | 开 |
| 3 | `右键` | `right` | 单击 | 开 |
| 4 | `右` | `right` | 单击 | 开 |
| 5 | `中键` | `middle` | 单击 | **关** |
| 6 | `上滚` | `middle` | 向上滚动 | **关** |
| 7 | `滚轮上` | `middle` | 向上滚动 | **关** |
| 8 | `下滚` | `middle` | 向下滚动 | **关** |
| 9 | `滚轮下` | `middle` | 向下滚动 | **关** |

> 两者触发词都是 `左` 且都是精确匹配，于是由**表内顺序**决定（键盘表排在鼠标表前面）。
> 不想要这个歧义就把其中一条禁用掉。

| 1 | 进入直播间不触发按键 | 只显示（不触发按键） | 无额外条件；消息类型 ∈ `ENTER` / `FOLLOW` / `LIKE` / `STATS` |

映射的「按键」列是个**可搜索下拉框**：下拉里是内置键码表的全部 114 个键名
（带中文说明），边打字边筛，也能直接手填。下面按类列出，填这些名字（大小写不敏感）都能识别：

| 类别 | 可用名字 |
| --- | --- |
| 字母 | `a` - `z` |
| 主键盘数字 | `0` - `9` |
| 功能键 | `f1` - `f12` |
| 小键盘数字 | `numpad0` - `numpad9` |
| 小键盘运算 | `add`、`subtract`、`multiply`、`divide`、`decimal` |
| 修饰键 | `ctrl`、`lctrl`、`rctrl`、`shift`、`lshift`、`rshift`、`alt`、`lalt`、`ralt`、`win`、`lwin`、`rwin` |

> 按键名不在表里时，编辑器会当场弹「未知按键」并告诉你可用示例，
> 而不是默默存下一个永远不会生效的映射。
>
> 下拉里显示的中文说明也可以直接用来筛选或填写（`方向键 ↑`、`回车`、`小键盘 1`、
> `字母 A`），存盘时统一换成上表的规范键名。所以 `settings.json` 里永远是
> `enter` / `up` 这种键名，不会出现中文。

### 发送后端与扩展键

四种后端（`input/keycodes.py` 的 `SEND_METHODS`）：

| 后端 | 说明 |
| --- | --- |
| `sendinput` | `SendInput`（推荐，通用）——普通模式默认 |
| `directx` | 扫描码 + 虚拟键码——游戏模式默认 |
| `scancode` | 纯扫描码（`keybd_event`） |
| `keybd_event` | 兼容旧程序 |

其中有 **17 个键属于「扩展键」**，发送时必须带上 `KEYEVENTF_EXTENDEDKEY` 标志，
否则 Windows 会把它解释成**另一个键**：
`up`、`down`、`left`、`right`、`insert`、`delete`、`home`、`end`、`pageup`、`pagedown`、
`numpad_enter`、`divide`、`rctrl`、`ralt`、`win`、`lwin`、`rwin`。

> 这张表曾经漏了 `lwin` 和 `divide`——两张手工维护的表漂移了，`is_extended_key()`
> 返回 `False`，于是这两个键会以「非扩展」形式发出，被系统识别成别的键。
> 现在 `EXTENDED_KEYS` 是从同一张扫描码表派生出来的，不可能再漂移。

## 命令行参数

```
screenkey [-h] [--version] [--debug] [--log-dir DIR] [--config-dir DIR]
           [--selftest] [--check-env] [--simulate]
           [--platform {douyin,bilibili}] [--room ROOM] [--no-hotkey]
```

| 参数 | 说明 |
| --- | --- |
| `-h`, `--help` | 显示帮助 |
| `--version` | 打印 `幕键 2.1.0` 并退出 |
| `--debug` | 日志级别降到 DEBUG |
| `--log-dir DIR` | 指定日志目录（等价于环境变量 `SCREENKEY_LOG_DIR`） |
| `--config-dir DIR` | 指定配置目录（等价于环境变量 `SCREENKEY_CONFIG_DIR`） |
| `--selftest` | 只跑离线自检，不开界面、不联网 |
| `--check-env` | 检查**本机注入环境**（权限/沙箱/前台窗口/配置目录），排查"按键发不出去" |
| `--simulate` | 启动后自动勾选模拟模式并直接连接 |
| `--platform {douyin,bilibili}` | 启动后自动选中平台 |
| `--room ROOM` | 启动后自动填入房间号 |
| `--no-hotkey` | 不注册全局热键 |

`--platform` / `--room` / `--simulate` 都只是**预填界面**，仍然需要界面正常启动。

`--selftest` 与 `--check-env` 分工不同，别混：

| | 检查什么 | 会不会失败 |
| --- | --- | --- |
| `--selftest` | **代码链路**对不对（导入、映射、匹配、筛选、协议解析、引擎端到端） | 会在代码坏了时 `[FAIL]`（退出码 3） |
| `--check-env` | **本机当前环境**能不能把按键送到目标窗口 | 只报告，永远退出 0 |

按键"发出去了但记事本/游戏收不到"时，先跑 `--check-env`。实测输出形如：

```
幕键 2.1.0 注入环境检查
  进程 PID        : 14012
  Win32 注入 API  : 可用
  管理员权限      : 否（普通权限）
  注入环境        : 有问题
      读不到本进程的令牌信息，通常说明它跑在受限环境里（沙箱、受限用户、被安全软件降权）。……
  受限宿主标记    : DSH_SESSION_ID（DSH 会话宿主）、DSH_SHELL（DSH 宿主 shell）
      说明：本程序是由这个宿主启动的。宿主可能限制输入注入；真实判据看下面的「注入回环」。
  注入回环        : **无效**
      SendInput 报告成功（错误码 0）、光标却停在 (1944, 40) 没动：**注入被静默丢弃**。……
  当前前台窗口    : Naraka　[NarakaBladepoint.exe]（pid 24360）
      目标窗口      : 权限不高于本程序，按键可以送达
  默认配置目录    : C:\Users\you\.screenkey
  实际使用目录    : E:\...\幕键\.screenkey
      说明：默认目录不可写，已自动改用上面这个。设置会存在那里，不会丢，但不是你预期的位置。
      写入测试      : 通过
```

其中**「注入回环」是唯一的确证判据**：它真的注入一个必然可见的变化
（把光标移动 1 像素随即复位、再按一下 F24），然后去读回来。
`SendInput` 报告成功、光标却没动 = Windows 把你的输入静默丢弃了。
「受限宿主标记」只是提示（命中不代表一定失败），令牌完整性级别也不够用
——实测里令牌读不到、级别也正常，注入照样被丢弃。

`启动.bat` 也会在被这类宿主启动时先打一段 `[警告]`，说明按键会被静默丢弃、
该改用哪种方式启动；`--selftest` / `--check-env` 两个分支不会被这段警告的
`pause` 挡住（它们本来就是给自动化用的）。

### 退出码

| 退出码 | 含义 |
| --- | --- |
| `0` | 正常 |
| `1` | 参数错误（`EXIT_ARGS`） |
| `2` | 缺少依赖（`EXIT_ENV`，实际触发场景是缺少 PyQt5） |
| `3` | 自检失败（`EXIT_SELFTEST`） |

`1` 和 `2` 是刻意分开的：调用方（包括 `启动.bat`）只看退出码就能区分
「命令敲错了，重敲」和「环境没装好，去装依赖」。

> **实现说明**：`argparse` 默认用 `2` 表示参数错误，正好会和 `EXIT_ENV = 2`
> 撞车。所以 `main.py` 里的 `_ArgumentParser` 自己接管了 `error()`，
> 把参数错误的退出码改成 `EXIT_ARGS`(1)。
> 实测：`.venv\Scripts\python.exe src\screenkey\main.py --definitely-not-a-flag` → 退出码 **1**；
> `--selftest` → 退出码 **0**。`tests/test_cli.py` 里有回归测试锁住这一点。

## 配置说明

### 位置

| 内容 | 默认路径 | 覆盖方式 |
| --- | --- | --- |
| 配置 | `%USERPROFILE%\.screenkey\settings.json` | 环境变量 `SCREENKEY_CONFIG_DIR`，或 `--config-dir` |
| 日志 | `%USERPROFILE%\.screenkey\logs\` | 环境变量 `SCREENKEY_LOG_DIR`，或 `--log-dir` |
| 抖音 sign.js | 包内 `screenkey/data/sign.js` | 环境变量 `SCREENKEY_SIGN_JS` |
| node 可执行文件 | `PATH` 里的 `node` | 环境变量 `SCREENKEY_NODE` |

放在用户目录而不是程序目录，是为了打包成 exe 后（安装目录只读）依然能写配置和日志。

### settings.json 结构

全部持久化状态都在**一个**文件里，**原子写**（先写临时文件再 `os.replace`）。
写到一半崩溃不会留下半个 JSON。读到损坏的 JSON 会自动备份成 `settings.json.bad` 并回落默认值——**绝不阻止启动**。

```jsonc
{
  "version": 2,
  "config": {
    "connection": {
      "platform": "bilibili",        // bilibili | douyin
      "room": "",
      "cookie": "",
      "sessdata": "",
      "douyin_mode": "websocket",    // websocket | browser
      "auto_reconnect": true,
      "reconnect_delay": 3.0,
      "max_reconnect_attempts": 5,
      "connection_timeout": 15.0,
      "heartbeat_interval": 10.0
    },
    "display": {
      "max_lines": 1000,
      "show_timestamp": true,
      "show_nickname": true,
      "show_platform": true,
      "font_size": 16,
      "auto_scroll": true,
      "only_triggered": false,       // 只看触发了按键的弹幕
      "opacity": 0.95                // 夹在 0.2 - 1.0
    },
    "input": {
      "enabled": true,
      "game_mode": false,            // 扫描码模式
      "toggle_hotkey": "ctrl+shift+p",
      "max_actions_per_message": 1,
      "global_cooldown": 0.0,
      "per_user_cooldown": 0.0,
      "dedupe_window": 0.0
    },
    "window": { "x": 100, "y": 100, "width": 1180, "height": 780 }
  },
  "key_mappings":   [ /* 25 条默认 */ ],
  "mouse_mappings": [ /*  9 条默认 */ ]
}
```

手改这个文件是安全的：未知字段会被忽略、缺失字段用默认值、单个子配置解析失败只影响它自己。
`key_mappings` / `mouse_mappings` 写成空数组时会被当成「用户清空了」，不会偷偷回落到默认表。

#### 诊断代码在打包产物里也是活的（实测）

「源码里有诊断」不等于「exe 里也有」：`dist\` 下没有 `.py` 文件，Python 模块
全被收进 PyInstaller 的 **PYZ 归档**（zlib 压缩），所以在 `dist\` 里按字节搜
源码字符串（`风控拦截`、`_diagnose_ws_failure`）**永远是 0 命中**，那种搜法
既不能证明有、也不能证明没有。正确做法是用 PyInstaller 自己的 reader 把模块
取回来执行（脚本 `verify_exe_pyz_bili_diag.py` + `verify_exe_bili_diag_e2e.py`）：

```python
from PyInstaller.archive.readers import CArchiveReader, ZlibArchiveReader
car = CArchiveReader(r"dist\幕键\ScreenKey.exe")
car.extract("PYZ.pyz")                      # 5888905 字节，708 个模块
zar = ZlibArchiveReader("_exe_pyz.pyz")     # 注意：只吃文件名，不吃 bytes
code = zar.extract("screenkey.danmaku.bilibili")
```

把取回的 code object `exec` 进一个模块、对**真实被风控的房间**跑完整
`connect()`，实测 `PASS=6 FAIL=0`：

```
connect() 返回： False
statuses = [(False, 'B 站接口返回 -352（风控拦截）：当前网络出口的 IP 被限制，'
                    '换房间号没有用，请换网络（家宽 / 手机热点）后重试')]
```

这同时证明了两件事：诊断代码确实被打进了 exe，且它在冻结环境里**真的跑到了
`-352` 那条分支**（而不是静默落到兜底文案）。

> **别直接调 `_diagnose_ws_failure()`**：它用的是 `self._session`，而
> `self._session` 要 `connect()` 才会创建。单独调它会因 `self._session is None`
> 立刻走兜底分支，看起来像「诊断没生效」，实际是探针用错了入口。
> 这也顺带解释了为什么诊断函数必须写成「任何异常都吞掉」——它要能容忍自己
> 被调用时环境不完整。

> **收不到弹幕不等于没连上**：绝大多数直播间极其安静，几分钟没人说话是常态。
> 想快速验证，去一个人气高的直播间，或者用 `--simulate` 验证后半段链路（筛选→匹配→按键）。

## 性能与资源占用

这里只写**实测过**的数字，不写「理论上应该很快」这类话。

### 空闲时

| 指标 | 实测 |
| --- | --- |
| 界面内存 | PyQt5 + 单窗口，通常几十 MB 量级 |
| CPU | 空闲时接近 0；心跳每 10 秒一次，几乎不可见 |
| 线程 | 主线程（Qt）+ 1 个抓取线程 + 抖音场景下 1 个 Node 子进程 |

### 弹幕刷屏时

限流是为了保护**你自己的电脑和游戏**，不是保护程序——程序本身扛得住。
「选项」里的四个限流项默认值是 `max_actions_per_message=1`、`global_cooldown=0.0`、
`per_user_cooldown=0.0`、`dedupe_window=0.0`，
也就是**默认只在「单条弹幕最多触发一个映射」上设了限**（见「按键映射 → 限流设置」）。

如果弹幕量很大（比如上万人气房），建议：

1. 把「全局动作间隔（秒）」调到 `0.05` - `0.2`；
2. 把「同一用户冷却（秒）」调到 `1` - `3`；
3. 把「相同内容去重窗口（秒）」调到 `1` - `3`。

三层都是「超限就**静默丢弃**该次动作」，不会阻塞抓取，也不会让界面卡住。

### 界面不会被弹幕拖死

弹幕窗口做了两级缓冲 + 批量刷新：

- 每 **100 毫秒**刷新一次，单次最多写 **200 行**；
- 显示区最多 `max(50, 最多显示行数)` 行，历史区最多 5000 条（超出丢弃最旧的 1000 条）；
- 主界面的「日志」页最多 3000 行。

所以即使每秒几百条弹幕，界面也只是「看起来在快速滚动」，不会逐条重绘到卡死。

### 按键延迟

按键在**后台线程**执行，`SendInput` 是线程无关的 Win32 调用，所以界面卡顿不影响按键。
每条映射的 `delay` 是**在锁外** `time.sleep(min(delay, 5.0))`，不会阻塞其它映射的冷却判断。

> 单条映射的 `delay` 上限是 **5 秒**（代码里硬夹的）。写 `delay: 60` 也只会等 5 秒——
> 这是防止配置写错导致动作队列堆积。

## 配置迁移

### 从旧版（参考项目）迁移映射

如果你之前用过 `抖音加B站幕键`，它的映射存在 `userdata\配置文件.json`。
本程序**不会自动去读那个文件**，但提供了导入入口：

```bat
:: 注意：要先进到 src 目录，让 Python 找得到 screenkey 包
cd /d <项目目录>\src
..\.venv\Scripts\python.exe -c "from screenkey.config.manager import ConfigManager; m = ConfigManager(); print(m.import_legacy(r'<旧项目目录>'))"
```

例如，把参考项目的映射导进来（实测输出 `(12, 0)`）：

```bat
cd /d E:\DSHwork\幕键\src
..\.venv\Scripts\python.exe -c "from screenkey.config.manager import ConfigManager; m = ConfigManager(); print(m.import_legacy(r'E:\DSHwork\抖音加B站幕键'))"
```

`import_legacy(legacy_dir, overwrite=False)` 返回 `(导入的键盘条数, 导入的鼠标条数)`。

> **为什么必须 `cd src`（或者先设 `PYTHONPATH`）？**
> `src\screenkey\main.py` 会自己把 `src` 插进 `sys.path`，所以 `启动.bat` 和
> `main.py` 都不需要任何环境变量。但上面这条 `python -c` 跑的是**你自己的代码**，
> 那段自举逻辑不在里面，Python 只会在当前目录找 `screenkey`。
> 在项目根目录直接跑会得到 `ModuleNotFoundError: No module named 'screenkey'`。
> 不想 `cd` 就先 `set PYTHONPATH=<项目目录>\src`。

三种旧格式都认（这也是**已修复**的：早先只认后两种，于是对参考项目的真实文件永远导入 0 条）：

| 旧文件形状 | 说明 |
| --- | --- |
| `[{...}, {...}]` | **裸 list**，参考项目 `userdata\配置文件.json` 的真实格式 |
| `{"keyboard": [...], "mouse": [...]}` | 键鼠分开的 dict |
| `{"mappings": [...], "mouse_mappings": [...]}` | 另一套键名；`key_mappings` 也认 |

查找顺序（`config/manager.py` 的 `_find_legacy_file`）：`<目录>\配置文件.json` →
`<目录>\userdata\配置文件.json` → `<目录>\src\配置文件.json`，
也兼容 `mappings.json` 这个名字。

- 默认 `overwrite=False`：**只在当前映射为空时才导入**，绝不覆盖你已有的配置。
- 想强制覆盖就传 `overwrite=True`。
- 旧格式的未知字段会被忽略、缺失字段用默认值，所以格式对不上也不会炸；
  损坏的 JSON 会被备份成 `配置文件.json.bad`，导入返回 `(0, 0)` 而不是抛异常。
- list 里混进无法解析的条目只会被跳过，不影响同一文件里其它条目。

### settings.json 的版本字段

顶层 `version` 目前是 `2`（`AppConfig.SCHEMA_VERSION = 2`）。
字段是**只增不减**的宽容解析：未知键忽略、缺失键用默认值、单个子配置坏掉只影响它自己。
所以从更早的版本升级时，不需要手工改文件——直接启动即可，程序会补上缺失的字段。

### 彻底重来

删掉 `%USERPROFILE%\.screenkey\settings.json` 就会回到全默认。
或者用 `--config-dir` 指一个临时目录，做到「多套配置互不干扰」。

## 已知限制

以下都是实打实的限制，不是「理论上可能」的问题。

1. **抖音需要本机安装 Node.js**。`signature` 参数必须由抖音自己的混淆 JS 现场计算，纯 Python 复现不了。
   没有 Node、或没有 `sign.js` 时，`signature_available()` 返回 `False`，抖音连接**会失败并明确报错**，
   程序**不会**假装连上。（缺 signature 的具体症状：连接建立后约 **155ms** 被服务端以 **1006** 断开，一帧都收不到。）
2. **抖音房间没人发言就收不到弹幕**，而这很正常——绝大多数直播间极其安静。
   程序会持续保持连接、定期发心跳，但不会凭空产生数据。别把「没弹幕」当成「连不上」。
3. **抖音未登录时，昵称/UID 可能被平台替换或缺失**。真实抓包里曾观察到完整昵称（如 `我也不是至尊宝`），
   也观察到过 UID 为 0 的情况，具体表现随房间和风控策略而变，程序只能原样透传、无法补全。
   带上 Cookie 登录通常能提高拿到完整昵称的概率，但并非所有房间都有效。
4. **B站 `-352` 已纠正归因（2026-10-23）**：以前把 `getDanmuInfo` 恒返回的 `-352`
   判成"按出口 IP 判定的接口级风控"，实测**推翻**了它——真因是请求**缺 WBI 签名**
   （`w_rid`/`wts`）。同一台机器、同一条网络，补上签名后立刻 `code=0` 并拿到 `host_list`。
   本项目已自实现签名（`danmaku/bilibili_wbi.py`），并把 blivedm 的
   `_init_room_id_and_owner`（改用 `room_init?id=<房间号>`，`?room_id=` 会得到 `60004` 或 `-352`）
   与 `_init_host_server`（改用签名 `getDanmuInfo`）替换掉。
   **实测**：房间 `34348`，抓取器与引擎级各 30 秒各收到 **41 条**事件，引擎触发 9 次动作。
   2026-10-24 又在房间 `21414905` 复验 45 秒：`status=True` 上报、收到 `enter`（`INTERACT_WORD_V2`）
   与在线人数 STATS（`在线 71~77 人`、`看过 1.3万`），证明 V2 分支与 STATS 分支在真实链路上生效。
   诊断层 `_diagnose_ws_failure` 仍保留：签名后**仍**报 `-352` 才是真的风控，
   那时才需要换网络出口（文案已改为"请求已带 WBI 签名仍被拒"）。
   取证原文与当年误判过程见[如何验证真的连上了](#如何验证真的连上了)第 5 节。
5. **抖音不支持扫码登录**。平台接口有反爬，纯 HTTP 客户端拿不到 `ttwid`，
   只能由用户从浏览器手工复制 Cookie。原因见 [连接弹幕 → 抖音登录](#抖音登录)。
6. **仅支持 Windows**。按键注入用了 Win32 API（`SendInput` / `keybd_event` / 扫描码），游戏模式更是直接依赖扫描码。
7. **反作弊游戏收不到按键**。扫描码能骗过 DirectInput，骗不过内核级反作弊。在那类游戏里用宏有封号风险。
8. **抖音字段号会随平台改版漂移**。本项目用手写解析 + 多候选字段号来抗改版，但大幅改版仍可能导致某类消息解析不出来。
9. **`sign.js` 的版权不属于本项目**，仅供研究学习，不得商用分发。
10. **`browser` 模式（playwright）未纳入依赖**。配置里有 `douyin_mode: browser` 这个值，但默认走 `websocket`；
    想用 browser 模式需要自己装 playwright 并跑 `playwright install chromium`。
11. **打包产物体积较大**（实测 `build.bat --clean` 后整个 `dist\幕键\` 目录 **222 个文件 / 102.4 MB**，
     其中 exe 本身只有 **6.29 MB**，剩下全是 Qt 运行时与 Python 解释器）。
     界面基于 PyQt5，onefile/onedir 都要把整个 Qt 运行时打进去，
     这是 PyQt5 应用的固有代价，不是本项目的额外负担。所以产物必须是**整个 `dist\幕键\` 目录**一起分发，
     单独拷 exe 无法运行（缺 `_internal\`）。
12. **界面槽函数抛未捕获异常会让进程直接消失**（PyQt5 的固有行为，退出码 `0xC0000409`），
    而且日志里不会留下任何错误。本项目已在槽函数内部做了防御，但如果你自己改界面代码，
    请务必不要在槽里放任异常逃逸。详见「常见问题 → 程序突然消失」。
13. **旧配置导入没有界面入口**，只能用上面「配置迁移」里的命令行跑一次。
    程序启动时**不会**自动扫描旧项目目录（刻意的：避免悄悄改动用户既有配置）。
14. **「匹配方式」不能在「映射」标签页的总表里改**。总表是只读的，要改得进
    「编辑映射…」对话框，那里每行都有独立的「匹配方式」下拉框。
    （这一列是**后补**的：早先界面里根本没有它，用户只能手改 `settings.json`。）
15. **项目根目录下残留的 `_probe*` / `pytest-cache-files-*` 空目录在本机删不掉**。
    它们是历史遗留物（`.gitignore` 已覆盖，不影响运行、不影响打包），
    理论上属于工作区文件权限问题：这些目录的安全描述符**连 `Get-Acl` 都读不到**
    （`UnauthorizedAccessException`），而同一批命令里普通目录是能正常删除的。
    这与项目代码无关，是创建它们的进程留下的权限；需要管理员权限或在「完全权限」下才能清掉。
    本节提到的 `tmp_path` 覆盖（见「开发与测试」）就是为了让测试不再依赖这类目录可写。
16. **焦点窗口过滤依赖 Windows 的窗口枚举**，有两类场景会不准：
    一是目标程序**以管理员权限运行**、而本程序没有，某些情况下读到的前台窗口信息不完整
    （解决办法：两个程序用同一权限级别运行）；
    二是 UWP/商店应用（例如部分微软系应用）的顶层窗口进程名可能显示为
    `ApplicationFrameHost.exe`，这时改用「窗口标题」匹配。
    另外全屏独占（exclusive fullscreen）游戏切出切入时窗口类名可能变化，
    不确定时用「进程名」+「精确」最稳。
    过滤器**默认关闭**，不启用时行为与旧版完全一致。
17. **在受限环境里运行时，按键会被 Windows 静默丢弃，程序检测不到**。
    程序跑在沙箱 / 受限令牌 / 被安全软件降权的宿主里时，`SendInput` 依然
    **返回成功**（`GetLastError() == 0`），但目标窗口什么都收不到——日志里
    每条弹幕都显示"已发出"，记事本和游戏却毫无反应。**这不是本项目能修的
    问题，是 Windows 的权限隔离**：必须在正常桌面环境里直接双击 `启动.bat`
    或 exe 运行。

    ⚠️ **注意一个真实踩过的坑**：从自动化/沙箱宿主（例如带 `DSH_SESSION_ID`
    环境变量的终端窗口）里敲 `启动.bat`，受限的是**宿主进程**——"我明明是
    双击/运行 `启动.bat` 的"并不能排除它。`--check-env` 的
    **「受限宿主标记」**一行会直接点名是哪个宿主，**「注入回环」**一行给出
    确证结论（`SendInput` 报告成功、光标却没动 = 已被静默丢弃）。

    为了不再让用户白猜，2.1.0 起做了四件事：程序启动时自检并**在日志/状态栏
    明说**环境有问题（`engine._warn_injection_environment`）；`启动.bat`
    在被受限宿主启动时先打一段 `[警告]`（自动化分支不会被它的 `pause` 挡住）；
    提供 `--check-env` 把判据一次打印出来（含**注入回环实测**与**受限宿主标记**，
    见[命令行参数](#命令行参数)）；以及入口注入环境自检。
    同类问题还有**目标程序比本程序权限高**（游戏是「以管理员身份运行」而本
    程序不是）：判据是完整性级别，同样静默失败，解决办法是两边权限一致。
    实测中还有一层：**令牌完整性级别本身不足以判据**——受限宿主里
    读不到令牌、级别看起来也正常，注入照样被丢弃；所以唯一可信的判据是回环。

## 常见问题

**Q：点了「开始接收弹幕」之后一直没反应，是没连上吗？**
（按钮就是主控条最左边那个；勾了模拟模式后它的文案会变成「开始模拟弹幕」。）
先看日志。`app.log` 里会有连接过程；`danmaku.log` 有内容才是真收到弹幕。
如果直播间本来就很安静，几分钟没弹幕是完全正常的。想确认链路，用「模拟模式」。

**Q：抖音报错说找不到 Node / 计算 signature 失败。**
装 Node.js（<https://nodejs.org/>）并确认 `node --version` 能用。装在非常规路径时设 `SCREENKEY_NODE`。
日志里会写明具体是 `LOAD_FAILED`、`NO_GET_SIGN` 还是根本找不到 node。

**Q：抖音连上 0.2 秒就断了。**
典型的缺 `signature`。确认 Node 可用、`sign.js` 存在（打包版在 `_internal\screenkey\data\sign.js`），
或设 `SCREENKEY_SIGN_JS` 指向你自己的副本。

**Q：按键在游戏里没反应。**
先分清是哪一种"没反应"——这两类的排查方向完全相反：

1. **日志里根本没有 `[按键]` 行** → 弹幕没触发映射（筛选规则拦了、映射关了、
   或者弹幕内容没匹配上）。看「日志」标签页与「筛选规则」。
2. **日志里有 `[按键] … → …` 行，但记事本/游戏收不到** → 输入被系统丢弃了，
   与映射、筛选都无关。跑一次注入环境检查：

   ```bat
   .venv\Scripts\python.exe src\screenkey\main.py --check-env
   ```

   如果它提示"注入环境/目标窗口有问题"，就按提示做：**直接在正常桌面里双击
   `启动.bat` 运行**（别在沙箱/受限宿主里跑），并让游戏与本程序**同一权限级别**
   （都普通启动，或都「以管理员身份运行」）。详见[已知限制](#已知限制)第 17 条。
   程序启动时也会自检一次，有问题会在日志里打 `[警告]`、状态栏显示 `⚠`。

   > **判断"是不是真的被丢弃了"只看一项：「注入回环」。**
   > 它真的把光标移动 1 像素（随即复位）再读回来。`SendInput` 报告成功、
   > 光标却没动，就是被静默丢弃 —— 这种情况程序日志里**一个字都不会错**，
   > 因为 Windows 按设计就不把这件事告诉调用方。
   > 如果你是从某个自动化/沙箱宿主（比如带 `DSH_SESSION_ID` 环境的终端）
   > 启动的 `启动.bat`，那么"双击了 启动.bat"也救不了：受限的是**宿主**，
   > 不是你双击的动作。请在资源管理器里直接双击，或直接双击 exe。

按键确实需要游戏模式（扫描码）时再开「游戏模式」；若开了仍无反应，且上面第 2 类
的检查全过，才轮到"游戏有内核级反作弊"这一条——本程序无能为力。

**Q：弹幕刷屏时电脑像卡死。**
去「选项」调限流：把「单条弹幕最多触发：」设为 1，加上「全局动作间隔（秒）：」、「同一用户冷却（秒）：」、「相同内容去重窗口（秒）：」。
也可以直接按 `Ctrl+Shift+P` 暂停按键输出。

**Q：配置改坏了，程序起不来？**
不会起不来。损坏的 JSON 会被备份成 `settings.json.bad` 并回落默认值。
想彻底重来，删掉 `%USERPROFILE%\.screenkey\settings.json` 即可。

**Q：双击 `启动.bat`，窗口一闪而过 / 什么都没发生。**
先改用 `启动.bat --console`，它会停在控制台上让你看到真正的报错。
历史上有一个已修复的版本会在这里报：

```text
ModuleNotFoundError: No module named 'screenkey'
```

原因是入口自己算错了 `sys.path` 该插哪一层（插了包目录而不是它的父目录 `src`），
而 `启动.bat` 的默认与 `--console` 分支都不设 `PYTHONPATH`，于是必然失败——
只有 `--selftest` 分支因为自己设了 `PYTHONPATH` 而看起来正常。
现在 `main.py` 会自己把 `src` 加进 `sys.path`，从任何工作目录都能启动；
`tests/test_cli.py::TestBootstrapWithoutPythonPath` 会刻意清空 `PYTHONPATH` 来守住这条路径，
`TestLauncherBat` 则直接跑 `启动.bat --selftest` 并断言批处理里不再出现 `PYTHONPATH`。
若你仍在旧版本上遇到，请更新源码，或临时用 `set PYTHONPATH=<项目根>\src` 兜一下。

**Q：`启动.bat` 里的中文是乱码。**
这个文件是 **GBK（cp936）+ CRLF** 编码的，这是 `cmd.exe` 在中文区域下的要求。
如果你的编辑器把它存成了 UTF-8，中文就会变乱码——改回 GBK 或干脆不要动它。

**Q：`python -m pip` 报「No module named pip」。**
这个 `.venv` 是用 `--without-pip` 建的。执行 `.venv\Scripts\python.exe -m ensurepip --upgrade`，
或者用普通方式重建虚拟环境。

**Q：B站提示「缺少 blivedm 依赖」，但我明明装了。**
这是打包/依赖环境问题，不是你的错。PyPI 上的 `blivedm` 0.1.x 是**扁平单文件包**——
只有 `client` / `handlers` / `models` 三个模块，**没有** `blivedm.clients` 或 `blivedm.models.web` 这类子包。
如果代码（或 PyInstaller 的 `hiddenimports`）里写了那些不存在的子模块，
`ModuleNotFoundError` 会把同一个 `try` 里的 `import blivedm` 一起带走，
于是探测结果变成「没装」。本项目的两处都已完成隔离，正常不会出现；
若你自行改过 `main.spec`，请确认 `hiddenimports` 里写的是 `blivedm.client` / `blivedm.handlers` / `blivedm.models`。

**Q：B站报 `Can not decode content-encoding: br`。**
aiohttp 发现环境里能 import `brotli` 就会自动协商 `br` 压缩，而 `blivedm` 依赖锁定的
`brotli==1.0.9` 其 `Decompressor` 只有单参 `process(data)`，与 aiohttp 3.14.4 的
`decompress_sync(data, max_length)` 双参调用不兼容，于是**每个**响应都解码失败。
本项目已显式声明 `Accept-Encoding: gzip, deflate` 绕开，正常不会出现。
如果你自己新建 `aiohttp.ClientSession`，请照抄这个头。

**Q：B站界面显示「已连接」但其实一帧弹幕都没有。**
不会了。blivedm 的 `start()` 只是把后台协程排进事件循环，
`init_room()` → `ws_connect` → 认证都还没发生；本项目会一直等到 WebSocket 真正握手
（`_on_ws_connect` 回调置位）才上报成功，超时（15 秒）就如实报失败并返回 `False`。
若你看到失败，程序会**主动再问一次接口并把原因翻成人话**：

- 报 `B 站接口返回 -352（风控拦截）：请求已带 WBI 签名仍被拒，换房间号没有用，请换网络出口（家宽 / 手机热点）后重试`
  → 签名已带仍被拒才是真风控，**换房间号、换 Cookie 都没用，只能换网络出口**（见[已知限制](#已知限制)第 4 条）；
- 报 `B 站接口返回 -400（请求错误）` 之类 → 接口本身回了别的错，按括号里的说明处理；
- 报 `B 站弹幕服务器连接未就绪（接口正常，可能是本地网络屏蔽了 2243/443 端口）`
  → 接口是好的，是 WebSocket 连不上，检查防火墙 / 代理。

**Q：B站为什么一直报 -352？**

先确认用的是不是带 WBI 签名的版本。**2026-10-23 实测推翻了"按 IP 判定的接口级风控"这个旧结论**：
`-352` 的主因是 `getDanmuInfo` **缺 WBI 签名**——补上 `w_rid`/`wts` 后同一台机器立刻 `code=0`，
并在房间 `34348` 30 秒收到 41 条弹幕。另一个坑是 `room_init` 必须用 `?id=<房间号>`。

签名补齐后**仍**报 `-352`，才轮到真风控：换网络出口（家宽 / 手机热点）重试，
或换机器跑 `.test_tmp/verify_bilibili_connect.py <房间号>` 复验。

**Q：怎么彻底关掉全局热键？**
启动时加 `--no-hotkey`，或者把「选项」里的热键设成一个你不会碰到的组合。

**Q：程序突然消失，日志里什么都没有。**
这是 PyQt5 的固有行为：**槽函数里逃逸的异常不会回到 Python，而是走 Qt 的
`qFatal` 路径直接终止进程**（实测退出码 `0xC0000409`，`emit()` 根本不返回，
所以界面层的 `try/except` 拦不住）。本项目已在所有槽函数内部做了防御，
正常情况下不该出现。若你改过界面代码后出现这种情况，请检查新增的槽函数——
用子进程跑一次就能确认（进程内断言没有意义，进程已经死了）。

**Q：勾了「游戏模式」但按键还是没反应。**
先确认版本：早期实现里 `set_game_mode()` 判断的是 `self.send_method`，
而它在构造时就已被填成非空默认值，**那个条件永远为假**，勾选等于没勾。
现在的实现用独立的 `_explicit_send_method` 标志记录「用户是否显式指定过后端」，
切换模式会真的换后端。日志里能看到实际使用的发送方式。

**Q：热键里多打了一个重复的键（比如 `ctrl+ctrl+q`）会怎样？**
会被自动合并成 `ctrl+q`，正常触发。早期实现用生成器推导、不去重，
于是这类热键的规范串与运行时按下的键集合对不上，**永远不可能触发且不报错**。

**Q：在「编辑映射…」里点一下「上移」/「下移」，映射就少了一条。**
这是**已修复**的严重缺陷。旧实现是「先 `removeRow` 再 `insertRow` 再回填」，
而 `insertRow` 建出的新行所有单元格都是空的（`cellWidget` 返回 `None`），
回填函数又在 `insertRow` **之后**去读控件，于是一个字段都没写回去——
点一次「上移」就毁掉一条映射，还在表里留个空行，接着点保存必然被
「第 N 行的触发词不能为空」拦下。
现在改成**数据驱动换序**：先把整表读成 mapping 列表 → 交换两项 → 重新 `load()`，
不碰控件，自然不会有空行。`tests/test_mapping_editor.py` 守住它。

**Q：打开「编辑映射…」什么都没改就点保存，感应/长按全没了。**
这是**已修复**的严重缺陷，且比上一条更隐蔽。旧实现构造新 mapping 时只填了表格里
那几列，其余字段（`delay`、`enable_sensing`、`short_press_count`、`long_press_count`、
`case_sensitive`、`use_scancode`、`move_x`、`move_y`、
`scroll_amount`）**静默回落到 dataclass 默认值**。
实测默认表里 **21/25 条键盘映射与 4/9 条鼠标映射**受影响，全部是
`enable_sensing: True → False`——也就是说，用户只是打开对话框再点保存，
就把「`666666` → 长按 6」这个主打功能整体清掉了，而且没有任何提示。
现在编辑器为每一行保留原始对象（`self._originals`），保存时用
`dataclasses.replace(original, ...)` 只覆盖表格里真有控件的那几列，其余原样保留。

**Q：导入旧版映射显示成功，但一条都没进来。**
这是**已修复**的缺陷。参考项目的 `userdata\配置文件.json` 是一个**裸 list**
（`[{...}, {...}]`，实测 12 条），而旧实现写的是
`if not isinstance(data, Mapping): return (0, 0)` —— 裸 list 直接被拒，
于是"导入"对参考项目的真实文件**永远返回 `(0, 0)`**。
现在三种形状都认（裸 list / `{"keyboard","mouse"}` / `{"mappings","mouse_mappings"}`）。
用上面「配置迁移」里的命令可以自己验一下，正常应输出 `(12, 0)`。

**Q：一个映射想配多个触发词，怎么填？**
在「触发词」列写 `w,上,前`（中英文逗号都认），就表示弹幕等于 `w`、`上`、`前`
任一都触发。这曾经是坏的：旧实现把整串当作一个字面量，
用户照界面提示写完之后发 `w`/`上`/`前` 一个都不触发，
只有弹幕原文恰好是 `w,上,前`（连逗号一起）才触发。现在数据层与匹配层都已改对。

**Q：「编辑映射…」里怎么找不到「长按(秒)」那一列？**
它不是常驻列——**表里只要还没有任何一行的「动作」选「长按」，整列就收起来**；
把任意一行的动作改成「长按」，这一列立刻出现在「动作」右边；再改回去又收起。
这是按用户反馈做的（"前面选了长按后面再出来"）：常驻一列会让人以为别的动作也用它。
行级还分两层：非长按的行看不到那一格，但**值仍然保留**，
来回切动作不会把已经调好的时长清掉。

**Q：总表「动作」列写成「长按 1.25s」，那 `settings.json` 里是什么？**
界面显示的是中文名，文件里存的永远是枚举值，两者对照如下（`action` 字段）：

| 界面显示 | `settings.json` 里的 `action` |
| --- | --- |
| 按下（不松开） | `press` |
| 松开 | `release` |
| 按下并松开（点按） | `press_and_release` |
| 长按 1.25s | `long_press`（时长在 `long_press_duration`，单位秒） |
| 单击 / 双击 | `click` / `double_click` |
| 移动 | `move`（配合 `move_x` / `move_y`，可为负数） |
| 向上滚动 / 向下滚动 | `scroll_up` / `scroll_down`（配合 `scroll_amount`） |

**Q：按键下拉框里敲 `page down`（带空格）一个候选都不出。**
候选弹窗是 Qt 按**字面包含**匹配的，`page down` 这个字符串匹配不到 `pagedown`。
想看候选就敲 `page`、`pagedown` 或 `page_down`；而**保存时 `page down` 是认的**
（校验会先折叠空白再比对，存成 `pagedown`）。同一条规则也适用于中文说明里带空格的写法，
比如 `左 Shift`、`方向键 ↑` 直接输入都能被认出来。

**Q：为什么总表「输出」列显示 `up` / `lshift`，下拉框里却是「方向键 ↑」/「左 Shift」？**
总表是**只读核对**用的，故意显示规范键名（和 `settings.json` 里的写法一致，方便排查）；
编辑对话框里的下拉框面向填写，才显示中文说明。两边指向同一个键，只是呈现不同。

### 一、B站弹幕以前 100% 连不上（最严重）

三个缺陷叠在一起，任何一个都足以让 B站这条路走不通：

| 位置 | 缺陷 | 后果 |
| --- | --- | --- |
| `danmaku/bilibili.py` 的 `_WsReadyHandler` | 注册成 `blivedm` 的 handler 后，指望 `blivedm` 回调自己的 `_on_ws_connect()`。但 `blivedm` 0.1.1 的 `client.py` 调的是 **`BLiveClient` 自己的**方法，**从不遍历 handlers** | `_ws_ready` 永远为 `False`，每次连接都白等满 `connect_timeout`（15s）后失败 |
| 同一个 handler | **缺 `handle()`**。`blivedm` 的 `client.py` 对每个 handler 调 `handler.handle(client, command)` | `AttributeError` 在 `asyncio.gather` 的参数求值阶段抛出，被宽 `except` 吞掉 → **所有弹幕静默丢弃** |
| `danmaku/bilibili.py` 的 `connect()` | 末尾 `await self._join_task` | `connect()` 永不返回，违反基类契约（基类是 `run_until_complete(connect(...))` 之后进空闲循环）；基类线程再也退不出去 |

另外 `stop_and_close()` 抛的 `CancelledError` 在 Python 3.8+ 继承 `BaseException`，
`except Exception` 捕不到，会从 `_thread_main` 的 `finally` 逃出去 —— `loop.close()` 与 `_running = False` 都不执行，
于是 `_running` 永远是 `True`，用户必须先点一次「停止」才能重连。

修法：`_WsReadyHandler` 改成真正的 `async def handle(...)`（在 `handle` 里置就绪位）；
`connect()` 不再 `await join`，改成给 join 任务挂 `add_done_callback`，
连接真断了就上报错误并让基类线程退出；`_wait_ws_ready()` 同时接受「WebSocket 已建立」作为就绪信号
（覆盖空房间"连上了但没消息"）；`stop_and_close()` / `stop()` 改成 `except (asyncio.CancelledError, Exception)`；
`ClientSession` 补 `ClientTimeout(total=None, sock_connect=10)`（**不能设 `total`**，否则长连接 ws 会被掐断）。

> 顺带把两条**死代码**就活了：`blivedm` 0.1.1 把 `INTERACT_WORD` 放进了 `IGNORED_CMDS`、
> `LIKE` 根本不在它的回调表里，所以子类里那两个 `_on_interact_word` / `_on_like` 永远不会被调用。
> 现在自己覆写 `handle()` 解析命令名再分派（含 `LIKE_INFO*`），进入直播间 / 点赞事件真的能进来了。

> **2026-10-24 补的第三个协议分支**：B站把进场事件升级成了 `INTERACT_WORD_V2`（载荷是
> base64 的 protobuf，放在 `data.pb`），而 blivedm 0.1.1 只认识旧的 JSON 版 `INTERACT_WORD`，
> 于是进场/关注又整批丢了（日志里只剩 `unknown cmd=INTERACT_WORD_V2`）。
> 现在用项目自带的 `danmaku/protobuf_lite.py` 手解 V2 载荷（字段号按真实抓包取证：
> `1=uid 2=uname 5=msg_type 6=room_id 7/8=时间戳`），同时补了 `ONLINE_RANK_COUNT`
> （当前在线人数）与 `WATCHED_CHANGE`（累计观看，如 `看过 1.3万`）两个 STATS 分支；
> 同值统计 15~60 秒内去重，避免 5 秒一推把弹幕列表刷屏。
> 离线测试见 `tests/test_bilibili.py::TestInteractWordV2AndStats`（fixture 在 `tests/fixtures/bilibili_frames.json`，
> 按真实抓包结构重新编码、已匿名化）。

### 二、抖音：连接状态与心跳

- `connect()` 在**重连次数耗尽后仍然 `return True`** → 基类以为连上了，`_running` 永为 `True`，
  下一次「开始接收弹幕」直接返回失败，用户必须先点停止。现在 `_run_connection_loop()` 返回 `bool`，
  只有真连上过才返回 `True`。
- `connect()` 里无条件 `self._stopping = False`，会**覆盖用户刚发出的 `stop()`**。已改为 `if self._stopping: return False`。
- 心跳原来挂在 `asyncio.wait_for(ws.recv(), timeout=heartbeat_interval)` 的 `TimeoutError` 分支上：
  **房间一忙，`recv` 永不超时，心跳就永远不发**（这正是"约 21 秒后被服务端以 1006 断开"的直接原因之一）。
  现在心跳按 `time.monotonic()` 独立判断（`_heartbeat_due()`），`recv` 只负责收包。
- `decode_payload()` 的 gzip 解压**没有输出上限**（帧上限 8MB），解压炸弹可以抛 `MemoryError`
  —— 而它不在 `except (OSError, EOFError, zlib.error)` 里。现在用 `zlib.decompressobj` + 32MB 上限，
  且解压失败计入 `MAX_PARSE_ERRORS`，不会出现"连接看着正常、其实一条都解不出来"。
- `_ack()` 原来**先清 `_pending_ack` 再发送**，发送失败只 `logger.debug` —— ack 丢了服务端就断你。
  现在发送成功才清，失败 `warning` 并在下一帧重试。
- 签名组件过去拿的是**它自己那份陈旧参数**：全项目**从未把当次参数传进去**，
  所以实际是在空参数上算签名。现在 `get_sign(params)` 每次都显式传入当次参数
  （签名用的就是这同一份 `params`，不存在"组件里那份"）。
  同时 `_last_signature_error` 以前**只写不读**，签名算不出来的原因永远看不到，现在连接时会上报一次。
- `auto_reconnect` / `reconnect_delay` / `max_reconnect_attempts` / `connection_timeout` / `heartbeat_interval`
  这**五项配置全项目没有任何读取点**（重连次数写死 5、退避写死 `2*attempt`、HTTP 超时写死 15s、心跳写死 10s）
  —— 也就是说改 `settings.json` 完全没用。现在由 `base.apply_connection_config()` 白名单接收、各 getter 真实生效。

### 三、筛选规则以前根本存不下来

`FilterEngine` 有完整的 `to_list()` / `from_list()`，`config/manager.py` 的 `save()` 却**只写 4 个键**
（`version/config/key_mappings/mouse_mappings`），`load()` 也从不读筛选规则；
`ui/main_window.py` 建引擎时还硬编码 `filters=FilterEngine.default()`。
结果就是：用户在界面里精心调的筛选规则，**关掉程序就没了**——
界面上的提示原文甚至写着"本次运行有效；如需永久保存请写入配置文件"。

现在 `save()` 会写 `filters`、`load()` 会读（空列表被尊重为"用户主动清空"，坏数据回落 2 条默认规则）、
`MainWindow` 从 `manager.filters` 构造引擎、`_edit_filters` 与 `_persist` 都会落盘。

### 四、手改 `settings.json` 会让整个弹幕处理崩掉

`InputConfig.from_dict` / `ConnectionConfig.from_dict` 原来是 `cls(**kwargs)`，**零类型强转**：

| 手写值 | 原来的行为 |
| --- | --- |
| `"enabled": "false"` | 字符串非空 → 判为 **True**（"关掉输入"反而变成开着） |
| `"global_cooldown": "1.5"` | `engine.py` 里 `if cfg.global_cooldown > 0:` → **`TypeError: '>' not supported between instances of 'str' and 'int'`**，每条弹幕都中断 |

现在统一走 `_as_bool` / `_as_int` / `_as_float` / `_as_str`，并夹取范围
（`font_size∈[6,72]`、`opacity∈[0.2,1.0]`、`max_actions_per_message∈[0,10]`、冷却 `>=0`、`max_lines>=1`）；
`toggle_hotkey` 是纯空白时回落默认值（否则全局热键永远注册不上）。
`WindowGeometry` 也补上了 `x`/`y` 夹取 —— 原来只夹宽高、注释却声称"防跑屏"，
窗口完全可以被存到屏幕外；`MainWindow._restore_geometry` 现在还会按 `QScreen.availableGeometry` 把窗口夹回可见区。

### 五、退出时会留下**物理按下的键**

这是最容易被忽略、后果最直观的一条。`closeEvent` 里 `engine.stop()` 之后**立刻 `_persist()` 退出**：

- `base.py` 的 `stop()` 是**非阻塞**的（只置 `_stopping = True`），从不 `join()` 抓取线程；
- 抓取线程此刻可能正卡在 `engine.py` 的 `time.sleep(mapping.delay)` 或 `keyboard.execute()` 里，
  紧接着执行 `press()` —— 进程没了，**那颗键在操作系统层面还是按下状态**；
- `KeyboardController` / `MouseController` 的 `_stopping` 标志**全项目只写不读**，
  `_send` / `press` / `execute` 从不检查它；`keyboard.stop()` / `mouse.stop()` **全项目零调用**。

现在：`closeEvent` 会 `join()` 抓取线程（带超时）再 `release_all()`；`_send()` / `press()` / `execute()`
在 `_stopping` 时直接返回 `False`。另外「停止」后立刻点「连接」原来必然失败（`_running` 要等线程退出才复位），
`engine.start()` 现在会在这种情况下先 `join` 一小段再重试一次。

### 六、界面层的线程安全问题

- **全局热键回调在 `pynput` 的监听线程里直接调用 `pause_input.toggle()`** → `toggled` → `_on_pause_input`
  → `self.log()` → `appendPlainText()`，**在非 GUI 线程里改两个控件**。
  轻则 `QObject: Cannot create children for a parent that is in a different thread`，重则随机崩溃。
  现在改成一个 `pyqtSignal` 转发到 GUI 线程再 toggle。
- `_flush()` 里 `if self._paused or not self._pending: return` —— 暂停期间 `_pending` **没有上限**
  （只有 `_history` 有 5000 上限），存的还是**已渲染好的 HTML 字符串**，内存单向增长。现在 `deque(maxlen=...)`。
- 弹幕窗口的 `only_triggered` / `auto_scroll` 两个勾选框**没有连任何写回信号**，
  而 `apply_config()` 又反向 `setChecked(bool(config.xxx))` —— 改一下字号，勾选状态就被静默回滚。
- 登录对话框：重复点「生成二维码」不先停掉旧轮询对象；倒计时用的 1 秒定时器**无条件覆盖**状态文本，
  于是"登录成功！"、"二维码已失效"最多只显示 1 秒。
- 选项页的改动**不落盘**，要等关窗口时才写；`_sim_sequence` 在 GUI 线程里同步跑完整串模拟弹幕（含 `time.sleep`），界面直接卡住；
  `_refresh_stats` 在 GUI 线程**无锁**读引擎统计（引擎早就有加锁的 `stats_snapshot()`）；
  `manager.save()` 的返回值被丢弃，**保存失败也照样提示"已保存"**。

### 七、编辑器会丢数据（这条最伤用户）

- `ui/filter_editor.py` 原来 `self._rules = list(engine.rules)` —— **只复制了列表，元素还是引擎里的活对象**。
  于是"改了一半点取消"，配置已经被改了。现在逐字段深拷贝（含条件列表）。
- 切换行 / 增删条件 / 上下移动之前**不收集当前行的输入**，直接重建表格 → 正在编辑的内容丢失。
  现在所有结构性操作前都先 `_flush_current_row()`；
  两个下拉框的 `currentIndexChanged` 还原本会把自己的 `int` 索引当成"目标行号"传进 `_save_detail()`。
- `ui/mapping_editor.py` 的 `.strip()` 把 `" "`（空格键）变成 `""` —— **空格键映射永远保存不了**，
  还会误报"没有选择按键"；按键下拉里有空白项；非法行复制**静默跳过**（现在会列出第几行有问题）。

### 八、抖音 Cookie 粘贴、B站扫码登录

- 界面的引导**正在教用户从 DevTools 复制**，而解析器恰好咽不下那两种格式：
  `ttwid\t1%7Cabc`（表格两列被当成分隔符）→ `{'ttwid': ''}`；`Cookie: ttwid=xxx` 整行 → `{}`。
  现在逐行处理，支持 `name=value;` 连写 / DevTools 表格 / `Cookie:` 请求头整行三种格式，
  并把识别结果回显给用户（"识别为 DevTools 表格"），`DouyinLoginInfo.source` 也不再恒为空。
- B站扫码轮询：`poll_once()` 把任何一次网络抖动都判成 `ERROR`，而轮询线程**遇到 `ERROR` 就永久退出**
  —— 用户扫完码点确认时，程序早就放弃了。现在容忍连续 5 次失败才终止，并且终止时把原因写清楚。
  `stop_polling()` 原来 `join(2s)` 之后**无条件 `self._thread = None`**（而单次 HTTP 超时是 15s），
  线程泄漏 + 下次 `start_polling` 与旧线程抢着改状态；`generate()` 也不先停旧线程。

### 九、模拟模式与平台工厂

- 模拟弹幕发完以后只 `break`，**不置 `_running = False`、不通知状态** → 基类线程空转，界面永远显示"已连接"。
- `emit_once()` / `emit_sequence()` 直接调 `self._notify(...)`，**绕过基类 `_emit_message()` 的 `_stopping` 检查**。
- `create_fetcher()` 对**未知平台名静默回落到 `SimulatorFetcher`** —— 平台名拼错就变成"模拟模式"，
  看起来一切正常却什么都没连；而且工厂把 `cookie` / `mode` / `signature` / `proxy` 等参数全吞了，
  抖音默认必然连不上。现在未知平台抛 `UnknownPlatformError`，参数真实透传。

### 十、Node 签名桥与 protobuf 解析

- `signature.py` 的 `_spawn()` 里 `proc.stdout.readline()` **裸阻塞、没有超时**：
  驱动脚本在写 `READY` 之前会先预热一次 `ctx.get_sign(...)`，而 `vm.runInContext(..., {timeout: 30000})`
  **不覆盖**这个调用 —— `sign.js` 一卡，事件循环就占死，`stop()` 永远无效，线程永久挂住。
  现在用带超时的 `_readline_with_timeout()`。
- `stderr=subprocess.PIPE` 启动成功后**从不读取** → node 写满 64KB 管道就阻塞；现在重定向到临时文件。
- `_disabled` 熔断之后**没有任何复位路径**（`close()` 也不清），用户装好 Node 必须重启程序；
  `get_sign()` 失败分支只把 `_proc` 置 `None`、**不 kill 旧进程**，最多漏 3 个 node 子进程。都已修。
- `protobuf_lite.read_varint()` 的边界判断写在 `shift += 7` **之后**：`shift == 63` 那次仍会移位，
  能返回 **70 位整数**；字段号越界后经 `_pick_int()` 流进 `build_ack()`，编出**非法 varint**。
- `get_int()` 对任意 `bytes` 做 `int.from_bytes(value, "little")`：字段一旦漂移成字符串或嵌套消息，
  就返回一个垃圾大整数；而抖音的 `_pick_int()` 是"**第一个非 0 值即胜出**"，
  于是后面真正正确的候选字段永远试不到。现在只接受 `int`。

### 十一、收尾

- `--selftest` 原来把配置写进 `get_log_dir().parent / "selftest"` 而且**永不清理**，
  在项目根目录跑一次就留下一个 `selftest\settings.json`（现在用一次性临时目录，跑完即删）。
- `logging_setup.setup_logging(force=True)` 只 `removeHandler` 旧 root handler、**不 `close()`**（句柄泄漏）。
- `input/hotkey.py` 有 **4 处 `undefined name 'Any'`**（`from __future__ import annotations` 把注解变成了字符串，
  运行时侥幸没炸）；另有 **48 处未用导入 / 未用变量**，现在 `pyflakes` 全项目 0 告警。
- 项目根下那批空目录（`_probe*`、`pytest-cache-files-*`）是历史遗留物，
  `.gitignore` 已经覆盖；**它们在本机删不掉**是 Windows 文件权限问题（连 `Get-Acl` 都拒绝访问），
  与代码无关，详见「已知限制」。

### 十二、按键"发出去了"却谁都没收到（一次真实故障的复盘）

用户报告：**更新后记事本和游戏都收不到按键了。** 这一条不是猜的，是照着日志和探针查出来的，
过程本身值得记下来——因为它推翻了我最初的判断。

**现象**：`src\screenkey_logs\app.log` 里 21:25:11–21:25:48 之间有 44 条弹幕
全部走完了整条链路，每条都是成对的：

```
screenkey.engine    | 弹幕「w」(测试用户) → w 点按
screenkey.ui.main_window | [按键] 测试用户: w → 向上
```

**关键取证**：`engine.py` 的日志格式是 `"… → %s" + ("" if ok else " [发送失败]")`，
日志里**没有** `[发送失败]` 标记，说明 `KeyboardController.execute()` 一路返回 `True`
——也就是 `SendInput` 报告成功。所以"代码没把按键发出去"这个方向可以直接排除。

于是写了一个探针（`inject_probe.py`，用后即删）实测：

| 探针做的事 | 结果 |
| --- | --- |
| `SendInput` 注入一个按键 | 返回 **True**（报告成功） |
| 之后读 `GetLastError()` | **0**（没有任何错误） |
| 记事本标题是否变化 | **没变** —— 按键没送到 |
| `SetForegroundWindow` 聚焦记事本 | **失败** |
| `mkdir C:\Users\<用户>\.screenkey` | **`[WinError 5] 拒绝访问`** |
| `OpenProcessToken` 读自身令牌 | **失败** |

后两项是关键：**这个进程跑在受限环境里**（沙箱 / 受限令牌）。受限令牌下 Windows 会
**静默丢弃**注入的输入——`SendInput` 照样返回成功、`GetLastError()` 照样是 0，
目标窗口却什么都收不到。这就是"日志说有、记事本说没有"的全部原因。
也解释了另一条线索：同一份日志里反复出现
`无法创建配置目录 C:\Users\<用户>\.screenkey: [WinError 5] 拒绝访问`。

**所以这不是本次改动引入的回归**，而是环境问题——但它暴露出两个**真实缺陷**：

| 缺陷 | 以前 | 现在 |
| --- | --- | --- |
| 环境不对时**完全无声** | 按键被系统丢弃，程序检测不到也不报告，用户只能怀疑程序坏了 | 启动时自检（`engine._warn_injection_environment`），受限令牌 / 完整性级别偏低 / 目标窗口权限更高 都会在日志打 `[警告]`、状态栏显示 `⚠`，并新增 `--check-env` 一次性打印全部判据 |
| 配置目录不可写时**设置全丢** | `~/.screenkey` 建不出来就每次 `save()` 报一次错，用户改的设置永远存不下来 | `writable_config_dir()` 依次回落到**程序旁边的 `.screenkey`**、再回落临时目录，并明确写出"已改用哪个目录"；同一目标只提醒一次 |

设计上的两个要点：

- **警告走单独的事件类型**（`EngineEvent.kind = "warning"` → `EngineBridge.warningOccurred`），
  不计入 `stats.errors`——环境问题不是程序出错，混进错误统计会让"错误数"失去意义。
- **自检失败绝不阻断启动**：`injection_environment_problem()` 抛异常也被吞掉（只写 debug 日志）。
  它只是"多说一句"，不是前置条件。

**给用户的结论**：在正常桌面里直接双击 `启动.bat` 运行即可，按键会正常工作；
如果游戏是「以管理员身份运行」的，本程序也要用同一权限级别启动。

#### 十二之二、用户回了一句"我是双击 启动.bat 的"——于是又查了一遍

上一轮的结论里有个隐含假设：**"在正常桌面双击 `启动.bat`"就等于没在受限环境里**。
用户回了一句"我是使用 `E:\DSHwork\幕键\启动.bat` 启动的"，这个假设就站不住了，
必须重新取证。这一步不能靠推理，靠的是三条硬证据：

1. **`C:\Users\hgcrts\.screenkey` 从来就没被创建过。** 该目录的 ACL 是
   `DESKTOP-BIAMGHP\hgcrts:(OI)(CI)(F)`（属主完全控制）——正常进程一定写得进去。
   它不存在，说明**每一次**启动都继承了一个被限制的宿主。
2. **`src\screenkey_logs\app.log` 跨了 10 天（10-10 → 10-19）**，从第一次运行起
   每次都在报 `无法创建配置目录 …: [WinError 5] 拒绝访问`。也就是说"受限"不是偶发，
   而是这台机器上启动该程序的**常态**；用户 10-11 那次 B 站连接还留下了
   `blivedm | room=… _init_room_id_and_owner() failed, message=-352`（风控）的记录。
3. **回环实测**：在一个小探针里让程序给自己注入输入，再读回来。
   键盘版读 `GetAsyncKeyState(VK_F24)`（F24 没有任何程序会绑定，误触发风险为零），
   鼠标版读 `GetCursorPos`——鼠标版是决定性的，因为 `GetCursorPos` 没有
   "桌面不活动就返回 0"的歧义：

   ```
   SendInput 相对移动(60,40) -> 返回 1, GetLastError=0
   光标: 之前 (1275, 1322) → 之后 (1275, 1322) 变化=False
   ```

   `SendInput` 报告成功、错误码 0、光标**一像素都没动** ⇒ 输入被静默丢弃。

第 3 条同时纠正了上一轮的一个不完整结论：**令牌完整性级别不足以当判据**。
受限宿主里 `OpenProcessToken` 读不到令牌，看似"级别正常"，注入照样无效；
所以现在唯一可信的判据是**回环实测**——注入一个必然可见的变化，再去读它。

**由这一轮补上的三处**：

| 位置 | 内容 |
| --- | --- |
| `input/keycodes.py` | `injection_loopback()` 真做一次回环（鼠标 1 像素 + F24），`interpret_injection_loopback()` 是**纯函数**负责把原始结果翻译成结论（三种：SendInput 直接失败 / 注入有效 / 静默丢弃）——抽成纯函数才好在离线测试里逐条覆盖 |
| `input/keycodes.py` | `restricted_host_markers()` 识别 `DSH_SESSION_ID` / `DSH_SHELL` / `SANDBOXIE` / `SNAPCHAT_IN_SANDBOX`，**定位是提示**（命中不代表一定失败），真正的判据仍是回环 |
| `启动.bat` | 新增第 0 段警示：被受限宿主启动时先打 `[警告]` 并给出该怎么做；**`--selftest` / `--check-env` 分支不会 `pause`**——这两个分支是给自动化用的，一句裸 `pause` 就会让它们在管道里永远等一个不会到来的按键 |

教训（与上一轮那条互补）：上一轮是"代码里没有失败 ≠ 用户那里成功了"，
这一轮是"**用户说的启动方式 ≠ 实际的宿主环境**"。判定"能不能注入"只能靠
**注入一次再读回来**，任何间接指标（令牌、权限、启动方式）都可能给出假阴性。

### 十三、写"项目现状"时又抓到两个缺陷（一个致命、一个是我自己造的）

这两条都不是"审计出来的"，而是**给项目写状态文档、逐条复核既有结论时撞出来的**。
放在这里是因为它们各自代表一类错误。

#### 13.1 日志文件打不开，会把整个程序打死（致命）

**症状**：`python main.py --selftest` → **退出码 1、屏幕上一个字都没有**；
双击 `启动.bat` 则是"什么都没发生"——没有窗口、没有报错、没有日志。
这一轮的全量测试也因此变成 `9 failed, 900 passed`（9 条 CLI/自检类用例全挂在子进程非 0 退出上）。

**根因**（`utils/logging_setup.py`）：原实现只检查"日志目录建出来了没有"：

```python
candidate.mkdir(parents=True, exist_ok=True)   # 目录已存在 → 直接成功，什么都没验证
```

而"目录存在"和"能往里写文件"是两件事。在受限环境里前者成功、后者被拒，
于是 `RotatingFileHandler(...)` 抛 `PermissionError: [Errno 13] ... app.log`，
这个异常从 `setup_logging()` 一路冒到 `main()` ——**程序还没到创建窗口就死了**。
更讽刺的是同文件的 docstring 早就写着"绝不因为日志目录失败而让程序起不来"。

**为什么之前没暴露**：今天早些时候 `~/.screenkey/logs` 还不存在，
`mkdir` 当场被拒 → 走了"临时目录"这条回落路 → 恰好能写；
用户自己跑了一次（那次是非受限的）把目录**建出来了**，于是 `mkdir` 开始成功，
崩溃条件才成立。这解释了"昨天还好好的，今天突然打不开"。

**修法**（三处，都在 `logging_setup.py`）：

| 位置 | 以前 | 现在 |
| --- | --- | --- |
| `get_log_dir()` | 只看 `mkdir` 成不成功 | 新增 `_probe_writable()`：**真写一个 `.write_test` 再删掉**，写不进去就不算可写 |
| 回落顺序 | 环境变量 → `~/.screenkey/logs` → 临时目录 | 环境变量 → `~/.screenkey/logs` → **程序旁 `.screenkey/logs`**（便携）→ 临时目录；每次回落都往 stderr 说明原因 |
| handler 构造 | 直接 `RotatingFileHandler(...)`（异常上抛） | `_try_make_file_handler()` 失败返回 `None`，只降级成"本次不写文件日志"，**绝不连累程序启动**；`danmaku.log` 的 raw handler 同样处理 |

**守住它的测试**：`tests/test_ui_worker_logging.py` 新增
`test_probe_writable_detects_write_denied`、`test_skips_candidate_that_is_not_writable`、
`test_falls_back_when_every_candidate_is_unwritable`、
`test_explicit_override_falls_back_without_probing_others`，
以及 `TestSetupLoggingFailures` 的两条（日志文件不可写时 `setup_logging()` 必须正常返回）。

#### 13.2 完整性探测从来没成功过，于是"正常用户"也会被冤枉

第十二节把"注入环境诊断"做出来时，判据之一是令牌完整性级别，当时的结论是
"受限进程读不到自己的令牌"。**这个观测本身是假的**：

```python
# 旧写法：ctypes.windll.kernel32 没有声明 restype
OpenProcessToken(GetCurrentProcess(), TOKEN_QUERY, byref(h))   # → 永远失败
```

`ctypes.windll` 的默认 `restype` 是 `c_int`，而 `GetCurrentProcess()` 返回的是伪句柄
`(HANDLE)-1`，被截成 32 位后不再是合法句柄 → `OpenProcessToken` **在任何环境都失败**。
于是"读不到令牌"被解释成"你在受限环境里"——一个**普通桌面用户也会收到的假警告**。

证据不是推理：用户 23:23 那次运行是**非受限**的（它成功地把日志写进了
`C:\Users\hgcrts\.screenkey\logs\app.log`），可它的日志里照样有
`[警告] 读不到本进程的令牌信息…`。也就是说这条警告当时**谁都躲不过**。

修完（显式声明 `argtypes`/`restype`，并用 `ctypes.WinDLL(..., use_last_error=True)`）
本机实测：

```
current_integrity_level()      → 4096（0x1000，中/普通用户）
process_integrity_level(自身)  → 4096
injection_environment_problem() → ''（不再是报警理由）
```

同一轮还调整了判据的分工，避免第二类误报：

- **读不到令牌不再等于受限**——`injection_environment_problem()` 此时返回空串；
  真正的权威判据是**回环实测**（第十二节那条），而它只在 `--check-env` 里跑。
- 受限宿主改由**宿主标记**识别（`DSH_SESSION_ID` / `DSH_SHELL` / `Sandboxie` / …），
  命中时启动自检给出警告并把"改从资源管理器双击"写清楚——因为这是程序**唯一能确定**
  的信息（谁把我拉起来的），而不是猜自己的权限。

教训：**在把某个观测当成证据之前，先验证观测工具本身**。
这次是两个最容易被当成"环境问题"的现象（文件写不进去、句柄打不开）里，
各藏着一个自己的 bug；它们的共同形状是"失败得太彻底、太稳定"——
稳定到不像环境问题，就该回头查工具。

### 十四、映射编辑器的按键列：从"背键名"到"可搜索下拉"

用户的原话是：填本地按键"太原始还是手动填写"，希望**能下拉选全部按键、也能自己填、
填的时候下面的候选跟着筛**。改完的用法见「[映射编辑器](#映射编辑器)」，这里只记三个坑。

| 坑 | 一开始的写法 | 后果 | 现在 |
| --- | --- | --- | --- |
| **显示文字 ≠ 键名** | 下拉项显示 `空格（Space）`，取值也直接取显示文字 | 一选"空格"就存进一个不存在的键名，按不出来 | 项文字用 `key_display()`，键名放在 `itemData`；读取一律经 `current_key()` 还原成规范键名 |
| **`currentIndex` 会骗人** | `current_key()` 直接按 `currentIndex()` 取 `itemData` | 用户选中某项后又把文字改成别的（可编辑下拉的常规操作），取到的还是那一项 | 只有 `currentText() == itemText(index)` 时才信索引，否则按文字解析 |
| **两套校验口径** | 校验用 `resolve_key(name) is not None` | `resolve_key` 对任何单字符都 `ord()` 通过，`左`（U+5DE6 → 24038）就被当成键名接受，运行期才发不出去 | 校验改用 `is_valid_key_name()`（只认 `VK_CODES` 成员 + 单个空格 + 空白不敏感的写法），映射编辑器和控制器共用这一个口径 |

另外两处小设计：搜索是 `input/keycodes.py` 里的**纯函数** `search_key_names()`
（先精确、再前缀、再键名包含、最后中文说明包含；比较前去掉空白，所以
`page down` / `pagedown` / `page_down` 在**搜索口径**里等价），Qt 那层只负责把结果塞进
`QCompleter`；下拉项保留**别名**（`enter` 与 `return`、`esc` 与 `escape` 都在列表里），
但输入 `回车` 这种**标签重复**的词时不猜具体是哪个——保留用户输入原样，由校验兜底。

一个刻意的取舍：`QCompleter` 的候选过滤是 Qt 按字面做的（`MatchContains`），
程序化改文本也不会更新它的补全前缀。要让它对 `page down` 也有候选，只能改写用户输入
或自定义补全器，代价大于收益——所以**弹窗按字面匹配，校验与存盘按空白不敏感**：
敲 `page` 就能看到两个翻页键，而手打的 `page down` 保存时一样认。

校验口径也跟搜索对齐了：搜索不区分空白，那么照着"搜出来的写法"手打的内容也得能存。
`is_valid_key_name()` 因此接受 `page down`（含空格），存盘时统一成 `pagedown`。
而 `resolve_key()` 那套"任何单字符都按字符码当虚拟键码"的宽松行为**只留给发送路径**，
不用来校验映射——否则中文 `左` 会被当成合法键名存进去，运行期永远发不出去。

## 焦点窗口过滤的实现要点

功能用法见「[焦点窗口过滤（只在指定窗口生效）](#焦点窗口过滤只在指定窗口生效)」，
这里只记**为什么这么做**，避免后来人"优化"掉关键的那几行。

**分层**：判定逻辑全在 [`src/screenkey/input/window.py`](../src/screenkey/input/window.py)，
它只依赖标准库（匹配部分是**纯函数**，可离线测试；Win32 探测集中在文件后半段）。
它**不 import** `config` 层——配置对象通过 `FocusFilter.from_config(cfg)` 用 duck typing 取，
装配仍然只发生在 `engine.py` 这个唯一的装配点。这条守着项目"`ui → engine → 其余四层`"的单向依赖。

**每次判定都新建一个 `FocusFilter`**，而不是在 `Engine` 里建好持有：配置对象是界面线程随时会改的，
持快照就必须在每个改动点记得同步，漏一处就变成"界面上关了过滤、实际还在拦"。
构造只是几个属性拷贝，代价可忽略。

**闸门位置在 `_execute_match` 里、去重与冷却之前**：

```
_handle_message → _execute_match
   ├─ ① 焦点判定（不匹配 → 直接 return False）   ← 冷却尚未记账
   ├─ 去重 / 用户冷却 / 全局冷却
   ├─ mapping.delay 睡眠
   ├─ ② 再判一次焦点（睡眠期间用户可能切走了窗口）
   └─ 真正注入 keyboard/mouse.execute
```

- 放在冷却**之前**：否则被拦下的那次会白白吃掉冷却，用户切回游戏后还要再等一个窗口，
  体感就是"切回来了还是没反应"。
- 判**两次**：`delay` 最长 5 秒，必须按"真正注入那一刻谁在前台"算。
- `--selftest` 与单测里 `dry_run=True` 时**整段跳过**：那时本来就不注入，
  再让结果依赖"跑的时候恰好哪个窗口在前台"只会让自检不可复现。

**一律 fail closed**：非法正则、读不到前台窗口、探测抛异常，全部按"不匹配"处理（＝不注入）。
状态文案 `status_text()` 也被包在 try 里——它是**在 GUI 定时器里**被调用的，
异常逃出去就是 PyQt5 的 `qFatal`（无 traceback、退出码 `0xC0000409`），
项目里已经有过一次这种闪退的教训。

**测试**：[`tests/test_window_focus.py`](../tests/test_window_focus.py)，96 项，全离线
（`keyboard.execute` 换成记录器、`get_foreground_window` 换成固定值，不碰真实窗口、不发按键）。
