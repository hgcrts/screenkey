# 幕键 —— 架构说明

本文说明代码的**真实分层与线程模型**，以及抖音弹幕协议的关键三步握手。
所有描述都对应仓库里的实际实现，括号里给出文件与行号。

- 版本：`2.1.0`（`src/screenkey/__init__.py`）
- 入口：`src/screenkey/main.py`
- 平台：仅 Windows（按键注入用 Win32 API）
- 当前整体状态与待办：[项目现状.md](项目现状.md)

## 一、总体分层

```
            ┌──────────────────────────────────────────────┐
            │  ui/        PyQt5 界面（主线程）              │
            │  main_window / mapping_editor / filter_editor │
            │  login_dialog / danmaku_window / theme        │
            └───────────────┬──────────────────────────────┘
                            │  EngineBridge(worker.py)  ← pyqtSignal 跨线程
            ┌───────────────▼──────────────────────────────┐
            │  engine.py  ScreenKeyEngine            │
            │  抓取 → 筛选 → 匹配 → 按键（跑在抓取线程）    │
            └──┬────────┬────────────┬─────────────┬───────┘
               │        │            │             │
   ┌───────────▼──┐ ┌───▼────────┐ ┌─▼──────────┐ ┌▼──────────────┐
   │ danmaku/     │ │ filters/   │ │ input/     │ │ config/       │
   │ 抓取器       │ │ 规则引擎   │ │ 映射与注入 │ │ 配置持久化    │
   └──────────────┘ └────────────┘ └────────────┘ └───────────────┘
               │
   ┌───────────▼──────────────────────────────────┐
   │  login/   扫码登录(B站) / Cookie 引导(抖音)  │
   │  utils/   日志、文本工具                     │
   └──────────────────────────────────────────────┘
```

依赖方向是**单向向下**的：`ui → engine → {danmaku, filters, input, config}`，
`danmaku / input / filters / config` 之间互不反向依赖 `ui`，也不互相 import（`engine` 是唯一的装配点）。
这样做的直接好处是：`engine.py` 可以在完全没有 Qt 的环境里跑（`--selftest` 就是这么做的，
其中的「引擎端到端」一项会真正跑完整链路，而完全不开界面）。

### 各层职责

| 层 | 目录 | 职责 | 关键类型 |
| --- | --- | --- | --- |
| 配置 | `config/` | 单一 `settings.json` 的读写、损坏恢复、旧配置导入 | `AppConfig`（聚合 `ConnectionConfig` / `DisplayConfig` / `InputConfig` / `WindowGeometry`）、`ConfigManager` |
| 抓取 | `danmaku/` | 各平台弹幕源，统一生命周期与回调协议 | `DanmakuFetcher`（基类）、`BilibiliFetcher`、`DouyinFetcher`、`SimulatorFetcher`、`create_fetcher()` 工厂 |
| 协议 | `danmaku/` | 抖音私有协议的解析与签名 | `protobuf_lite`（手写 wire-format）、`signature`（Node 桥）、`message`（`DanmakuMessage` / `MessageType`） |
| 筛选 | `filters/` | 有序规则列表，决定一条弹幕的去留与可动作性 | `FilterEngine`、`FilterRule`、`Condition`、`FilterAction` |
| 输入 | `input/` | 触发词匹配与真实键鼠注入 | `KeyMapping` / `MouseMapping` / `MatchMode`、`matcher.match_content`、`KeyboardController`、`MouseController`、`GlobalHotkey` |
| 登录 | `login/` | B站扫码登录、抖音 Cookie 导入引导 | `bilibili_qr`、`qr_image`、`douyin`（只做引导，不做假扫码） |
| 界面 | `ui/` | 全部 Qt 代码；`qt_env` 负责在导入 Qt 前修好插件路径 | `MainWindow`、`EngineBridge`、`configure_qt_environment()` |
| 工具 | `utils/` | 全局日志（只配置一次）、文本与房间号解析 | `logging_setup`、`helpers` |

### 贯穿全局的约定

1. **`danmaku/base.py` 统一了回调协议**，三个抓取器共享同一套生命周期，不再各自复制样板：

   - 回调异常**绝不向外传播**——一个回调抛异常不能杀掉抓取线程；
   - 回调**在抓取线程里被调用**——界面层必须自己切回主线程；
   - `stop()` 同步且非阻塞——点「断开」要立刻返回，清理在后台完成；
   - `disconnect()` 用 `_disconnecting` 标志防重入（`danmaku/base.py`）。

2. **`utils/logging_setup.py` 是全项目唯一配置 root logger 的地方**，且幂等。
   各模块一律 `get_logger(__name__)`，绝不自己调 `logging.basicConfig()`
   （参考项目里两个模块各调一次，第二次被静默忽略，导致抖音的日志全部丢失）。

3. **`config/manager.py` 只维护一个 `settings.json`，并且是原子写。**
   配置、键鼠映射、筛选规则全部塞进同一个文件（`{"version", "config", "key_mappings",
   "mouse_mappings", "filters"}`），写入走「临时文件 → `flush()` → `os.fsync()` → `os.replace()`」。
   参考项目把它们拆成 4 个 JSON 分别 `open(path, "w")`，写到一半崩溃就留下**截断的半个文件**，
   下次启动直接解析失败；`os.replace` 在同文件系统内是原子的，读者要么看到旧版本、要么看到新版本。
   读坏时把原文件复制成 `settings.json.bad` 再回落默认值——**绝不因为配置坏了就拒绝启动**。
   另外：映射在文件里是**空列表**时视为「用户就是要清空」，不会回落到内置默认映射。

4. **热键名统一排序后再比对。**
   `normalize_hotkey()`（`input/hotkey.py`）把组合键拆开、逐段归一化后 `sorted()` 拼回，
   所以用户写 `shift+ctrl+q` 与配置里存的 `ctrl+q+shift` 会得到同一个规范串，比对永远成立。
   参考项目拿「用户书写顺序」直接和「查表顺序」比字符串，两者只要不一致，热键**永远不触发且不报错**。
   按下状态的比对同样用排序后的串（`input/hotkey.py`、`:229`）。

5. **映射的反序列化用显式枚举表，不用内省。**
   `_KEY_ENUM_FIELDS` / `_MOUSE_ENUM_FIELDS`（`input/mappings.py`）手动列出
   「字段名 → 枚举类」的对应关系，`_mapping_from_dict()` 只查这张表
   （`input/mappings.py`）。
   参考项目从 `dataclasses.field.type` 拿类型，可模块里有 `from __future__ import annotations`，
   `field.type` 拿到的是**字符串** `"MatchMode"` 而不是类型对象，判断静默失败、
   枚举字段永远退回默认值。显式表不受 PEP 563 影响，也顺带把「哪些字段该被转换」写明白了。

6. **只有一份 `DanmakuMessage`，且它是不可变的。**
   参考项目两个平台各定义一份字段完全相同的 `DanmakuMessage`
   （`core/danmaku/bili.py` 与 `core/danmaku/douyin.py`），还要靠注释强调
   「`core.DanmakuMessage` 必须是 B 站版」，于是筛选器、匹配器、界面**到处都要写平台分支**。
   这里统一成一个类，平台差异只体现在 `platform` 字段与 `extra` 字典里
   （`danmaku/message.py`）。
   同时它是 `@dataclass(frozen=True)`：参考项目里这些对象被多处**就地改写**
   （`message.content = ...`），出现过「界面显示的内容与触发匹配的内容对不上」；
   需要变更时一律用 `evolved()` 派生新对象（`danmaku/message.py`），原对象不动。
   `MessageType.coerce()` 对未知值回落 `DANMAKU` 而不抛异常——平台新增消息类型时旧版本不该崩
   （`danmaku/message.py`）。

7. **筛选是「有序规则列表、第一条命中即返回」，不是「一堆平行条件全部叠加」。**
   参考项目的 `DanmakuFilter` 带 6 个平行列表（`keywords` / `prefixes` / `regex_patterns` /
   `blocked_users` / `min_length` / `max_length`），这些条件**只能全部叠加**：
   用户没法表达「包含 A **或** 包含 B」，也没法给不同规则配不同动作
   （比如「只显示不按键」）。
   这里改成有序的 `FilterRule` 列表，每条规则自带条件与动作，按顺序求值、
   第一条给出结论的规则胜出，末尾默认规则兜底（`filters/rules.py`、`:447`）。
   一条规则**内部**的多条件默认是「与」（`FilterRule.match_any=False`），
   可切成「或」（`match_any=True`）——像「长度必须落在 `[min,max]` 内」这种
   一侧太短、另一侧太长的约束，用 `DROP` 动作表达时只能写成「太短 **或** 太长」，
   在「与」语义下两个条件永不可能同时成立，规则会**彻底失效**（长度模板就踩过这个坑）。

8. **B站依赖探测必须与子模块探测解耦，`Accept-Encoding` 必须显式声明，
   「已连接」必须等 WebSocket 真的握手，连不上时必须说清是不是 `-352` 风控。**
   四条都是实测踩出来的，详见 [六、B站四处环境陷阱](#六b站四处环境陷阱)。

## 二、数据流：抓取 → 筛选 → 匹配 → 按键

主干的实现在 `engine.py` 的 `_handle_message()`（`engine.py`），串行四步：

```
DanmakuMessage
      │
      ▼
① FilterEngine.evaluate(message)        filters/rules.py
      │   有序规则列表，第一条命中即返回；
      │   一条都没命中 → 默认放行（actionable=True）
      │
      ├── FilterAction.DROP ──────────► 丢弃，界面也不显示，stats.dropped_messages++
      ├── FilterAction.DISPLAY_ONLY ──► 显示但 actionable=False，不进入下一步
      ├── FilterAction.REWRITE ───────► 用改写后的 content 继续（rewrite_to / strip_prefix）
      └── FilterAction.ALLOW ─────────► 继续
      │
      ▼
② match_content(content, mappings, max_results)   input/matcher.py
      │   mappings = key_mappings + mouse_mappings（合并视图）
      │   max_results 取自 config.input.max_actions_per_message（默认 1）
      │   五种模式：exact / contains / startswith / regex / sensing
      │   感应判定：detect_repeated_char() → repeat_count ≥ long_press_count
      │             则 is_long_press=True（matcher.py）
      │
      ▼
③ 冷却过滤（CooldownTracker）          input/matcher.py
      │   每条映射的 cooldown（默认 0.5s）+
      │   全局 cooldown / 同一用户冷却 / 内容去重窗口
      │
      ▼
④ KeyboardController.execute() / MouseController.execute()
      │   默认 SendInput；游戏模式（use_scancode）走扫描码
      │   程序退出或断开时 release_all() 释放所有按下的键
      │
      ▼
EngineEvent（kind = message / action / status / error / stats）
```

### 事件出口

引擎不直接调用界面，而是把一切包成 `EngineEvent` 通过 `on_event` 回调抛出去
（`engine.py`，字段 `kind / message / actionable / matches / text / extra`）。
`kind` 有五种：`"message"`、`"action"`、`"status"`、`"error"`、`"stats"`。

这种「引擎只发事件、不知道界面存在」的设计，让 `--selftest` 里的
「引擎端到端」检查可以直接替换成 `SimulatorFetcher` + `dry_run=True` 来跑整条链路。

### 关键的顺序语义

- **筛选在匹配之前**：被 `DROP` 的弹幕根本不会进入匹配，也不会出现在界面上。
- **第一条规则命中即生效**：`FilterEngine.evaluate()` 一命中就 `return`，后面的规则不再评估；
  所以规则列表的**顺序就是优先级**。
- **默认放行**：规则列表一条都不命中时返回 `actionable=True`，保持「不加规则就等于不过滤」的直觉。
  默认规则集只有两条：`进入直播间不触发按键`（对 `ENTER`/`FOLLOW`/`LIKE`/`STATS` 执行 `DISPLAY_ONLY`）
  与兜底的 `默认放行`（`filters/rules.py`）。
- **一条规则内多条件的组合方式可切换**：`FilterRule.match_any` 默认 `False`（条件之间是「与」），
  置为 `True` 则「任一满足即命中」（`filters/rules.py`）。这个开关不是可选项而是必需品——
  像「长度必须落在 [min, max] 内」这种约束，用 `DROP` 动作要表达成「太短 **或** 太长 → 丢弃」，
  两个条件在「与」语义下永远不可能同时成立，规则会彻底失效（`length_rule` 历史上就踩过这个坑，
  见 `filters/rules.py` 的 `length_rule` 注释）。界面上的对应控件是「条件之间」下拉框
  （`ui/filter_editor.py`）。

## 三、线程模型

系统里有**两类线程**，边界非常明确。

```
   抓取线程（每个 fetcher 一个）                Qt 主线程
┌────────────────────────────────┐      ┌──────────────────────────────┐
│ asyncio 事件循环               │      │ QApplication.exec_()         │
│  WS 收帧 → 解析 → _emit()      │      │  所有 QWidget 的读写          │
│      ↓                         │      │        ▲                     │
│  engine._handle_message()      │      │        │ 队列连接（自动）     │
│   筛选 → 匹配 → 冷却           │      │        │                     │
│      ↓                         │      │  EngineBridge 的槽函数        │
│  KeyboardController.execute()  │      │        ▲                     │
│   （真的按键，就在这里）        │      │        │ pyqtSignal.emit()   │
│      ↓                         │      │        │                     │
│  on_event ──► EngineBridge._on_event ──► emit(信号) ──────────────────┘
└────────────────────────────────┘      └──────────────────────────────┘
```

### 为什么用 `pyqtSignal` 跨线程

Qt 有一条硬规则：**控件只能在主线程操作**。引擎的回调却跑在抓取线程里
（`danmaku/base.py` 明确约定「回调在抓取线程里被调用」）。

`ui/worker.py` 的 `EngineBridge`（`worker.py`）就是这条边界上的适配器：
它把引擎的 `on_event` 回调转成 `pyqtSignal.emit()`。`emit` 是 Qt 保证线程安全的操作——
跨线程 emit 会走**队列连接**（queued connection），信号被投递到接收者所在线程的事件循环里，
于是槽函数天然在主线程执行，界面代码可以放心操作控件。

`EngineBridge._on_event()` 里**只做 emit，不碰任何控件**，并且整个函数包在
`try/except` 里——绝不让异常回抛进引擎（`worker.py`）。

五条信号（`worker.py`）：

| 信号 | 签名 | 触发时机 |
| --- | --- | --- |
| `messageReceived` | `(object, bool, str)` | 收到一条弹幕（不论是否触发按键） |
| `actionTriggered` | `(object, list)` | 一条弹幕触发了按键，携带命中列表 |
| `statusChanged` | `(bool, str)` | 连接状态变化 |
| `errorOccurred` | `(str)` | 出错 |
| `statsUpdated` | `(object)` | 统计刷新（由定时器驱动，不是每条弹幕都发） |

> 反面教材（本项目刻意避开的写法）：直接在抓取线程里调 `ui.append(...)`，靠「碰巧没崩」运行。
> 弹幕量一上来就会随机出现
> `QObject: Cannot create children for a parent that is in a different thread`。

### 为什么按键也放在抓取线程

`SendInput` / `keybd_event` 是**线程无关**的 Win32 调用，不需要主线程。
把它们放在抓取线程执行是刻意的（`engine.py`）：即使界面因为渲染或阻塞卡住，
按键依然不会被拖慢。代价是按键与界面更新之间没有强同步——这是可接受的取舍，
因为两者本来就服务于不同的目的。

### 线程安全措施

- `DanmakuFetcher` 内部用 `threading.RLock` 保护可变状态，`stop()` 可从任意线程调用。
- `ScreenKeyEngine` 同样用可重入锁保护统计、映射表与配置读写
  （例如 `engine.py` 在锁内取一份映射快照，再在锁外做匹配，避免长时间持锁）。
- **绝不在持锁时调用用户回调**：事件一律在释放锁后 emit。

### `--no-hotkey` 相关的第三个线程

全局热键由 `pynput` 的监听线程驱动（`input/hotkey.py`），
它触发的是界面上的暂停/恢复开关。这是独立于上述两类线程的第三条线程，
之所以需要「全局」，是为了游戏全屏时也能按到。

## 四、抖音协议摘要

抖音这一侧是本项目工程量最大的部分。协议分**三步握手**，之后是长连接上的帧循环。

### 第 0 步：为什么必须自己实现

抖音 Web 端的弹幕**不在页面 HTML 里**，也不是轮询 REST 接口，而是走自己的 IM 推送协议
（`/webcast/im/push/v2/` 的 WebSocket）。`danmaku/douyin.py` 用 `websockets` + 手写的
`protobuf_lite` 实现它，**不是模拟、不是抓页面**。

### 三步握手

```
① 暖场拿 ttwid
   GET https://live.douyin.com/                     （danmaku/douyin.py）
   → 从 Set-Cookie 里取 ttwid 合并进 self.cookie
   已有 ttwid 就跳过这一步，省一次请求（danmaku/douyin.py）

② 拿 roomId
   GET https://live.douyin.com/<web_rid>            （danmaku/douyin.py）
   → extract_room_info(html) 抠出：                  （danmaku/douyin_protocol.py）
        room_id / user_unique_id / cursor / internal_ext
   若返回反爬验证页（含「验证」/ verify / __ac_nonce）则 room_id 拿不到，
   只在日志里 warning，不会假装成功。

③ 建 WS 连接
   wss://<push_server>/webcast/im/push/v2/?<参数表>   （danmaku/douyin.py _build_ws_url）
   参数表逐字段对齐浏览器实际发出的那一份，多传少传都可能被拒。
   其中 signature 由本地 Node 常驻进程算出（见下节）。
```

**为什么要先暖场拿 `ttwid`**：实测直接请求直播间页会被判定为爬虫并返回验证页
（页面里搜不到 `roomId`）；带上 `ttwid` 后同样的请求就能稳定拿到正常页面
（`danmaku/douyin.py`）。

兜底的 WS 主机是 `DEFAULT_WS_HOST = "wss://webcast100-ws-web-lq.douyin.com/webcast/im/push/v2/"`
（`danmaku/douyin.py`）；服务端下发的 `push_server` 优先。

### `signature` 的计算

```
signature = get_sign( md5( 13 个字段的逗号串 ) )
```

- 13 个字段的顺序**是协议的一部分，不能改**，定义在 `danmaku/signature.py`
  （`SIGN_MD5_FIELDS`）：`live_id, aid, version_code, webcast_sdk_version, room_id, sub_room_id,
  sub_channel_id, did_rule, user_unique_id, device_platform, device_type, ac, identity`。
  这四个（`sub_room_id` / `sub_channel_id` / `device_type` / `ac`）即使为空也必须**出现在 URL 里**，
  否则服务端复算的签名对不上（`danmaku/douyin.py`）。
- `get_sign` 由抖音自己的 `webmssdk.js`（已混淆）现场计算，**纯 Python 无法复现**。
  缺这个参数的后果很明确：**连接建立后约 155 ms 被服务端以 1006 断开，一帧数据都收不到**
  （`danmaku/signature.py`）。

因此 `danmaku/signature.py` 起一个**常驻 JS 运行时进程**（发布包随附 `node.exe`）：
`sign.js` 有 480KB+，每次冷启动都要重新解析混淆代码（实测 300ms+），
所以用「**stdin 一行 md5 → stdout 一行签名**」的协议复用已加载的 VM 上下文，单次计算降到毫秒级
（`danmaku/signature.py` 的 `_DRIVER_JS`；预热时先跑一次丢弃结果触发惰性初始化，`__PING__` / `__EXIT__` 为控制指令）。

- 单次计算超时 `SIGN_TIMEOUT = 20.0` 秒；
- 连续失败 `MAX_CONSECUTIVE_FAILURES = 3` 次后**彻底放弃**并把 `signature_provider` 置空，
  避免每条弹幕都卡 20 秒（`danmaku/signature.py`）。
- **绝不假装能算**：没有可用的 JS 运行时或没有 JS 文件时 `signature_available()` 返回 `False`，
  抓取器把失败原因如实报给界面。
- JS 文件用 `SCREENKEY_SIGN_JS` 指向自己的副本；源码运行时可用 `SCREENKEY_NODE` 指定 node。

### 帧循环（长连接上发生的事）

```
服务端 ──► PushFrame
            payloadEncoding = ""（**实测为空**，别在这里找压缩方式）
            payloadType     = "msg"
            headersList     = [{compress_type: "gzip"}, {im-internal_ext: ...}]
            payload         = gzip(Response)
                └─ Response.messagesList = [Message, ...]
                       Message.method  = "WebcastChatMessage" 等（信封 field 1）
                       Message.payload = 具体消息体            （信封 field 2）

客户端 ──► ack        把 internal_ext 塞进 PushFrame.payloadType="ack"（build_ack, danmaku/douyin_protocol.py）
                       不回 ack，服务端会认为客户端跟不上而断开
客户端 ──► 心跳        b':\x02hb'（即 payloadType="hb"）
```

几个实测踩过的细节，都在代码注释里写明原因：

- **ack 用的 `internal_ext` 有两个来源**：`Response.internal_ext` 与
  `headersList` 里的 `im-internal_ext`（常量 `HEADER_INTERNAL_EXT`，`danmaku/douyin_protocol.py`）。
  实测两种都出现过，**只认一个就会漏 ack**（`danmaku/douyin.py`）。
- **压缩方式不在 `payloadEncoding` 里**：实测真实下行帧的 `payloadEncoding`（field 6）是**空的**，
  压缩只在 `headersList` 的 `compress_type` 里声明。只看 field 6 的后果是 gzip 数据被当成裸 protobuf 解析，
  表现为「连接稳定、却永远 0 条弹幕」。解码按三条证据依次判断：`compress_type` → `payloadEncoding` →
  payload 前两字节为 `1f 8b`（gzip 魔数）兜底（`decode_payload`，`danmaku/douyin_protocol.py`）。
- **消息信封的字段号是 `1=method` / `2=payload` / `3=msgId`**，不是 `6` / `8`。
  早期版本把 payload 写成 `(6, 8)`，那两个号实际是 `needWrdsStore`(bool) 与 `wrdsSubKey`(string)，
  于是**每一条消息都被静默丢弃**（连接正常、收帧正常、永远 0 条）
  （常量 `MSG_METHOD` / `MSG_PAYLOAD` / `MSG_MSG_ID`，`danmaku/douyin_protocol.py`）。
- **`compress_type` 与 ack 要回的 `internal_ext` 都在 `headersList` 里**
  （`HEADER_INTERNAL_EXT = "im-internal_ext"`，`danmaku/douyin_protocol.py`），
  只认 `Response.internal_ext` 会漏 ack（`danmaku/douyin.py`）。
- **`internal_ext` 绝不能留空**：空值实测会被服务端拒绝（`danmaku/douyin.py`）。
- **Cookie 合并要按键比较、取 `morsel.value`**：aiohttp 迭代出的 `Morsel`
  用 `str()` 会得到整段 `Set-Cookie` 文本，f-string 拼接会把 Cookie 头污染成畸形串，服务端拒绝升级
  （`danmaku/douyin.py`）。
- **`ttwid` 取值要校验格式**：真实 `ttwid` 形如 `1%7C<base64url>%7C<ts>%7C<md5>`，
  不含空格和冒号；只做 `ttwid=([^;\s]+)` 会把 `ttwid=Set-Cookie: ttwid=...` 里的字面量匹配进来
  （`danmaku/douyin.py`）。

### 为什么手写 protobuf 解析

`danmaku/protobuf_lite.py` 不依赖 `protoc` / `grpcio-tools`。理由：

- 抖音的字段号会随平台改版**漂移**。用 protobuf 编译器意味着字段对不上就直接抛异常；
  手写解析对未知字段号**直接跳过**，不会因为多了一个新字段就整个失效。
- `douyin.py` 对关键字段采用「**多候选字段号 + 逐个试**」的策略（`_pick` / `_pick_int` /
  `_pick_str`，`danmaku/douyin_protocol.py`），平台小改版不会让功能整体失效。

代价是解析器要自己维护，且大幅改版仍可能导致某类消息解析不出来——这是已知限制。

### 消息类型映射

帧里的 `Message.method` 经 `douyin.py` 分派到各自的构造器：
`_build_chat`（弹幕）、`_build_gift`（礼物）、`_build_member`（进场）、`_build_like`（点赞）、
`_build_social`（关注）、`_build_stats`（统计）、`_build_control`（控制）
（`danmaku/douyin.py`），统一产出 `DanmakuMessage`，之后的流程与 B 站完全一致。

## 六、B站四处环境陷阱

这四条都不是「理论上可能」，是实测复现出来的，而且**都会让 B 站弹幕整体不可用却看起来像别的问题**。

### 1. `blivedm` 0.1.x 是扁平单文件包，探测必须与子模块解耦

PyPI 上的 `blivedm`（最新只有 0.1.0 / 0.1.1）**没有子包**，只有四个模块：

```
blivedm/__init__.py   # from .models import * / from .handlers import * / from .client import *
blivedm/client.py     # BLiveClient、InitError
blivedm/handlers.py   # BaseHandler
blivedm/models.py     # DanmakuMessage、GiftMessage …
```

最初的写法把两个 import 塞进同一个 `try`：

```python
try:
    import blivedm
    import blivedm.models.web as _blivedm_models   # ← 这个模块不存在
    BLIVEDM_AVAILABLE = True
except ImportError:
    BLIVEDM_AVAILABLE = False
```

`blivedm.models` 是**模块**不是包，`import blivedm.models.web` 抛
`ModuleNotFoundError: No module named 'blivedm.models.web'; 'blivedm.models' is not a package`，
把同一个 `try` 里的 `import blivedm` 一起带走了。后果是 `BLIVEDM_AVAILABLE` 恒为 `False`，
`connect()` 直接返回 `False` 并**谎报「缺少 blivedm 依赖，请运行: pip install blivedm」**——
用户装了依赖却被告知没装，而且整个 B 站功能静默失效。

修改后的结构：`import blivedm` 单独一个 `try`（它决定 `BLIVEDM_AVAILABLE`），
子模块用 `importlib` 另起一段**只探测、不致命**地遍历候选名，赋给 `_blivedm_models`。
同一处逻辑在 `main.spec` 的 `hiddenimports` 里也踩过：
写 `blivedm.clients` / `blivedm.models.web` 会让 PyInstaller 找不到模块，
而且打包后探测同样失败——现在写的是 `blivedm.client` / `blivedm.handlers` / `blivedm.models`。

### 2. 不显式声明 `Accept-Encoding` 就会踩到 brotli 不兼容

`aiohttp` 只要能 `import brotli` 就把 `br` 加进自动协商的编码里
（`aiohttp/compression_utils.py`）。
本机实测（本地回环服务器回显请求头）：

```
no override (aiohttp default)    -> server saw Accept-Encoding: 'gzip, deflate, br'
Accept-Encoding: gzip, deflate   -> server saw Accept-Encoding: 'gzip, deflate'
```

而 `blivedm` 的依赖锁定了 `brotli==1.0.9`，它的 `Decompressor` **只有单参 `process(data)`**：

```python
>>> brotli.Decompressor().process(b"", 8192)
TypeError: process() takes exactly 1 argument (2 given)
```

实测三个版本（从 PyPI 下 wheel 逐个解开验证）：

| brotli 版本 | `Decompressor` 的 API | `process(data, max_length)` |
| --- | --- | --- |
| **1.0.9**（`blivedm` 锁定） | 只有 `process(data)` | `TypeError`（单参签名） |
| 1.1.0 | 只有 `process(data)` | `TypeError`（单参签名） |
| 1.2.0 | 只有 `process(data)` | **能跑**（已支持双参） |

所以坏的是 1.0.9 / 1.1.0，1.2.0 才修好。可惜"升级 brotli"这条路走不通：
`blivedm` 0.1.1 的 `requires_dist` 是 `['aiohttp (>=3.7.4)', 'brotli (==1.0.9)']`，
**精确锁定** 1.0.9；而 PyPI 上 `brotli` 1.0.9 共 82 个文件（81 个 wheel + 1 个 `Brotli-1.0.9.zip` 源码包），
**最高的 CPython 只到 cp311，没有任何 cp312 的 wheel**——
Python 3.12 下装它必然触发本地源码编译（需要 MSVC）。
结论：绕开 `br` 比动依赖链稳妥得多。

`aiohttp` 3.14.4 的 `BrotliDecompressor.decompress_sync` 在 `max_length` 非 0 时
会调 `self._obj.process(data, max_length)`（`aiohttp/compression_utils.py`，第 460 行），
于是抛出的 `TypeError` 被包成
`ContentEncodingError: 400, message: Can not decode content-encoding: br` ——
**每一个 HTTP 响应都解码失败**，`init_room()` 之类全部走不通。

抖音抓取器一开始就写对了（`danmaku/douyin.py` 显式声明 `"Accept-Encoding": "gzip, deflate"`），
B 站这条路径当初漏了，现在补上。测试 `tests/test_bilibili.py` 里有一条
`test_aiohttp_session_header_matches_douyin` 专门锁死「两边必须一致」，防止再次漂移。

> 注：`_brotli` 后端本身没问题（一次性 `brotli.decompress()` 往返正常，
> `blivedm` 解 B 站帧正是走这条路径，`blivedm/client.py`）；
> 坏的只是 aiohttp 的**流式**解压调用约定。
>
> 还有一个环境细节：本机 `.venv` 里的 `brotli.py` / `_brotli.cp312-win_amd64.pyd`
> 是 **1.0.9 但没有 `brotli-1.0.9.dist-info`**（参考项目的 venv 里两者都有），
> 说明它是在没有 cp312 wheel 的情况下由源码编译产出或被手工放置的。
> 这不影响程序运行，但意味着 `pip list` 看不到它——
> 如果哪天要重装环境，请记得 `brotli==1.0.9` 在 Python 3.12 上需要 MSVC 编译。

### 3. 「已连接」必须在 WebSocket 真的握手之后

`blivedm` 的 `BLiveClient.start()` 只是 `asyncio.create_task(self._network_coroutine_wrapper())`
（`blivedm/client.py`，第 203 行就是那句 `create_task`），此刻
`init_room()` → `ws_connect()` → 认证**都还没发生**。
最初在 `start()` 之后立刻 `_notify_status(True)` 并 `return True`，
于是在 `-352` 风控导致 `init_room()` 失败、降级到默认服务器列表时，
界面已经显示「已连接」——用户以为通了，实际一帧都收不到。

现在的做法：注册一个只负责置位的观察者 `_WsReadyHandler`
（`_on_ws_connect` 置 `fetcher._ws_ready = True`，`_on_ws_close` 置回 `False`），
`connect()` 用 `_wait_ws_ready()` 以 50ms 步长轮询、上限 `connect_timeout = 15.0` 秒，
`_join_task` 提前结束就立刻放弃；等到了才 `_notify_status(True, "已连接 B 站直播间")`，
等不到就 `_notify_status(False, "B 站连接未就绪")` 并返回 `False`。

选轮询而不是 `asyncio.Event`，是为了不让一个 asyncio 原语成为跨事件循环的共享状态——
50ms 的轮询代价在这个场景可以忽略，而 `Event` 一旦绑定错 loop 会静默失效。

### 4. 连不上时必须说清原因：`-352` 曾被误判成"按 IP 判定的接口级风控"

> **更正（2026-10-23）**：本节结论**已被实测推翻**。`-352` 的真正主因是
> `getDanmuInfo` **缺 WBI 签名**（`w_rid`/`wts`），而不是出口 IP。同一台机器、
> 同一条网络，给请求补上签名后立刻 `code=0` 并拿到 `host_list`，实测连上房间
> `34348`、30 秒收到 41 条弹幕。本节的四路对照之所以全部得到 `-352`，是因为
> **每一条分支都没带签名**——它们能排除"房间号/域名/Cookie/请求头"，却排不掉
> "缺签名"。实现见 `danmaku/bilibili_wbi.py`；`room_init` 也必须改用
> `?id=<房间号>`（`?room_id=` 会返回 `60004` 或 `-352`）。
> 下面这段保留原文，作为"取证范围没覆盖到关键变量"的反面教材。

上面那条修完之后，`-352` 的表现从"假已连接"变成了"如实报错"，但报的是
`B 站连接未就绪`——**用户据此唯一能做的就是反复换房间号，而换房间号完全没用**。
所以又补了一层诊断：`connect()` 在未就绪分支里调用 `_diagnose_ws_failure()`，
主动再请求一次 `getDanmuInfo`，把返回码翻成人话。

**为什么能确定是接口级风控**（`E:\DSHwork\.tmp\probe_bili_352.py` /
`probe_bili_buvid.py` / `probe_bili_alt_endpoints.py` / `probe_bili_ws_bypass.py` 四路取证）：

| 实验 | 结果 | 说明 |
| --- | --- | --- |
| `Room/get_info`（4 个房间） | 全部 `code=0` | 网络通、域名没被墙 |
| 直连 `getDanmuInfo`（4 房间 × 2 次） | **8 次全部 `code=-352`** | 与房间号无关 |
| 同域名 `room/v1/Danmu/getConf` | `code=0`（返回 4 个 host） | **同一域名下只封了这一个接口** |
| 带 `buvid3`/`buvid4`（`x/frontend/finger/spi` 现取） | 仍 `-352` | 不按 Cookie 判定 |
| 完整浏览器头（UA / Referer / `sec-ch-ua` / `Origin`） | 仍 `-352` | 不按请求头判定 |
| `web_location` 参数 / POST 表单 / `app-room` 接口 | `-352` / HTTP 405 / `-400` | 换接口也没用 |
| 用 `getConf` 的 host 直连 WS、认证包不带 `key` | 服务器直接关连接 | token 必需，绕不过 |

结论：**换网络出口才有用**（家宽 / 手机热点），换房间号、换 Cookie、换请求头都没用。

**实现上踩到的第二个坑**：第一版诊断用 `await resp.json(content_type=None)`，
结果永远走兜底分支。原因是 aiohttp 默认**不带浏览器 UA**，B 站直接回
**HTTP 412 + 反爬 HTML**（实测 `Content-Type: text/html`、正文 3286 字节），
`json()` 抛 `JSONDecodeError` 被 `except` 吞掉 —— **看起来有诊断，实际永远是兜底文案**。
修法是显式带 `_BROWSER_UA` 与 `Referer`，并且**先判 `resp.status`、再宽容地 `json.loads(text)`**，
把"412 反爬页"和"真的 JSON 错误码"分开处理。

诊断本身绝不能把连接流程弄挂，所以它是个纯"尽力而为"的分支：
任何异常、非 200、非 JSON 都返回兜底文案，不影响 `connect()` 的返回值和后续清理。

守住它的测试见 `tests/test_bilibili.py::TestFailureDiagnosis`（9 项），
其中两条是机制断言：`test_request_pretends_to_be_a_browser`（必须带 Mozilla UA + Referer，
否则会被 412 挡掉）与 `test_connect_calls_diagnosis_when_not_ready`（诊断必须在未就绪分支里被**调用**，
不能只是被定义）。非空性证明 `E:\DSHwork\.tmp\prove_bili_diag_nonvacuous.py`：
原始 sha256 `e5a85414fe049877`，锚点 A（删掉诊断调用）→ `1 failed, 25 passed`，
锚点 B（去掉浏览器 headers）→ `1 failed, 25 passed`，恢复后 sha 一致、`26 passed`，`VERDICT=PROOF_OK`。

### 附：怎么验证「诊断代码真的在 exe 里」——dist 目录里搜字符串永远是 0 命中

补完诊断后要确认它真的进了打包产物，第一反应是去 `dist\` 里 grep `风控拦截`——
**total hits 0**，看起来像没打进去。实际上 `dist\幕键\_internal\screenkey\`
下**只有 `data\sign.js`**，没有任何 `.py`：Python 模块全被收进
PyInstaller 的 **PYZ 归档**（zlib 压缩，`PYZ.pyz` 共 **5888905 字节 / 708 个模块**）。
所以"搜不到"既不证明有、也不证明没有，那种搜法本身没有判别力。

正确做法是用 PyInstaller 自己的 reader 把模块取回来执行
（`E:\DSHwork\.tmp\verify_exe_pyz_bili_diag.py`）：

```python
from PyInstaller.archive.readers import CArchiveReader, ZlibArchiveReader
car = CArchiveReader(r"dist\幕键\ScreenKey.exe")   # 13 个归档条目
pyz = car.extract("PYZ.pyz")
Path("_exe_pyz.pyz").write_bytes(pyz)
zar = ZlibArchiveReader("_exe_pyz.pyz")   # 只接受文件名，传 bytes 会 TypeError
code = zar.extract("screenkey.danmaku.bilibili")
```

`CArchiveReader` 能吃 `str`，`ZlibArchiveReader` **只能吃文件名**（内部
`_parse_offset_from_filename` 会 `rfind('?')`，传 bytes 报
`TypeError: argument should be integer or bytes-like object, not 'str'`），所以中间必须落盘一次。

把 code object `exec` 进一个模块再跑**真实被风控房间**的完整 `connect()`
（`verify_exe_bili_diag_e2e.py`）→ **`PASS=6 FAIL=0`**：

```
connect() 返回： False
statuses = [(False, 'B 站接口返回 -352（风控拦截）：当前网络出口的 IP 被限制，'
                    '换房间号没有用，请换网络（家宽 / 手机热点）后重试')]
```

这同时证明两件事：诊断代码确实在 exe 里，且它在冻结环境里**真的走到了 `-352` 分支**
（不是静默落兜底）。

**踩的坑**：第一版探针直接调 `_diagnose_ws_failure()`，拿到的是兜底文案
`B 站连接未就绪（可能是网络问题或接口风控）`，一度以为冻结产物有问题。
真实原因是该函数用 `self._session`，而 `self._session` 要 `connect()` 才创建——
单独调它必然 `self._session is None` → 立刻走兜底。**探针用错了入口，不是产品错**。
反过来这也说明诊断函数"任何异常都吞掉"的写法是必要的：它得容忍自己被在
环境不完整时调用。另一条：`--platform` / `--room` 只**预填界面**、不会自动点
「开始接收弹幕」（只有 `--simulate` 会调 `_on_connect()`），所以想用 exe 直接触发
`connect()` 是走不通的，必须像上面那样把模块取出来调。

## 七、测试基础设施（受限环境下的两个陷阱）

这一节记的是**测试怎么跑得起来**，不是被测代码怎么工作。两条陷阱都源自同一个根因，
而且报错信息都长得像"权限坏了"，实际上跟权限配置无关。

### 陷阱一：`tmp_path` 用的 `0o700` 恰好是本环境唯一不可用的权限组合

pytest 内置的 `tmp_path` / `tmp_path_factory` 一律用 `mode=0o700` 建目录
（`_pytest/tmpdir.py` `p.mkdir(mode=0o700)`，另见 `:158` / `:168` / `:172` / `:218`）。
在本工作区的受限令牌下，实测：

| 目录权限 | list | write | rmdir |
| --- | --- | --- | --- |
| `0o700` | ❌ `[WinError 5]` | ❌ `[Errno 13]` | ❌ |
| 默认（不传 mode） | ✅ | ✅ | ✅ |
| `0o750` / `0o755` / `0o770` / `0o777` | ✅ | ✅ | ✅ |

顺序无关、每项重复 6 次结果一致；`os.makedirs(mode=0o700)` 同样坏，
`tempfile.mkdtemp(dir=...)` 之后 rename 也报 `[WinError 5]`。
失效点在**夹具解析阶段**，所以任何用到 `tmp_path` 的测试都会直接 error：

```
PermissionError: [WinError 5] 拒绝访问。:
'...\AppData\Local\Temp\dsh-XXXX\pytest-of-<user>'
```

`tests/conftest.py` 因此用同名夹具**顶掉**内置实现：在项目内 `.test_tmp/` 下用
不带 mode 的 `Path.mkdir()` 建目录，并在 teardown 里 `shutil.rmtree(ignore_errors=True)`
（删不掉不算失败——本环境确实有删不掉的目录）。
`tmp_path_factory` 一并替换，因为内置那个在 session 结束时会
`cleanup_dead_symlinks()` → `iterdir()`，同样被拒。

> 中途试过"只把 `--basetemp` 挪到项目内"这条更省事的路，**它救不了**：
> pytest 建那一层 basetemp 用的仍是 `0o700`，而且 session 结束时照样去遍历它。

### 陷阱二：删不掉的残留目录会打断裸 `pytest` 的采集

同一个 `0o700` 根因会让项目根下遗留的 `pytest-cache-files-*`（cacheprovider 在
`_pytest/cacheprovider.py` 用 `mkdtemp` 建的）变成**连安全描述符都读不到、
因而删不掉**的目录：`Remove-Item -Recurse -Force`、`icacls`、`takeown`、
`cmd /c rd /s /q` 全部拒绝。

pytest 默认的 `norecursedirs`（`_pytest/main.py` 的 ini 默认值）只有
`*.egg` / `.*` / `_darcs` / `build` / `CVS` / `dist` / `node_modules` / `venv` / `{arch}`，
**不匹配** `pytest-cache-files-*`，于是裸跑 `pytest` 会对它们 `iterdir()` 并当场：

```
PermissionError: [WinError 5] 拒绝访问。: '...\pytest-cache-files-oy59pck2'
!!!!!!!!!!!!!!!!!! Interrupted: 10 errors during collection !!!!!!!!!!!!!!!!!!
```

`conftest.py` 的 `pytest_configure()` 用 `config.addinivalue_line("norecursedirs", ...)`
把 `pytest-cache-files-*` 与 `_probe*` 追加进去，于是 `pytest` 与 `pytest tests`
两种跑法结果一致。

> `norecursedirs` 是 **ini 选项**，由 `config.getini("norecursedirs")` 读取
> （`_pytest/main.py`），**不在** `config.option` 上。写成
> `config.option.norecursedirs = ...` 会抛
> `AttributeError: 'Namespace' object has no attribute 'norecursedirs'`
> ——这条弯路走过，报错发生在 `pytest_configure` 里、表现为 `INTERNALERROR`。

这两条陷阱都被 `tests/test_test_infra.py` 锁住（覆盖是否真的生效、默认模式有没有被挤掉、
裸跑时的模式是否注册），所以将来有人删掉这段基础设施时会立刻红，而不是等到
某个无辜的测试在夹具解析阶段报一个看起来像权限问题的错。

## 七之二、实例属性遮蔽同名方法（一个被宽 `except` 藏起来的缺陷）

这条单独立一节，因为它的**失败方式**值得记住：真实缺陷、真实崩溃，
却既没有日志级别上的异常、也没有让任何测试变红。

### 症状

走真实的 `SimulatorFetcher.start()`（起后台线程、真事件循环）时，
弹幕**一条都收不到**，只在日志里留下：

```
模拟器异常: 'ProactorEventLoop' object is not callable
```

### 根因

`DanmakuFetcher.__init__` 曾用 `self._loop` 保存事件循环
（原 `base.py` `self._loop: Optional[asyncio.AbstractEventLoop] = None`），
而 `SimulatorFetcher` 恰好把主循环方法命名为 `async def _loop()`。
**Python 的实例属性优先于类里的方法**，于是 `await self._loop()`
拿到的是 `ProactorEventLoop` 对象而不是方法。

这个 `TypeError` 又被 `_guarded_loop` 的 `except Exception` 接住，
降级成一条 `logger.error` —— 于是：

- 没有任何测试失败（此前大家只调 `make_message()` / `emit_once()`，从不走 `start()`）
- 界面只会显示「已连接、0 条弹幕」，看起来跟"房间没人说话"一模一样

### 修法（两处，双保险）

1. 基类属性改名 `self._event_loop`（`danmaku/base.py`），`run_coroutine()`
   里的读取点同步改（该协程后来作为死代码删掉了，此处只作历史记录）。
2. 子类方法改名 `_emit_loop`（`danmaku/simulator.py`），并在 docstring 里
   写明为什么**不能**再叫 `_loop`。

### 守住它的测试

`tests/test_fetcher_lifecycle.py`：

- AST 级扫描：子类方法名 ∩ 基类实例属性名必须为空，四个抓取器文件都扫
- 真的跑 `start()`：断言 5 秒内至少 5 条弹幕、`on_error` 没有被调用
- `_emit_loop` 必须是协程函数，且实例上取出来的也是绑定方法
- `connect()` 源码里不得出现 `await self._guarded_loop`

> **通用教训**：基类里每个 `self._xxx` 都占用了子类的名字空间。
> 子类给方法起名时要么用带前缀的描述性名字，要么让基类属性名足够具体
> （`_event_loop` 而不是 `_loop`）。另外，`except Exception` 包住整个后台
> 循环虽然能防线程崩死，但也会把这类编程错误伪装成运行期噪音——
> 所以「后台循环有没有真的产出数据」值得单独写一条端到端断言。

## 七之三、字段声明与运行时取值不一致，导致「收到第一条弹幕就闪退」

与前两节同源：**真实缺陷、真实崩溃，302 条里 268 条全绿时依然存在**
（测试套件后来已增长到 534 条，这个数字是当时的历史记录）。

### 症状

界面能正常启动（日志里窗口建好、热键注册、模拟器启动都在），
然后**在第一条弹幕到达的瞬间整个进程消失**：

```
exit=-1073740791  (0xC0000409, STATUS_STACK_BUFFER_OVERRUN)
```

同样的 `0xC0000409` 在源码直跑和打包 exe 上都出现，所以它不是打包问题。
源码直跑能看到真正的 traceback：

```
File ".../src/screenkey/ui/main_window.py", line 544, in _on_message
    self.danmaku_window.append(message, actionable=actionable, matched=matched)
File ".../src/screenkey/ui/danmaku_window.py", line 134, in append
    stamp = datetime.fromtimestamp(message.timestamp or 0).strftime("%H:%M:%S")
TypeError: 'datetime.datetime' object cannot be interpreted as an integer
```

### 根因（四环，缺一环都不会崩）

1. `DanmakuMessage.timestamp` 的**声明**类型是 `datetime`
   （`danmaku/message.py`），但 `__post_init__` 当时并不规整它——
   谁传 float、毫秒整数、ISO 字符串都能原样存进去。
2. 界面的写法是 `message.timestamp or 0`，本意是"没有就兜底成 0"。
   但 **`datetime` 恒为真**（`bool(datetime(2000,1,1)) is True`），
   所以 `or 0` 永远取左边，兜底形同不存在。
3. `datetime.fromtimestamp(datetime 对象)` → `TypeError`。
4. **PyQt5 5.15 遇到槽里的未捕获异常会 `qFatal` 终结整个进程**，
   而不是只丢掉那一条弹幕。前三点在任何框架里都只是"这条弹幕显示不了"，
   到第 4 点就变成"程序闪退"。

另有一处同源缺陷：`DanmakuMessage.from_dict` 自己手写了
"datetime / ISO 字符串 / **其他一律 `datetime.now()`**" 三分支。
平台原始数据里最常见的**毫秒整数时间戳正好落进第三个分支**，
于是时间戳被静默换成"此刻"——不报错、不崩溃，只是时间全错。

### 为什么当时 268 条测试没抓到

- `tests/` 里**没有任何一条**构造 `DanmakuWindow` 或调用它的 `append()`
  （`test_ui_smoke.py` 只建 `MainWindow`，不打开弹幕窗）
- `DisplayConfig.show_timestamp` 默认是 **True**（`config/models.py`），
  也就是说**默认配置下必崩**，不是边角情况
- `__post_init__` 不规整字段这件事，没有任何测试断言过

### 修法（选择"修数据源头"，不是"装兜底"）

| 位置 | 改动 |
| --- | --- |
| `danmaku/message.py` `__post_init__` | 末尾加 `object.__setattr__(self, "timestamp", timestamp_to_datetime(self.timestamp))`，让声明类型与运行时取值一致 |
| `danmaku/message.py` `from_dict` | 三分支合并为 `timestamp = timestamp_to_datetime(data.get("timestamp"))`，数字时间戳不再被丢弃 |
| `ui/danmaku_window.py` | `message.timestamp.strftime("%H:%M:%S")` |
| `ui/danmaku_window.py`（导出） | `msg.timestamp.strftime("%Y-%m-%d %H:%M:%S")` |

> **为什么不在界面里加 `isinstance` 判断？** 那只是把同一个判断复制到每个
> 使用点，将来加一个使用点就再漏一次。`timestamp_to_datetime`（`utils/helpers.py`）
> 本来就支持 datetime / ISO 串 / 秒级 / 毫秒（`>1e11` 除以 1000），
> 只是没人让数据模型去用它。

### 关于 `sys.excepthook`：实测有效，但本次没装

对照实验（三个独立子进程，均先 `configure_qt_environment()`）证明：

| 场景 | 结果 |
| --- | --- |
| 槽里裸抛异常 | **进程被终结**，`returncode=3221226505` (0xC0000409) |
| 装了自定义 `sys.excepthook` | `returncode=0`，**存活**，hook 被调用 |
| 槽内 `try/except` | `returncode=0`，存活 |

结论是**两种兜底都能阻止 abort**，`sys.excepthook` 是可用的。
本次仍然选择修数据源头，理由同上；如果将来要再加固，
`sys.excepthook` 是第一顺位（它一处生效、覆盖所有槽）。
**但要注意：兜底只让程序活着，缺陷本身不会被修好，用户看到的是"这条弹幕没了"。**

### 守住它的测试

`tests/test_message_timestamp.py`（34 项）：

- 6 种输入（datetime / 秒级 int+float / 毫秒 int+float / ISO 串）构造后
  必须都是 `datetime`；4 种垃圾输入（`None` / 空串 / 乱码）不抛异常且回落"此刻"
- 秒级与毫秒级同一时刻必须得到同一个 `datetime`（防"单位猜错"）
- `test_truthiness_bug_that_made_or_0_useless` —— 把"`or 0` 救不了"钉住
- `from_dict` 的数字时间戳不再被丢弃；`to_dict`/`from_dict` 往返稳定
- 界面层：真的建 `DanmakuWindow` 并 `append()`（含默认 `show_timestamp=True`）、
  `_flush()` 真写 DOM、`_save()` 导出（monkeypatch 掉阻塞的 `getSaveFileName`）
- 从 `MainWindow._on_message` 一路走到弹幕窗（真实崩溃发生的那条链）

非空性已用回退实验证明：把两处修复回退成修复前的写法后，
这 34 项里 **20 项失败**；恢复后 **34 项全绿**
（脚本 `E:\DSHwork\.tmp\prove_ts_test_nonvacuous.py`）。

> **通用教训**：**字段的声明类型必须由 `__post_init__` 保证**，
> 否则它就只是一句注释。尤其当"宽容接受多种输入"（宽容反序列化、
> 平台原始数据直接入模型）和"下游按声明类型使用"同时存在时，
> 两端都以为对方会规整。另外，`x or default` 对 `datetime`/`Decimal`
> 这类**恒为真**的对象不是兜底而是空操作——写兜底前先想清楚它到底在防什么。

## 七之四、打包：PyQt5 5.15.x 处理不了非 ASCII 安装路径

这是"把项目放在中文目录里"才会出现、但报错信息会把人引向完全错误方向的一类问题。

### 症状

`python -m PyInstaller main.spec` 在收集 Qt 插件时抛异常：

```
File "...\PyInstaller\utils\hooks\qt\__init__.py", line 523, in collect_plugins
    raise Exception(f"Qt plugin directory '{plugin_src_dir}' does not exist!")
Exception: Qt plugin directory 'E:/DSHwork/????V2/.venv/Lib/site-packages/PyQt5/Qt5/plugins' does not exist!
```

注意路径里的 **`????V2`**——「幕键」四个汉字被替换成了四个问号。
而那个目录**真实存在**（`platforms\qwindows.dll` 1477104 字节，好好的）。

### 根因：不是 PyInstaller，是 `QLibraryInfo`

直接用 PyQt5 读一遍就清楚了：

```python
from PyQt5.QtCore import QLibraryInfo
QLibraryInfo.location(QLibraryInfo.PluginsPath)
# 'E:/DSHwork/????V2/.venv/Lib/site-packages/PyQt5/Qt5/plugins'   ← os.path.isdir 为 False
```

**PyQt5 5.15.2 的 `QLibraryInfo` 把安装路径按 ASCII 转换**，非 ASCII 字符变成 `?`，
于是 `os.path.isdir()` 全部为 False。PyInstaller 的 Qt hook 只是**受害者**：
它去读 `PluginsPath` 收集插件，拿到坏路径后按"目录不存在"抛异常。
换 PyInstaller 版本没有用。

**判别因子只有一条：路径里有没有非 ASCII 字符。** 已实测排除的假设：

| 假设 | 实测结果 |
| --- | --- |
| codecs 插件缺失 | `plugins\codecs` 确实不存在，但 `QTextCodec.codecForLocale()` 是 `b'System'`；`setCodecForLocale(GBK)` 之后路径**仍然** `????V2` |
| `locale.setlocale` 没设 | 实际已是 `LC_CTYPE=Chinese (Simplified)_China.936`；显式 `setlocale(LC_ALL, "")` 后**仍然** `????V2` |
| 环境变量 | `QT_PLUGIN_PATH` / `QT_QPA_PLATFORM_PLUGIN_PATH` / `PYTHONUTF8=0` / `PYTHONLEGACYWINDOWSFSENCODING=1` / `PYTHONCOERCECLOCALE=0` 六种组合**全部无效** |
| Qt 整体不支持中文路径 | `QFileInfo(r"...\幕键\src").exists()` → **True**，`QDir(...).exists()` → **True**。**只有 `QLibraryInfo` 这一条计算路径是坏的** |

### 决定性实验：纯 ASCII 的 junction

用 `mklink /J`（目录联接，**普通用户权限即可，不需要管理员**）建一个纯 ASCII 路径指向项目：

```bat
mklink /J "E:\DSHwork\dmkb2_link" "E:\DSHwork\幕键"
```

从 junction 里的 python.exe 跑同一个探测：

```
真实路径 python.exe  : PrefixPath 'E:/DSHwork/????V2/...'          [MISSING]
junction 里的 python.exe : PrefixPath 'E:/DSHwork/dmkb2_link/...'  [EXISTS]
```

（`LibrariesPath` 两边都是 MISSING，因为 `Qt5\lib` 本就不存在，与缺陷无关。）

> **一个反直觉的细节，也是这个坑真正的难点**：光把工作目录 `cd` 到 junction **不够**。
> `QLibraryInfo` 是按 **`sys.prefix`**（由 python.exe 自身的路径推出）算 Qt 安装前缀的，
> **跟 CWD 无关**。所以必须**通过 junction 里的 python.exe 启动**构建，
> 这样 `sys.prefix` 才是纯 ASCII 的。实测脚本 `E:\DSHwork\.tmp\probe_junction_prefix.py`：
> 真实路径 python.exe → `sys.prefix = E:\DSHwork\幕键\.venv`（非 ASCII）；
> junction 里的 python.exe → `sys.prefix` 纯 ASCII，Qt 三个路径全部 EXISTS。

### 修法：`tools/build_helper.py` + `build.bat`

`tools/build_helper.py`（约 330 行）负责这套流程，`build.bat` 在第 2 步调用它：

1. `is_ascii_path()` 判断项目路径；纯 ASCII 就直接返回，什么都不做；
2. 含非 ASCII 时，从 `SCREENKEY_BUILD_LINK` 环境变量 / `%TEMP%` / `%USERPROFILE%` / `%SystemDrive%\`
   依次挑一个可写位置，建 junction `dmkb2_build_link`；
3. `build.bat` 用 `set "BUILD_PY=%BUILD_ROOT%\.venv\Scripts\python.exe"` 跑 PyInstaller
   ——**是 junction 里的 python.exe，不是 `%VENV_PY%`**，这是上一节那条反直觉细节的落地。

几个实现细节值得记住：

- `_link_points_at()` 用 `Path.resolve()` 判断 junction 是否已指向正确目标，
  **不去解析 `dir /al` 的输出**——中文 Windows 上 `dir` 的输出格式会变，
  早期版本因此把目标读成 `None`，每次都白删重建（失去幂等性）。
- `_remove_link()` **必须用 `os.rmdir`**：junction 不是普通目录，
  `shutil.rmtree` 会**跟随链接进去把真实项目删掉**。
- `--out` 把结果写进文件（UTF-8 无 BOM）再由 batch 用 `set /p` 读，
  因为 `for /f` 解析带引号的命令会报「文件名、目录名或卷标语法不正确」。
- `build.bat` 里必须 `set "PYTHONIOENCODING=gbk:replace"`：脚本开头 `chcp 936` 后
  控制台是 GBK，而 Python 3 默认按 UTF-8 写 stderr，不设就是乱码。
- **存在性判断必须用 `os.path.lexists()`，绝不能用 `Path.exists()`** ——见下一节。

### 一个真实踩到的缺陷：悬空 junction 让构建永久失败

**症状**：`build.bat --check` 与 `build.bat` 都失败，报

```
[处理] 在 C:\...\dmkb2_build_link 建立指向项目目录的 junction …
  [失败] mklink 返回 1：当文件已存在时，无法创建该文件。
```

而它同时又说"已存在但不指向本项目，先删除再重建"——**自相矛盾**：
它知道有东西在那儿，却删不掉，因为**它根本没进删除分支**。

**根因**：junction 的**目标目录被删掉**后，链接本身仍在（悬空 junction）。
此时 `Path.exists()` 会**跟随重解析点**，目标没了就返回 `False`：

```python
link.exists()      # False  ← 跟随重解析点，被骗
os.path.lexists(str(link))  # True   ← 只看名字在不在
link.is_junction()          # True
```

修复前 `ensure_ascii_build_root()` 写的是 `if link.exists():`，于是悬空 junction
被当成"不存在"，跳过删除直接 `mklink`，系统报「当文件已存在时」。
**这个失败是永久的**——重跑多少次都一样，除非手工去删那个链接。

**修法**：新增 `_link_exists(link)`，内部用 `os.path.lexists()`（不跟随链接），
`_link_points_at()` 与 `ensure_ascii_build_root()` 都改走它。
`os.rmdir` 对悬空 junction 同样有效（它本来就不跟随链接），所以删除分支不用改。

> **通用教训**：`Path.exists()` 是"**目标可达**"，不是"**这个名字被占用**"。
> 对符号链接、junction、快捷方式、网络驱动器映射，这两件事会分叉，
> 而且分叉的时机（目标消失）恰好是最需要正确处理的时候。
> 想判断"名字是否被占用"，用 `os.path.lexists()`；
> 想判断"链接指向哪"，用 `resolve()` 之后比较。
>
> 顺带一个测试方法上的坑：这个缺陷**是被新写的测试逼出来的**——
> 在写 `TestRemoveLinkIsSafe` 时我顺手把清理逻辑改成 `_link_exists`，

## 七之五、输入层：三个"看起来在工作"的缺陷

这一节记的三个缺陷有一个共同点：**它们都不会报错，只会让功能悄悄不生效**。
它们是在给 `input/` 补测试时一次性暴露出来的——而在此之前，
`input/keycodes.py`、`keyboard.py`、`mouse.py`、`hotkey.py`
**一条测试都没有**。也就是说：整个"映射到本地键盘"的最后一跳，
此前从未被真正执行过。

### 1. 「游戏模式」复选框是空操作

`KeyboardController.__init__` 里有一行：

```python
self.send_method = send_method or ("directx" if self.game_mode else "sendinput")
```

构造完 `send_method` **一定非空**。而 `set_game_mode()` 里判断是否需要换后端时写的是：

```python
if not self.send_method:          # 永远为假
    self.send_method = "directx" if self.game_mode else "sendinput"
```

于是勾选「游戏模式」什么都不发生，按键仍走 `sendinput`——而 `sendinput`
在游戏里正是会被过滤掉的那一种。实测（`E:\DSHwork\.tmp\probe_game_mode.py`）：
默认构造后切游戏模式，`send_method` 仍是 `'sendinput'`；真发一次 `press('w')`
实际调用的是 `send_key_sendinput` 而不是 `send_key_directx`。

这正是参考项目"游戏模式切回普通模式控制器不重建"那个缺陷的翻版：
**看起来修了，其实改的是一段死代码**。

修法：用一个独立标志记录"用户是否显式指定过后端"。

```python
self._explicit_send_method = bool(send_method)   # __init__
if not self._explicit_send_method:               # set_game_mode
    self.send_method = "directx" if self.game_mode else "sendinput"
```

`set_send_method()` 同样置 `_explicit_send_method = True`，
这样显式选过后端之后，切模式不会再把它覆盖掉。

### 2. `normalize_hotkey` 不合并重复键

原实现用**生成器**推导：

```python
canonical = sorted(_KEY_ALIASES.get(p, normalize_key_name(p)) for p in parts)
```

`normalize_hotkey("ctrl+ctrl+q")` 于是得到 `'ctrl+ctrl+q'`。
但触发判定那边是 `"+".join(sorted(self._pressed))`——`_pressed` 是**集合**，
`ctrl` 只出现一次，两边永远对不上，**这个热键永远不可能触发**。
`"control+ctrl+q"` 这种混用别名与本名的写法同理。

修法是把生成器换成集合推导：`sorted({... for p in parts})`。
用户手滑多打一个键，不该得到一个静默失效的热键。

### 3. `EXTENDED_KEYS` 与 `_EXTENDED_SCAN_CODES` 漂移

`keycodes.py` 里原本有**两张手工维护的表**：`_EXTENDED_SCAN_CODES`（17 项）
与 `EXTENDED_KEYS`（15 项）。后者漏了 `lwin` 与 `divide`。

后果不小：`is_extended_key()` 对这两个键返回 `False`，于是
`send_key_sendinput` / `send_key_directx` / `keybd_event`
**少发一个 `KEYEVENTF_EXTENDEDKEY` 标志**，Windows 会把该键解释成**另一个键**——
又是"不报错，只是发错"。

修法是取消手工表，改为派生：

```python
EXTENDED_KEYS: List[str] = []          # 占位，见下
...
EXTENDED_KEYS = list(_EXTENDED_SCAN_CODES)   # 在源表定义之后
```

两张表不可能再漂移，因为它们本来就是一张。

## 七之六、三个"藏在角落"的缺陷

### 1. 占位二维码把提示文字裁掉了

`login/qr_image.py` 在没装 `segno` 时会画一张占位图，图里写着
"缺 segno，请 pip install segno"。画布尺寸原本是：

```python
size = max(modules, 29)      # modules = rows + 2*border
```

`rows` 由**行数**算出，完全没考虑**列数** `cols = len(text) * char_w`。
于是 13 个字符的 `'INSTALL SEGNO'`（`cols = 78`）在 `size = 29` 的画布里
从第 5 个字符起被 `if 0 <= px < size` **静默裁掉**——后半截 "SEGNO" 整词不可见，
而这句话是用户唯一的提示。

修法：`size = max(modules, cols + 2 * border, 29)`。
取证脚本 `E:\DSHwork\.tmp\prove_qr_canvas.py` 实测：旧尺寸被裁 9 个字符，新尺寸裁 0 个。

### 2. `force=True` 时 raw 弹幕日志仍写旧目录

`utils/logging_setup.py` 里，root 的 handler 在 `force=True` 时会被清空重建，
但弹幕原文那个独立 logger 写的是：

```python
if not danmaku_logger.handlers:          # force 时它已有 handler，条件为假
    danmaku_logger.addHandler(...)
```

于是它**一直抓着第一次配置时那个文件的 handler**。结果：
`app.log` 写到新目录、`danmaku.log` 还在旧目录，排查问题时看不到弹幕原文。

修法：`force` 时先把旧的 handler 逐个 `removeHandler` + `close()` 再重建。
取证脚本 `E:\DSHwork\.tmp\probe_force_raw_logger.py` 修前输出
"A 目录有 danmaku.log: True / B 目录有 danmaku.log: False"。

### 3. PyQt5 的槽函数抛异常会直接杀掉进程（无法用 try/except 兜住）

这一条不是代码缺陷，是**必须知道的平台行为**。给 `ui/worker.py` 的
`EngineBridge._on_event` 写测试时，我原本假设"槽里抛异常，`emit()` 会抛回 Python"，
于是写了个 `try/except` 断言异常不外传。实测推翻了这个假设
（`E:\DSHwork\.tmp\probe_qt_slot_exception.py`）：

```
A) 直接 emit 一个抛异常的槽：
<进程当场结束>
EXIT=-1073740791   (0xC0000409, STATUS_STACK_BUFFER_OVERRUN / Qt qFatal 路径)
```

`AFTER_EMIT` 从未打印——`emit()` **根本不返回**，Python 层的 `try/except`
在它上面没有机会执行。

含义很实际：**任何界面槽函数抛未捕获异常，程序都会以 `0xC0000409` 静默消失**，
日志里连一行错误都不会留下。所以界面槽函数里的防御性 `try/except`
不是可选项，是必需品。这个事实已写进本文件与 README。

守住它的测试因此**不能**在进程内断言（进程已经死了），
只能起子进程取证：`test_slot_exception_kills_process_with_qt_abort_code`
断言子进程 stdout 里有 `BEFORE_EMIT`、没有 `AFTER_EMIT`，
且 returncode 落在 `{-1073740791, 3221226505, 1}` 里。

> **教训**：写"异常会被兜住"这类测试时，先确认这个异常**真的会回到 Python**。
> Qt 的 C++ 边界上有不少地方会把异常转成 `abort()`，
> 此时测试的正确形态是子进程取证，而不是 `pytest.raises`。

> 恢复后 sha 对不上——因为 `qr_image.py` 是 **CRLF**，文本模式读写会做换行翻译。
> 改为字节级读写（解码 → 归一成 `\n` 匹配 → 还原原换行 → 写回字节）后一致。
> 脚本里现在先跑一次"读→写"空转自检，确认往返无损，后面的 sha 断言才有意义。

## 七之七、入口自举插错层级：测试替被测代码兜住的缺陷

### 症状

用户报告（原话）：「我使用 `E:\DSHwork\幕键\启动.bat` 无法正常启动」。

`启动.bat --console` 的实测输出：

```text
[检查] 依赖齐全
[启动] 控制台模式。关闭窗口或按 Ctrl+C 退出。

Traceback (most recent call last):
  File "E:\DSHwork\幕键\src\screenkey\main.py", line 29, in <module>
    from screenkey import __version__  # noqa: E402
    ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^
ModuleNotFoundError: No module named 'screenkey'

[退出] 返回码: 1
```

注意 `启动.bat` 自身**返回 0**（它只是把子进程的返回码打印出来，没有传播），
所以双击时表现为「闪一下就没了」。

### 根因

`src/screenkey/main.py` 把 `sys.path` 引导写错了一层：

```python
# 缺陷版本
_SRC = Path(__file__).resolve().parent          # ...\src\screenkey  ← 包目录自己
if str(_SRC) not in sys.path:
    sys.path.insert(0, str(_SRC))

from screenkey import __version__              # 需要 ...\src 在 sys.path 里
```

本文件位于 `src/screenkey/main.py`，而 `import screenkey` 需要的是
**包目录的父目录** `src`。插成 `.parent` 时，`sys.path` 里出现的是
`...\src\screenkey`，从那里根本看不到 `screenkey` 这个包。

| 表达式 | 值 | `import screenkey` 能否成功 |
| --- | --- | --- |
| `Path(__file__).resolve().parent` | `...\src\screenkey` | ❌ 缺陷版本 |
| `Path(__file__).resolve().parent.parent` | `...\src` | ✅ 修复版本 |

三种组合实测（均在清空 `PYTHONPATH` 的前提下）：

```text
cd 项目根 && .venv\Scripts\python.exe src\screenkey\main.py --version
  → EXIT=1  ModuleNotFoundError: No module named 'screenkey'
set PYTHONPATH=...\src && 同上
  → EXIT=0  幕键 2.0.0
cd /d ...\src && ..\.venv\Scripts\python.exe screenkey\main.py --version   （模拟 start /D "%SRC%"）
  → EXIT=1  ModuleNotFoundError: No module named 'screenkey'
```

这也解释了为什么 `启动.bat --selftest` 看起来是好的：该分支显式
`set "PYTHONPATH=%SRC%"`（`启动.bat:90`），而默认分支（`启动.bat:72` 的
`start "" /D "%SRC%" "%GUI_PY%" "%ENTRY%"`）与 `--console` 分支（`:79`）
**都没有设** `PYTHONPATH`。**一个分支恰好绕过缺陷，掩盖了另外两个分支全坏。**

### 为什么 534 条测试全都没抓到

因为**每一处测试都替它把 `PYTHONPATH` 设好了**：

- `tests/test_cli.py` 与 `:121`：`env["PYTHONPATH"] = str(SRC)`
- `tests/conftest.py`：`sys.path.insert(0, str(SRC))`
- `tests/test_ui_smoke.py`、`tests/test_message_timestamp.py`：同上

于是 `main.py` 自己的引导逻辑**从未被执行到**：测试跑的是"外部已经把路径
铺好"的场景，而用户跑的是"只有入口自己"的场景。这是"测试把被测代码的缺陷
替用户兜住"的典型——测试越周到，这个缺陷藏得越深。

> **通用教训**：当被测代码有一条"自己找路"的引导逻辑时，
> 测试**不能**把那条路替它铺好，否则测的就不是它。
> 判据很简单：**这条测试如果删掉入口里的引导代码，还会通过吗？**
> 会通过，就说明它在测夹具、不在测入口。
> 所以回归测试刻意 `env.pop("PYTHONPATH", None)`，
> 并在三种不同工作目录下各跑一次。

### 修法

```python
_PACKAGE_DIR = Path(__file__).resolve().parent   # ...\src\screenkey
_SRC = _PACKAGE_DIR.parent                       # ...\src —— 只有它能让 import screenkey 成功
if str(_SRC) not in sys.path:
    sys.path.insert(0, str(_SRC))
```

（保留 `_PACKAGE_DIR` 命名是为了让"插的是谁的父目录"这件事在代码里可读。）

### 守住它的测试

`tests/test_cli.py::TestBootstrapWithoutPythonPath`（6 项），每一例都
`env.pop("PYTHONPATH", None)`：

| 测试 | 断言 |
| --- | --- |
| `test_version_works_from_any_cwd_without_pythonpath` | 项目根 / `src` / 任意其它目录三种 CWD 下 `--version` 都返回 0，且输出不含 `ModuleNotFoundError` |
| `test_module_form_still_works` | `python -m screenkey.main` 仍然可用（两种入口都要活） |
| `test_selftest_works_without_pythonpath` | 自检也返回 0、11 项全 `[OK]` |
| `test_bootstrap_inserts_src_not_package_dir` | **机制断言**：用 `runpy.run_path` 探针 dump `sys.path`，断言 `src` 在里面、`src\screenkey` 不在 |

最后一项是刻意的**机制断言**而非行为断言：即使将来目录结构变了而行为恰好
还能通过，只要插入的层级不对就会在这里失败。

同一文件里还有 `TestLauncherBat`（3 项），守的是**用户真正的入口**
`启动.bat` 本身——修好 `main.py` 只是第一层，当时没有任何测试碰过那个
批处理文件，所以「默认分支与 `--console` 分支都不设 `PYTHONPATH`」这件事

## 八、本轮全项目审计：三类「契约误解」与一条「半截管道」

这一节记录的不是"代码写丑了"，而是**写完了、看着对、实际不工作**的几类缺陷。
它们的共同点是：**没有任何报错**，只有一个安静的 `False` / 空列表 / 永不触发的回调。

### 1. `blivedm` 的 handler 契约：钩子不是钩子，`handle()` 是硬要求

原来的 `_WsReadyHandler` 是这么写的：

```python
class _WsReadyHandler:
    def __init__(self, fetcher): self.fetcher = fetcher
    async def _on_ws_connect(self): self.fetcher._ws_ready = True
    async def _on_ws_close(self): self.fetcher._ws_ready = False
```

然后 `self._register_handler(self._client, _WsReadyHandler(self))`。
作者的假设是"注册进 `self._handlers` 的对象，`blivedm` 会在合适的时机回调它的 `_on_ws_connect()`"。

读 `blivedm` 0.1.1 的源码，这个假设**两处都不成立**：

| 事实 | 位置 | 后果 |
| --- | --- | --- |
| `await self._on_ws_connect()` 调的是 **`BLiveClient` 自己的方法**，`self._handlers` 从头到尾没参与 | `blivedm/client.py` | `_ws_ready` 永远 `False` → `_wait_ws_ready()` 白等满 `connect_timeout`（15s）→ 每次连接都失败 |
| `await asyncio.shield(asyncio.gather(*(handler.handle(self, command) for handler in self._handlers), return_exceptions=True))` | `blivedm/client.py` | handler **必须有 `handle()`**；没有的话 `AttributeError` 在 `gather` 的**参数求值阶段**就抛出（还没进 gather，`return_exceptions=True` 救不了） |

第二条更隐蔽：那个 `AttributeError` 一路冒到 `_on_ws_message` 的宽 `except` 里被吞掉，
表现是"WebSocket 连上了、心跳在跑、日志干干净净、**一条弹幕都没有**"。

**可复用的规则**：凡是"把自己注册进第三方框架、指望框架回调某个方法名"的代码，
必须去**框架源码里确认那个方法名真的被调用**，而不是看到框架里有同名钩子就当它存在。
`blivedm` 真正保证的回调只有 `BaseHandler` 上列出的那几个（`_on_danmaku` / `_on_gift` /
`_on_buy_guard` / `_on_super_chat` / `_on_heartbeat` …），且**都经由 `handle()` 分派**。

> 附带一个"死代码"结论：`blivedm` 把 `INTERACT_WORD` 放进了 `IGNORED_CMDS`
> （`handlers.py`，配套 `_CMD_CALLBACK_DICT[cmd] = None`），
> 而 `LIKE` 根本不在它的回调表里 —— 所以子类里那两个 `_on_interact_word` / `_on_like`
> **永远不会被调用**。想让进入直播间 / 点赞事件进来，只能自己覆写 `handle()` 先解析命令名。
> 这类"看起来实现了、其实框架不给调"的方法，静态检查是查不出来的。

### 2. 基类契约：`connect()` 必须"尽快返回"，而不是"连到断为止"

基类的模型是（`danmaku/base.py` 的 `_thread_main`）：

```python
ok = loop.run_until_complete(self.connect(room, **kwargs))   # ← 这里必须返回
while not self._stopping:                                     # ← 然后才进空闲循环
    loop.run_until_complete(asyncio.sleep(0.1))
```

`connect()` 是**"建连并返回是否成功"**，长连接的维持交给后面那个空闲循环。
B站实现里却写了 `await self._join_task`（`join()` 要等连接真正结束才返回），
于是 `run_until_complete` 永不返回、空闲循环永不进入、`_stopping` 也没人看 ——
`stop()` 只是把一个标志置位，而没有任何人在检查它。

**可复用的规则**：模板方法（`_thread_main` 调子类 `connect`）里"父类写好的后续步骤"，
一旦子类把控制流截住，父类的所有清理与状态复位都会静默失效。
症状是"第一次能用、之后再也起不来"，因为 `_running` 卡在 `True`。
修法是给 `join` 挂 `add_done_callback`（连接真断了再从回调里上报并让基类线程退出），而不是 `await` 它。

### 3. `CancelledError` 不是 `Exception`

```python
try:
    await self._client.stop_and_close()
except Exception:          # ← 捕不到
    ...
```

`blivedm` 的 `stop_and_close()` 是 `stop()` + `await join()`，而 `join` 内部是
`await asyncio.shield(self._network_future)`，取消后抛 `CancelledError`。
Python 3.8 起 `CancelledError` 继承 **`BaseException`**，所以 `except Exception` 放它过去，
它从 `_thread_main` 的 `finally` 逃出去 —— `loop.close()`、`_running = False`、
`_notify_status(False)` **全都不会执行**。

**可复用的规则**：所有"以取消/关连接为预期的清理代码"都别用裸 `except Exception`。
本项目统一的写法是 `except (asyncio.CancelledError, Exception)`。

### 4. 「半截管道」：序列化器写好了，但没人调用它

`FilterEngine` 一直有完整的 `to_list()` / `from_list()`，`FilterRule` 有 `to_dict()` / `from_dict()`，
测试也都在（`tests/test_filters.py::TestSerialization`）。可是：

| 层 | 状态 |
| --- | --- |
| 模型层 `filters/rules.py` | ✅ 序列化/反序列化齐全 |
| 配置层 `config/manager.py` | ❌ `save()` 的 payload 只有 5 个键，**没有 `filters`**；`load()` 从不读 |
| 界面层 `ui/main_window.py` | ❌ 建引擎时硬编码 `filters=FilterEngine.default()` |

于是"筛选规则能存能读"这件事在测试里是**真的**，在程序里是**假的** ——
用户改完规则关掉窗口就丢，界面提示原文还写着"本次运行有效；如需永久保存请写入配置文件"。

**可复用的规则**：给一个子系统写序列化时，要顺着"谁调用它"往上追到**最外层入口**，
确认这条链真的接上了。`grep` 一下 `to_list(` 的**调用点**（而不是定义点）就能发现这类问题：

```bat
findstr /s /n /c:"to_list(" src\screenkey\*.py
```

### 5. 手改 JSON 会让引擎当场抛异常

`config/models.py` 的 `from_dict` 原来是 `return cls(**_filter_fields(cls, data))` ——
**只过滤字段名，不做任何类型强转**。JSON 里 `"1.5"` 是字符串，`"false"` 是**非空字符串**：

| 手写值 | 后果 |
| --- | --- |
| `"enabled": "false"` | 非空字符串 → `bool()` 为 `True`，用户想关掉输入结果开着 |
| `"global_cooldown": "1.5"` | `engine.py` 的 `if cfg.global_cooldown > 0:` → `TypeError: '>' not supported between instances of 'str' and 'int'`，**每条弹幕都中断** |
| `"x": "abc"` | `int("abc")` 在 `WindowGeometry.from_dict` 里炸（这一处原来有 `int()`，但没兜住） |

**可复用的规则**：配置层是**不可信输入**的边界，和网络报文同级。`from_dict` 里每一个字段都该问一句
"如果它是字符串/是 `None`/超范围会怎样"，并给出默认值。本项目为此加了
`_as_bool` / `_as_int` / `_as_float` / `_as_str` 与范围夹取。

### 6. 两个让缺陷"隐身"的语言特性

- **`from __future__ import annotations`**：`input/hotkey.py` 有 4 处
  `self._listener: Any = None` 却**根本没导入 `Any`**。因为注解被延迟成字符串，
  运行时不会求值，所以程序照跑；只有 `pyflakes` 能看出来。
  **结论**：这个 future import 会让"未定义的名字"在运行时彻底隐身，静态检查不是可选项。
- **只写不读的标志位**：`KeyboardController._stopping`、`MouseController._stopping`、
  `DouyinFetcher._last_heartbeat`、`DouyinFetcher._last_signature_error`、`MainWindow._input_enabled`
  全都是"赋值了但全项目没人读"。这类字段的正确处理只有两种：
  接上消费点，或者删掉。它和 `closeEvent` 不 `join()` 组合起来，
  直接导致**进程退出后物理按键还按着**。
  查法：对每个 `self._xxx = ` 赋值处，`grep` 它在别处**被读**的位置。

## 八之二、焦点窗口过滤：一个新功能为什么这么写

需求一句话：**只有指定窗口是前台窗口时才注入模拟键鼠**。
功能用法在 README，这里记的是实现上的几个非显然决定——都是"看起来可以更简单、但会更糟"的地方。

### 1. 新增的模块放在哪一层

`input/window.py` 是**输入层**的新成员，不是配置层、也不是界面层：

- 匹配部分（`FocusFilter.matches_*`）是**纯函数**，只吃字符串，离线可测；
- Win32 探测（`get_foreground_window()` / `list_windows()` / `window_info()`）集中在文件后半段；
- 它**不 import `config` 层**：配置通过 `FocusFilter.from_config(cfg)` 用 duck typing 读属性。

最后一条是为了守住「[一、总体分层](#一总体分层)」的单向依赖。如果 `input/window.py`
`from ..config.models import FocusFilterConfig`，依赖图就会多出一条
`input → config` 的边；今天不构成环，但下一个想在 `config` 里用到输入层常量的人就会造出环。

### 2. 为什么每次判定都新建 `FocusFilter`，而不是在 `Engine` 里建好存着

配置对象是**界面线程随时会改**的。如果引擎持有一份构造好的过滤器快照，那么每个能改配置的
入口（选项页 6 个控件、配置文件热重载、命令行）都必须记得同步它——漏一处，
症状就是"界面上明明关了过滤，实际还在拦"，而且**不报错**。

这正是「[八、本轮全项目审计](#八本轮全项目审计三类契约误解与一条半截管道)」
里那类"只写不读"缺陷的翻版。构造只是几个属性拷贝，省它没有意义。

### 3. 闸门为什么在 `_execute_match` 里、而且在冷却记账之前

```
_handle_message → _execute_match
   ├─ ① 焦点判定：不匹配 → return False      ← 冷却/去重尚未记账
   ├─ 去重 → 用户冷却 → 全局冷却
   ├─ mapping.delay 睡眠
   ├─ ② 焦点判定：再判一次（睡眠期间用户可能切走了窗口）
   └─ keyboard/mouse.execute(...)            ← 真正注入
```

两个决定都需要理由：

- **放在冷却之前**：冷却的目的是"限制注入频率"，而被拦下的那次**根本没有注入**。
  如果先记账再判定，用户切回游戏后还要再等一个冷却窗口，体感就是"切回来了还是没反应"。
  代价是恶意刷屏在非目标窗口前台时不再受限——但那种情况下本来就不注入，没有风险。
- **判两次**：`mapping.delay` 最长 5 秒。只在入口判定的话，一条带延迟的弹幕可能在用户
  切走窗口之后才真正注入——恰好就是这个功能要防的场景。

### 4. 一切 fail closed

下面这些情况**全部**按"不匹配"处理（＝不注入）：

| 情况 | 为什么不能放行 |
| --- | --- |
| 正则写错 | 放行＝按键打进"你当时正在看的任意窗口"，正是这个功能要防的事 |
| `get_foreground_window()` 返回 `None`（判定失败） | 取不到就不发，绝不赌 |
| 启用过滤但目标内容为空 | 没配好 ≠ 全部匹配 |
| 探测抛异常 | 同上；异常还要吞掉，不能让抓取线程挂掉 |

失败原因由 `FocusFilter.status_text()` 直接说出来（"读不到前台窗口：为保证安全，现在不会注入按键"
／"当前前台：Chrome → 不注入（窗口不匹配）"），显示在选项页那行实时状态里
——"没生效"必须能看出为什么，否则用户只会觉得"勾了没用"。

### 5. 自检与单测里为什么整段跳过

`main.py --selftest` 与测试都让引擎处于 `dry_run=True`。这时焦点过滤**不参与判定**。

理由：自检要证明的是"程序本身没坏"，如果它的结果取决于"跑的那一刻恰好哪个窗口在前台"，
它就**不可复现**了——同一台机器上跑两次可能一次 OK 一次 FAIL，这种自检比没有更糟。
焦点判定另有专门的自检项（真的探一次本机窗口并把前台窗口打印出来），
以及 `tests/test_window_focus.py` 里 96 项离线测试（注入 `get_foreground_window` 与
`keyboard.execute`，不碰真实窗口、不发真实按键）。

### 6. 界面上的一个坑：状态文案要在 try 里算

`status_text()` 是**在 GUI 定时器里**被调用的（选项页那行实时状态每秒刷新）。
PyQt5 的槽函数里异常逃出去＝`qFatal`，进程直接 `abort()`，退出码 `0xC0000409`，
**连 traceback 都看不到**。项目里已经因为这个原因闪退过一次
（见「[七之三](#七之三字段声明与运行时取值不一致导致收到第一条弹幕就闪退)」），
所以这里对探测和格式化都做了防御，并且在典型路径上**不查询目标窗口**（那要跨进程读内存，
每秒一次没必要）——只用前台窗口的信息就能算出会不会注入。

## 八之三、「发出去了但没人收到」：一次真实故障的取证与两个修复

这一节记的是一次**真实用户报告**的排查过程，因为它的结论违反直觉：
程序把按键**真的发出去了**（`SendInput` 返回成功、`GetLastError() == 0`），
记事本和游戏却**什么都收不到**，而程序也检测不到任何失败。

### 1. 先分清哪一类"没反应"

按键链路很长，出问题时第一件事是**定位断点**，而不是改代码：

```
弹幕到达 → 筛选 → 匹配 → 冷却/去重 → [焦点闸门] → KeyboardController.execute
                                                          ↓
                                              SendInput / keybd_event / 扫描码
                                                          ↓
                                                     目标窗口收到？
```

判据是日志：`engine.py` 里那行

```python
logger.info("弹幕「%s」(%s) → %s %s%s", ..., "" if ok else " [发送失败]")
```

- **日志里没有 `[按键]` 行** → 卡在前半段（筛选/匹配/冷却）。
- **有 `[按键] … → …` 行且没有 `[发送失败]`** → `execute()` 返回了 `True`，
  也就是 Win32 报告"注入成功"。断点在第 3 段：**系统收了，但没送到**。

### 2. 断点在第 3 段的三种原因

| 原因 | 判据 | 能否在代码里修 |
| --- | --- | --- |
| 本进程跑在**受限令牌**里（沙箱、降权宿主） | 读不到自身令牌（`OpenProcessToken` 失败）/ 完整性级别 < 中 | ❌ 环境问题 |
| 前台窗口**权限更高**（游戏以管理员运行） | 目标进程完整性级别 > 本进程 | ❌ 但可以两边一致 |
| 游戏有**内核级反作弊** | 上面两条都正常，仍收不到 | ❌ 明确说明 |

Windows 的 UIPI 在拦下注入时**不会**给调用方一个可检测的错误：`SendInput`
的成功返回值只表示"事件进了系统输入队列"，不表示"目标窗口收到了"。
所以**程序无法自动判断按键是否真的送达**——只能判断自己有没有资格送。

### 3. 实测取证（探针）

| 探针动作 | 结果 |
| --- | --- |
| `SendInput` 注入按键 | 返回 `True` |
| 之后读 `GetLastError()` | `0` |
| 记事本标题是否变化 | **没变** |
| `SetForegroundWindow` 聚焦记事本 | **失败** |
| `mkdir C:\Users\<用户>\.screenkey` | **`[WinError 5] 拒绝访问`** |
| `OpenProcessToken` 读自身令牌 | **失败** |

后两项说明进程在受限环境里。同一份日志里反复出现
`无法创建配置目录 …: [WinError 5] 拒绝访问`，是同一个根因的另一个表现。

### 4. 修复一：把"说不出来的失败"说出来

新增 `input/keycodes.py` 的 `current_integrity_level()` / `integrity_level_name()` /
`injection_environment_problem()` / `target_blocks_injection(pid)`，两级判定：

- `injection_environment_problem()`：**本进程自己**有没有资格注入（启动时查一次）；
- `target_blocks_injection(pid)`：**当前前台窗口**会不会挡下（切窗口时查一次）。

引擎侧（`engine.py`）：

```python
def _warn_injection_environment(self) -> None:   # start() 里调，每次运行只说一次
def _check_foreground_integrity(self) -> None:   # _execute_match 注入前调，同一 pid 只查一次
```

两者都走**新的事件类型** `EngineEvent.kind = "warning"`，在 `ui/worker.py` 里
转成 `EngineBridge.warningOccurred`，界面把它写进日志、状态栏显示 `⚠`。
**刻意不走 `errorOccurred`**：环境问题不是程序出错，`stats.errors` 被它污染之后
"错误数"就没意义了。另外 `start()` 里自检抛异常也必须吞掉（只写 debug 日志）——
它只是"多说一句"，不能成为启动的前置条件。

界面上**启动时也自检一次**（`MainWindow._check_injection_environment()` 在
`__init__` 末尾调用）：用户打开程序就该看到，而不是等弹幕来了才提示。

### 5. 修复二：配置目录必须回落到一个真能写的地方

旧实现的 `default_config_dir()` 只负责**给出**路径，不保证可写：
`~/.screenkey` 建不出来时，每一次 `save()` 都报一次错，用户的设置永远存不下来
（这正是上面那条 `WinError 5` 刷屏的来源）。

现在 `config/manager.py` 分成两个函数，职责明确：

- `default_config_dir()` —— 只回答"首选是哪个"（环境变量 → `~/.screenkey` → …）；
- `writable_config_dir()` —— 回答"**实际用哪个**"，顺序是
  `SCREENKEY_CONFIG_DIR`（显式指定，**不探测**，写不进去就如实报错）→
  `default_config_dir()` → `portable_config_dir()`（**程序旁边**的 `.screenkey`）→
  临时目录。

两个细节值得留着：

- 显式指定的目录**不探测**：用户说了算，偷偷换地方比报错更糟。
- 回落只提醒**一次**（`_fallback_warned` 集合）：`writable_config_dir()` 每次构造
  `ConfigManager` 都会被调用，每次都刷一条 warning 只会把日志淹掉。

### 6. `--check-env`：把判据交给用户

`main.py` 新增 `run_check_env()` 与 `--check-env`。它和 `--selftest` **分工不同**：

| | 查什么 | 会不会失败 |
| --- | --- | --- |
| `--selftest` | **代码链路**对不对 | 会 `[FAIL]`，退出码 3 |
| `--check-env` | **本机当前环境**能不能送达 | 只报告，**永远退出 0** |

所以 `--check-env` **不是**第 12 个自检项：自检必须离线可复现，而环境检查
天生依赖运行环境。`tests/test_cli.py::TestCheckEnv` 同时守住这两点
（`--check-env` 退出 0 + `--selftest` 的 `[OK]` 计数仍是 11）。

### 7. 判据的升级：间接指标不够，要**回环实测**

上面第 4 节那套判据（令牌完整性 / 前台窗口权限）后来被用户一句话推翻了隐含假设：

> 用户（m02963）：我是使用 `E:\DSHwork\幕键\启动.bat` 启动的

"在正常桌面双击 `启动.bat`"并不等于"没在受限环境里"——受限的是**宿主进程**，
而 `启动.bat` 可以从任何宿主里被启动。三条硬证据把这件事定了下来：

| 证据 | 结果 | 说明 |
| --- | --- | --- |
| `C:\Users\<用户>\.screenkey` 是否存在 | **从未被创建** | 该目录 ACL 是属主 `(OI)(CI)(F)` 完全控制，正常进程一定写得进去 |
| `src\screenkey_logs\app.log` 时间跨度 | **10 天**（10-10 → 10-19）每次运行都报 `WinError 5` | "受限"是常态，不是偶发 |
| **回环实测** | `SendInput` 返回 1 / `GetLastError=0` / **光标一像素都没动** | 输入被静默丢弃 |

第三行同时说明：**令牌完整性级别不能当判据**——受限宿主里读不到令牌、
看起来"级别正常"，注入照样无效。间接指标（启动方式、权限、环境变量）都只能
给出**假阴性**，唯一可信的判据是：**注入一个必然可见的变化，再读回来**。

于是 `input/keycodes.py` 增加三个东西：

```python
_PROBE_VK = 0x87          # F24：没有任何程序会绑定它，按一下不打字、不触发快捷键
_PROBE_MOVE = 1           # 1 像素：即使被误认为手抖也难以察觉

def interpret_injection_loopback(send_ok, cursor_before, cursor_after, send_error=0) -> tuple
def injection_loopback() -> tuple          # 只在 --check-env 里调用：会动光标
def restricted_host_markers() -> str       # 提示性判据，命中不代表一定失败
```

- 判据用**鼠标**而不是键盘：`GetCursorPos` 没有"桌面不活动就返回 0"的歧义；
  键盘（F24 + `GetAsyncKeyState`）只作辅助信号一起报出来。
- `injection_loopback()` 把判断抽成纯函数 `interpret_injection_loopback()`，
  所以三种结论（SendInput 直接失败 / 注入有效 / **静默丢弃**）都能在离线测试里
  逐条覆盖——真实回环会副作用式地动光标，不适合当测试的默认路径。
- 光标在 `finally` 里一定复位；注入前先朝屏幕内侧移动，避免贴边时被夹取导致
  "没动"的假阴性。
- 它**只在 `--check-env` 里跑**：这是有副作用的探测，不该在启动或每次连接时偷偷做。

同时 `启动.bat` 加了第 0 段预警（见「七之四」对这种"启动脚本自己也要能被测试"
的讨论）：被受限宿主启动时先打 `[警告]`，并给出该改用哪种方式启动。
这里踩了一个坑值得记下——**预警段里的 `pause` 必须按模式守卫**：

```bat
if /i not "%MODE%"=="selftest" if /i not "%MODE%"=="checkenv" pause
```

一句裸 `pause` 就会让 `--selftest` / `--check-env` 在管道或无人值守环境里
永远等一个不会到来的按键——而这两个分支恰恰是给自动化用的（`tests/test_cli.py`
的 `test_restricted_host_warning_never_blocks_automation` 现在钉住了这一点）。

### 8. 教训

**"代码里没有失败"不等于"用户那里成功了"。** 这一层失败发生在程序之外
（操作系统的安全边界），任何 `try/except` 都碰不到它。能做的只有三件事：
把**判据**查清楚、把**结论**说出来、把**环境问题与代码缺陷分开报**——
否则用户只会得到一个"日志全绿但什么都没有"的结果。

补一条（第二轮取证换来的）：**"用户说的启动方式"也不等于"实际的宿主环境"。**
凡是"能不能送达"这类问题，都要用**主动探测**（注入一次再读回来）来判定，
不要用间接指标推断——启动方式、令牌级别、环境变量都可能给出假阴性。

## 八之四、两个"证据"其实是工具自己的 bug

这两条都是在写 [项目现状.md](项目现状.md)、逐条复核既有结论时撞出来的，
形状一模一样：**一个失败得"太彻底、太稳定"的观测，被当成了环境问题的证据。**

### 1. `mkdir` 成功 ≠ 目录可写（致命：程序完全起不来）

`utils/logging_setup.py` 的 `get_log_dir()` 原来只做：

```python
candidate.mkdir(parents=True, exist_ok=True)   # 目录已存在 → 直接成功
```

两件事被混成一件：**"目录存在"和"能往里创建文件"**。在受限环境里前者成功、后者被拒，
于是 `RotatingFileHandler(...)` 抛 `PermissionError`，从 `setup_logging()` 冒到 `main()`，
**窗口还没创建程序就死了**——退出码 1、stdout 一个字都没有。

它还有个"时炸弹"性质：目录**不存在**时反而安全（`mkdir` 被拒 → `except OSError` →
回落临时目录 → 能写）。是用户那次**非受限**运行把 `~/.screenkey/logs` 建出来之后，
`mkdir` 才开始成功，崩溃条件才成立。这类"昨天好好的，今天打不开"的故障，
根因经常是**某个状态被别的东西变成了另一个分支**。

修法见 `get_log_dir()` / `_probe_writable()` / `_try_make_file_handler()`：

- 判断可写要用**真写一个文件再删掉**，不要用 `mkdir` 当代理；
- 回落链要**多级**（环境变量 → `~/.screenkey/logs` → 程序旁 `.screenkey/logs` → 临时目录）；
- handler 构造失败**只能降级**（`None` = 本次不写文件日志），绝不向上抛。

### 2. `ctypes` 不声明 `restype`，句柄会被截断

```python
OpenProcessToken(GetCurrentProcess(), TOKEN_QUERY, byref(h))   # 永远失败
```

`ctypes.windll` 默认 `restype = c_int`，而 `GetCurrentProcess()` 返回**伪句柄** `(HANDLE)-1`；
截成 32 位后不再是合法句柄 → `OpenProcessToken` 在**任何**环境都失败 → "读不到令牌"
被解释成"你在受限环境里"，**普通桌面用户也会收到假警告**（作者本人那次非受限运行
也中了一次，日志写进了 `C:\Users\hgcrts\.screenkey\logs\app.log`，可里面照样有这条警告）。

修法：给每个 API 显式声明 `argtypes` / `restype`，并用
`ctypes.WinDLL(name, use_last_error=True)`（不要用 `ctypes.windll.*`——两者是**不同的
library 对象、各自缓存函数指针**，在一个上面声明原型不会影响另一个）。修完实测
`current_integrity_level() == 0x1000`。

由此还调整了判据分工，从根上消掉第二类误报：

| 判据 | 定位 |
| --- | --- |
| `injection_loopback()` | **权威**（注入必然可见的变化再读回来），只在 `--check-env` 里跑 |
| 令牌完整性级别 | 只在**确定读到**时报"级别偏低"；**读不到不再当报警理由**（返回 `""`） |
| `restricted_host_markers()` | 提示性：命中才说"你是被这个宿主拉起来的"，并给出该怎么办 |

### 教训

**在把某个观测当证据之前，先验证观测工具本身。**
两条都命中了同一个嗅探信号：失败得太彻底、太稳定（永远失败、任何环境都失败）——
稳定到不像环境问题，就该回头查工具，而不是继续为它找环境解释。

## 八之五、一个可搜索下拉框的三个坑

需求很简单：「目标按键」从手填改成可下拉、可手填、边打边筛。
真正的坑都在**"显示的文字"和"实际的值"不是同一个东西**这件事上。

### 1. 显示文字不是键名

项文字用 `key_display()`（`方向键 ↑` / `字母 A` / `空格`），**键名放在 `itemData`**。
取值一律走 `current_key()`，它把项文字/中文说明/别名还原成 `VK_CODES` 里的规范键名。
如果直接读 `currentText()` 存盘，`settings.json` 里就会出现"空格（Space）"这种不存在的键，
行为是"保存成功、按不出来"——最坏的一种。

### 2. 可编辑下拉的 `currentIndex` 会骗人

用户选中某项之后接着改文字（可编辑下拉的常规操作），`currentIndex()` 仍然指向那一项。
所以 `current_key()` 只在

```python
self.currentText() == self.itemText(self.currentIndex())
```

时才信 `itemData`，否则按文字解析。**"索引"只对"用户真的选了某项"这件事负责**，
一旦文字被改过，事实源就变成了文字。

### 3. 校验口径必须只有一个

原来的校验是 `resolve_key(name) is not None`，而 `resolve_key` 对**任何单字符**
都走 `ord()` 兜底 → 中文 `左`（U+5DE6 = 24038）被当成合法键名，运行期
`send_key(...)` 才失败，表现为"配了没反应"。

现在校验统一走 `is_valid_key_name()`（`VK_CODES` 成员 + 单个空格 + 空白不敏感的
多词写法，所以搜索里能搜到的 `page down` 也能存成 `pagedown`），
**编辑器和控制器共用这一个函数**；键码目录、中文说明、搜索排序也都在
`input/keycodes.py` 里，是**不依赖 Qt 的纯函数**，所以这批测试全部离线。

> 顺带记一条分层经验：能被"纯函数化"的交互逻辑，就别放进控件里。
> 搜索排序（精确 → 前缀 → 键名包含 → 中文说明包含，比较前去掉空白）在
> `search_key_names()` 里，`KeyComboBox` 只负责把结果喂给 `QCompleter`——
> 排序规则改了不用起界面就能测。

### 4. 一个没有硬撑的取舍：弹窗候选按字面匹配

`QCompleter` 的候选过滤由 Qt 自己做：它只在**真实按键事件**里更新补全前缀，
程序化 `setEditText()` 不会更新（所以测试里断言候选数必须用 `QTest.keyClicks()`
走真事件路径）；而且它按字面做包含匹配，输入 `page down` 一个字都筛不出来。

一开始在 `editTextChanged` 里把前缀去掉空白再 `complete()`，看起来能补上——
真实敲键时会被 Qt 的下一次前缀更新覆盖，等于没做。于是**撤掉这段代码**，
保留诚实的分工：

- **候选弹窗**：Qt 字面匹配（`page` / `pagedown` / `page_down` 都能筛到，`page down` 不行）；
- **校验与存盘**：空白不敏感（`page down` 存成 `pagedown`）。

删掉"看起来在工作"的代码，比留着一个只在测试里成立的钩子好——后者会让
文档、测试、真实行为三者互相矛盾。

## 九、扩展点

想加东西时，改动通常落在这些位置：

| 想做的事 | 改哪里 |
| --- | --- |
| 支持新平台 | 继承 `danmaku/base.py` 的 `DanmakuFetcher`，实现 `connect` / `disconnect`，并在 `danmaku/__init__.py` 的 `create_fetcher()` 里注册；`Platform` 枚举（`config/models.py`）也要加一项 |
| 加一种匹配方式 | `input/mappings.py` 的 `MatchMode` 枚举 + `input/matcher.py` 的 `_match_one()` |
| 加一种筛选动作 | `filters/rules.py` 的 `FilterAction` 枚举 + `FilterRule.apply()` |
| 加一种筛选字段或比较方式 | `filters/rules.py` 的 `FieldMatch` / `CompareOp` 枚举 + `Condition.matches()` |
| 加一个配置项 | `config/models.py` 对应的子配置 dataclass；`from_dict` 用的 `_filter_fields()` 会自动忽略未知键，所以旧配置不会因此报错。**嵌套配置（如 `input.focus_filter`）要自己写 `from_dict`**：`_filter_fields()` 只处理一层 |
| 加一种焦点比对字段 | `input/window.py` 的 `FocusField` 枚举 + `window_info()` 里多采一个属性，再在 `_FIELD_GETTERS` 注册 |
| 加一个自检项 | `main.py` 的 `run_selftest()` 里按现有 `_check(name, fn)` 追加；**必须离线、必须可复现**，不要依赖网络或"当前恰好哪个窗口在前台"。**依赖运行环境**的检查不要放这里——那是 `--check-env`（`run_check_env()`）的地盘，它只报告、永远退出 0 |
| 加一种"环境不对"的判据 | `input/keycodes.py` 里加判定函数（返回 `""` 表示正常、非空字符串就是给用户看的原因），再挂到 `engine._warn_injection_environment()`（启动时）或 `engine._check_foreground_integrity()`（切窗口时）；**警告走 `kind="warning"`，不要用 `error`**，否则会污染 `stats.errors` |
| 加一种"注入能不能送达"的判据 | 优先做**主动回环**（注入一个必然可见的变化再读回来，见 `interpret_injection_loopback()` 的三种结论），而不是推断权限/宿主；纯判定部分要抽成纯函数，真实探测只在 `--check-env` 里跑 |
| 给某个键加中文说明 / 改进按键搜索 | `input/keycodes.py` 的 `_KEY_LABELS`（没有登记的名字自动派生：字母/数字/功能键/小键盘）与 `search_key_names()` 的排序；**这些是不依赖 Qt 的纯函数**，界面层只消费 |
| 新增一个"可选值"输入控件 | 照 `ui/key_selector.py` 的 `KeyComboBox`：项文字用 `*_display()`、真实值放 `itemData`、读取走 `current_key()` 并在 `currentText() == itemText(index)` 时才信索引；校验口径与控制器共用同一个函数，别各写一份（见八之五） |
| 给映射编辑器加一列 | 四处一起改：`ui/mapping_editor.py` 的 `_COL_*` 常量、`_build_tab()` 的表头、`_append_mapping()` 里建控件、`_row_to_mapping()` 里读值。**读值时若控件缺失必须回落到 `self._originals` 的原值**，否则"打开对话框直接保存"会把它清成 dataclass 默认值（这正是历史缺陷 #3）。再同步 `tests/test_mapping_editor.py` 的列数断言与 `_HIDDEN_FIELDS`。可参考「长按(秒)」列（`_COL_HOLD` / `_coerce_hold()` / `HOLD_MIN`–`HOLD_MAX`）。**如果这一列只对某些取值有意义，别让它常驻**：像 `_refresh_hold_column()` 那样，在相关下拉的 `currentIndexChanged` 以及 `load()`/`add_row()`/`remove_selected()`/`duplicate_selected()` 之后重算——单行用 `setVisible()` 藏控件、全表都不需要时再 `setColumnHidden()` 收起整列；**藏起来的是控件不是值**，切回来必须还在 |
| 给 `启动.bat` 加"先警告再继续"的段落 | 直接照抄第 0 段的形状（`set` 标志变量 → `if not defined … goto :after_warn`）；**任何 `pause` 都必须用 `if /i not "%MODE%"=="…"` 守卫**，否则会卡住 `--selftest` / `--check-env` 这类自动化分支 |
| 改界面 | `ui/` 下对应文件；**跨线程的数据一律走 `EngineBridge` 的信号**，不要新增直接操作控件的回调 |
| 让某处失败不再拖死程序 | 照 `utils/logging_setup.py` 的形状：**判断可写要真写一个文件**、回落链多级、构造型操作失败只降级不抛（见八之四第 1 节） |
| 新增一个动作枚举值（`KeyAction` / `MouseAction`） | 三处一起改：`input/mappings.py` 的枚举、实际执行处（`input/keyboard.py` / `mouse.py` 的 `execute()`）、**中文显示名**（`ui/mapping_editor.py` 的 `_KEY_ACTION_LABELS` / `_MOUSE_ACTION_LABELS`）。主窗口「映射」总表的「动作」列走 `action_label()` 读同一张表——漏了这步，界面就会在中文里冒出一个 `your_new_action`（这正是"总表显示英文"那个反馈的来源） |
| 新增一个 Win32 调用 | 用 `ctypes.WinDLL(name, use_last_error=True)` 并**显式声明 `argtypes`/`restype`**；不要用 `ctypes.windll.*`，也不要把"(HANDLE)-1"这类伪句柄交给未声明的默认 `c_int`（见八之四第 2 节） |

三处需要特别小心的地方：

1. **`ui/qt_env.configure_qt_environment()` 必须在任何 `from PyQt5...` 之前调用**
   （`main.py`），因为它负责把 `QT_PLUGIN_PATH` 指向 `PyQt5\Qt5\plugins`。
   `ui/__init__.py` 已经保证了导入顺序，新增入口时要照做。
2. **`danmaku/protobuf_lite.py` 的字段号与 `signature.py` 的 `SIGN_MD5_FIELDS` 顺序**
   都是协议的一部分，改之前先想清楚服务端会不会跟着改。
3. **`data/sign.js` 是第三方混淆代码，版权不属于本项目**，仅随包携带供研究学习，
   请勿商用或二次分发。想替换成自己的副本，用环境变量 `SCREENKEY_SIGN_JS`。
